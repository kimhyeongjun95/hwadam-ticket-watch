S3 보안 문제는 시험에서 거의 빠지지 않습니다. 저장 데이터 암호화 방식 네 가지와 전송 중 암호화, 브라우저 교차 출처 요청(CORS), 실수 삭제를 막는 MFA Delete, 접근 기록, 임시 링크, 지울 수 없게 잠그는 객체 잠금, 팀별 입구인 액세스 포인트를 다룹니다.

#### 저장 데이터 암호화 방식

| 방식 | 키를 누가 관리 | 요청 헤더 | 특징 |
|---|---|---|---|
| **SSE-S3** | S3가 만들고 관리(AES-256) | `x-amz-server-side-encryption: AES256` | **새 버킷·새 객체의 기본값**(2023년 1월부터). 추가 비용 없음 |
| **SSE-KMS** | **KMS 키**(AWS 관리형 또는 고객 관리형) | `x-amz-server-side-encryption: aws:kms` | 키 정책으로 누가 쓸지 통제, **CloudTrail로 키 사용 감사** |
| **DSSE-KMS** | KMS 키, **두 겹** 암호화 | `aws:kms:dsse` | 규정상 다중 계층 암호화가 필요할 때 |
| **SSE-C** | **고객이 AWS 밖에서** 관리 | 요청마다 키를 헤더로 보냄 | S3는 키를 저장하지 않음. **HTTPS 필수** |
| 클라이언트 측 암호화 | 고객 | 없음(이미 암호화된 데이터) | 올리기 전에 클라이언트가 암호화, 내려받은 뒤 복호화 |

#### SSE-KMS와 KMS 요청 한도

SSE-KMS 객체를 올리면 S3가 KMS의 `GenerateDataKey`를, 내려받으면 `Decrypt`를 부릅니다. 이 호출은 **KMS의 초당 요청 한도**에 들어갑니다. 한도는 리전에 따라 초당 10,000, 20,000, 100,000번이며 Service Quotas에서 늘릴 수 있습니다(강의의 5,500·10,000·30,000은 예전 값). 요청이 아주 많은 버킷은 한도에 걸려 느려질 수 있으므로 **S3 버킷 키(Bucket Key)**를 켭니다. 버킷 단위 키를 잠시 만들어 쓰므로 KMS 호출이 크게 줄어듭니다(최대 99%).

SSE-KMS 객체를 읽으려면 S3 권한과 함께 **그 KMS 키를 쓸 권한**도 있어야 합니다.

#### SSE-C

고객이 키를 직접 보관하고, 요청할 때마다 키를 헤더에 담아 보냅니다. S3는 키로 암호화·복호화만 하고 키는 버립니다. 키가 오가므로 **HTTPS만** 받습니다.

> **바뀐 점** 2026년 4월부터 **새 범용 버킷은 SSE-C가 기본으로 막혀** 있습니다. SSE-C를 쓰려면 버킷 기본 암호화 설정에서 막힌 암호화 유형(`BlockedEncryptionTypes`)을 풀어야 하고, 그 전에는 SSE-C 업로드가 403으로 거부됩니다. SSE-C 객체가 없던 계정은 기존 버킷도 같은 설정으로 바뀌었습니다.

#### 전송 중 암호화

S3에는 HTTP와 HTTPS 엔드포인트가 모두 있지만 HTTPS를 씁니다. 버킷 정책에서 `aws:SecureTransport`가 `false`인 요청을 Deny하면 **HTTPS를 강제**합니다.

#### 기본 암호화와 버킷 정책

- 버킷의 **기본 암호화**는 헤더 없이 올라온 객체를 자동으로 암호화합니다(기본 SSE-S3, SSE-KMS나 DSSE-KMS로 바꿀 수 있음).
- **버킷 정책은 기본 암호화보다 먼저 평가**됩니다. "SSE-KMS 헤더가 없는 업로드는 거부"처럼 특정 방식을 강제하려면 버킷 정책에서 `s3:x-amz-server-side-encryption` 조건으로 Deny합니다.

> **시험 포인트** "키 사용을 감사하고 키 순환·권한을 직접 통제" → SSE-KMS(고객 관리형 키). "키를 AWS에 맡기지 않음" → SSE-C 또는 클라이언트 측 암호화. "관리 부담 없이 암호화" → SSE-S3(기본값). "SSE-KMS로 바꾼 뒤 요청이 많아 스로틀링" → S3 버킷 키나 KMS 한도 증가. "암호화 안 된 업로드 거부" → 버킷 정책 Deny. "HTTPS가 아닌 요청 거부" → `aws:SecureTransport`.

> **실제 출제** 2026년 6월 후기는 문제 풀이 중 헷갈려 따로 정리한 개념에 *S3 암호화*를 꼽았습니다. 지문에서 "키를 누가 관리하나", "감사가 필요한가", "AWS에 키를 맡겨도 되나"를 먼저 찾으면 네 방식이 갈립니다.

@analogy
창고 물건에 **자물쇠**를 채우는 방법이 네 가지예요.

- **창고가 다 알아서(SSE-S3)**: 창고가 자물쇠와 열쇠를 모두 관리해요. 요즘은 따로 말하지 않아도 이렇게 채워요.
- **열쇠 보관소 열쇠로(SSE-KMS)**: 도시의 **열쇠 보관소(KMS)**에서 열쇠를 빌려 채워요. 누가 언제 열쇠를 빌렸는지 **출입 기록부(CloudTrail)**에 남아요. 대신 열쇠 보관소 창구가 1초에 받을 수 있는 손님 수가 정해져 있어서, 너무 바쁘면 줄이 생겨요. 그래서 **창고용 임시 열쇠(버킷 키)**를 받아 두고 써요.
- **자물쇠 두 개(DSSE-KMS)**: 규칙이 엄한 곳은 자물쇠를 두 겹으로 채워요.
- **내 열쇠를 들고 와서(SSE-C)**: 손님이 올 때마다 자기 열쇠를 가져와요. 창고는 채우고 바로 돌려줘요. 열쇠를 들고 다니니 꼭 **잠긴 트럭(HTTPS)**으로 와야 해요. 요즘 새 창고는 이 방법을 기본으로 막아 두었어요.
- **집에서 잠가 오기(클라이언트 측)**: 손님이 집에서 자물쇠를 채워 가져와요. 창고는 내용을 몰라요.

| 창고 | S3 |
|---|---|
| 창고가 알아서 채운 자물쇠 | SSE-S3 |
| 열쇠 보관소 열쇠 | SSE-KMS |
| 창고용 임시 열쇠 | S3 버킷 키 |
| 내가 들고 온 열쇠 | SSE-C |
| 집에서 잠가 오기 | 클라이언트 측 암호화 |
| 잠긴 트럭만 받기 | `aws:SecureTransport` |

#### CORS

**출처(origin)**는 프로토콜 + 호스트 + 포트입니다. `https://www.example.com`과 `https://other.example.com`은 출처가 다릅니다. 브라우저는 기본으로 **다른 출처**의 리소스를 불러오지 못하게 막고(동일 출처 정책), 상대 서버가 CORS 헤더로 허락할 때만 불러옵니다.

1. 브라우저가 먼저 `OPTIONS` **사전 요청(preflight)**을 보내며 `Origin` 헤더에 자기 출처를 적습니다.
2. 상대 서버가 `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`로 허락하면 실제 요청을 보냅니다.

S3에서는 정적 웹사이트 버킷(`my-html`)의 페이지가 **다른 버킷**(`my-assets`)의 이미지를 불러올 때 문제가 됩니다. CORS 규칙은 **불려 가는 쪽 버킷(`my-assets`)**에 설정합니다. 특정 출처를 적거나 `*`로 모두 허용합니다.

#### 미리 서명된 URL(Pre-signed URL)

비공개 객체를 **잠깐만** 내려받거나 올리게 하는 링크입니다. 링크를 만든 사람의 권한을 그대로 빌려 씁니다.

| 만드는 곳 | 최대 유효 기간 |
|---|---|
| S3 콘솔 | 12시간 |
| AWS CLI, SDK | 7일(CLI 기본 3,600초, `--expires-in`으로 지정) |

- 임시 자격 증명(역할)으로 만든 링크는 그 자격 증명이 끝나면 정해 둔 시간보다 **먼저 만료**됩니다.
- 쓰임: 로그인한 사용자에게만 유료 동영상 다운로드 허용, 사용자가 버킷의 정해진 위치에 직접 업로드, 수시로 바뀌는 사용자 목록에 파일 공유(버킷은 비공개 유지).

> **시험 포인트** "웹사이트가 다른 버킷의 글꼴·이미지를 불러오지 못함, 브라우저 콘솔에 CORS 오류" → 리소스가 있는 버킷에 CORS 규칙. "버킷을 공개하지 않고 특정 사용자에게 몇 시간만 다운로드 허용" → 미리 서명된 URL. "사용자가 앱 서버를 거치지 않고 S3에 직접 업로드" → PUT용 미리 서명된 URL. 전 세계 배포까지 필요하면 CloudFront 서명된 URL을 씁니다([15.1](#c15-cloudfront)).

@analogy
**CORS**: 진열장 가게(웹사이트)가 옆 창고의 사진을 가져다 걸고 싶어요. 그런데 손님의 브라우저는 "다른 가게 물건은 함부로 못 가져와요" 하고 막아요. 그래서 브라우저가 먼저 옆 창고에 "이 가게가 가져가도 돼요?" 하고 물어보고(사전 요청), 옆 창고 문에 **"이 가게는 가져가도 됨"** 안내가 붙어 있으면 가져와요. 안내는 **물건을 빌려주는 쪽 창고**에 붙여요.

**미리 서명된 URL**: 창고 주인이 **시간 제한 쪽지**를 써 줘요. "이 쪽지를 가진 사람은 오늘 오후 6시까지 3번 칸 물건 하나를 가져갈 수 있음." 쪽지에는 주인의 허락이 담겨 있어서, 창고 문을 활짝 열지 않고도 그 사람만 들어와요. 시간이 지나면 쪽지는 소용없어요.

| 창고 | S3 |
|---|---|
| "이 가게는 가져가도 됨" 안내 | CORS 규칙 |
| 먼저 물어보기 | 사전 요청(preflight) |
| 시간 제한 쪽지 | 미리 서명된 URL |

@topic c14-mfa-logs | MFA Delete와 서버 액세스 로그 | dom=1 | prio=2 | les=S3 MFA Delete; S3 MFA Delete Hands On; S3 Access Logs; S3 Access Logs - Hands On
#### MFA Delete

버전 관리 버킷에서 위험한 작업을 할 때 **MFA 코드**를 요구합니다.

| MFA가 필요한 작업 | MFA가 필요 없는 작업 |
|---|---|
| 객체 버전 **영구 삭제** | 버전 관리 켜기 |
| 버전 관리 **일시 중지** | 삭제된 버전 목록 보기 |

- **버전 관리가 켜져 있어야** 쓸 수 있습니다.
- **버킷 소유자(루트 사용자)만** 켜고 끌 수 있습니다.
- 콘솔에서는 켤 수 없고 **CLI, SDK, API**로 켭니다.

#### 서버 액세스 로그

버킷에 들어온 **모든 요청**(허용·거부 모두)을 다른 S3 버킷에 로그 파일로 남깁니다. 감사, 접근 분석에 쓰고 **Athena**로 조회합니다.

- 로그를 받는 버킷은 **같은 리전**에 있어야 합니다.
- **로그 버킷을 감시 대상 버킷과 같게 하면 안 됩니다.** 로그를 쓰는 일이 또 로그를 만들어 끝없이 커집니다.
- 전달은 최선 노력(best effort)이고 몇 시간 늦을 수 있습니다. 객체 단위 API 호출을 빠짐없이 감사하려면 CloudTrail 데이터 이벤트를 씁니다([24.4](#c24-cloudtrail)).

> **시험 포인트** "버전 관리 버킷에서 실수나 악의로 버전이 영구 삭제되는 것을 막음" → MFA Delete(더 강하게는 객체 잠금, [14.4](#c14-lock)). "버킷에 들어온 모든 요청을 기록해 분석" → 서버 액세스 로그(+ Athena). "로그 버킷 용량이 끝없이 늘어남" → 감시 대상 버킷에 로그를 쓰고 있지 않은지 확인.

> **후기에서** 2026년 2월 정리 노트의 키워드 목록에 "S3 데이터 실수로 삭제 방지 → 버전 관리 + MFA Delete"가 들어 있습니다.

@analogy
**MFA Delete**: 옛 물건까지 **완전히 버리거나** "옛 물건 쌓아 두기"를 멈출 때는, 창고 주인이 **휴대폰 인증 번호**까지 대야 해요. 아무나 실수로 다 버리지 못하게요. 이 규칙은 창고 주인(사장님)만 켤 수 있어요.

**액세스 로그**: 창고 문을 드나든 모든 사람을 **방문 기록장**에 적어요. 들어간 사람도, 거절당한 사람도요. 기록장은 **다른 창고**에 보관해요. 같은 창고에 두면 "기록장에 적으러 들어감"도 또 적어야 해서 기록장이 끝없이 두꺼워져요.

| 창고 | S3 |
|---|---|
| 휴대폰 인증 번호까지 확인 | MFA Delete |
| 방문 기록장 | 서버 액세스 로그 |
| 기록장은 다른 창고에 | 로그 대상 버킷 분리 |

@topic c14-lock | Glacier Vault Lock과 S3 객체 잠금 | dom=1 | prio=3 | les=Glacier Vault Lock & S3 Object Lock
규정상 데이터를 **정해진 기간 동안 지우거나 고칠 수 없어야** 할 때가 있습니다(금융 거래 기록, 감사 자료 등). 이것을 **WORM(Write Once Read Many)**, 한 번 쓰고 여러 번 읽기라고 합니다.

#### Glacier Vault Lock

예전 **Amazon Glacier**(볼트 기반 서비스)의 볼트에 **볼트 잠금 정책**을 걸고 잠그면, 그 정책은 아무도 바꾸거나 지울 수 없습니다. 볼트의 아카이브를 지우지 못하게 하는 데 씁니다.

> **바뀐 점** 볼트 기반 Amazon Glacier는 2025년 12월 15일부터 새 고객을 받지 않습니다. 새로 시작한다면 S3 Glacier 스토리지 클래스와 S3 객체 잠금을 씁니다. 시험에는 "Glacier Vault Lock = 바꿀 수 없는 WORM 정책"으로 나올 수 있습니다.

#### S3 객체 잠금(Object Lock)

- **버전 관리**가 켜져 있어야 합니다. 객체 **버전마다** 잠급니다.
- 잠긴 버전은 정한 기간 동안 **지우거나 덮어쓸 수 없습니다**(새 버전을 올리는 것은 가능).

| 보존 모드 | 누가 풀 수 있나 | 쓰임 |
|---|---|---|
| **규정 준수(Compliance)** | **아무도 못 함(루트 사용자 포함)**. 모드를 바꾸거나 기간을 줄일 수도 없음 | 규제상 반드시 보존 |
| **거버넌스(Governance)** | `s3:BypassGovernanceRetention` 권한이 있는 사용자는 지우거나 설정을 바꿀 수 있음 | 대부분은 막되 관리자에게 예외 허용, 규정 준수 모드 전 시험 |

- **보존 기간**: 정한 기간 동안 보호합니다. 늘릴 수는 있습니다.
- **법적 보존(Legal Hold)**: 기간 없이 **무기한** 보호합니다. 보존 모드·기간과 따로 걸리며, `s3:PutObjectLegalHold` 권한이 있으면 걸고 풉니다. 소송 중인 자료처럼 끝나는 날을 모를 때 씁니다.

> **시험 포인트** "규정상 7년간 누구도(루트 포함) 지울 수 없어야" → 객체 잠금 **규정 준수 모드**. "대부분은 못 지우지만 특정 관리자는 지울 수 있어야" → **거버넌스 모드**. "끝나는 날이 정해지지 않은 소송 자료 보존" → **법적 보존**. "Glacier 볼트의 정책을 바꿀 수 없게" → Vault Lock.

@analogy
**WORM**은 "한 번 넣으면 정해진 날까지 **절대 못 꺼내 버리는** 금고"예요.

- **엄격한 금고(규정 준수 모드)**: 날짜가 될 때까지 **창고 사장님도** 못 버려요. 날짜를 앞당길 수도 없어요.
- **관리자 열쇠가 있는 금고(거버넌스 모드)**: 보통 직원은 못 버리지만, 특별 관리자 열쇠를 가진 사람은 열 수 있어요.
- **"재판 중" 빨간 딱지(법적 보존)**: 날짜 없이 딱지를 붙여 둬요. 딱지를 뗄 권한이 있는 사람이 떼기 전까지는 못 버려요.
- **지하 보관실 봉인(Vault Lock)**: 옛 지하 보관실의 규칙표를 봉인하면, 그 규칙은 영원히 못 고쳐요.

| 금고 | S3 |
|---|---|
| 한 번 넣으면 못 버리는 금고 | WORM, 객체 잠금 |
| 사장님도 못 여는 금고 | 규정 준수 모드 |
| 관리자 열쇠 금고 | 거버넌스 모드 |
| "재판 중" 딱지 | 법적 보존 |
| 규칙표 봉인 | Glacier Vault Lock |

#### 액세스 포인트(Access Points)

버킷 하나를 여러 팀이 쓰면 버킷 정책이 길고 복잡해집니다. **액세스 포인트**는 버킷에 **팀이나 용도별 입구**를 따로 만들고, 입구마다 **액세스 포인트 정책**(버킷 정책과 같은 형식)을 둡니다.

| 액세스 포인트 | 정책 | 쓰는 쪽 |
|---|---|---|
| finance-ap | `/finance` 접두사 읽기·쓰기 | 재무팀 |
| sales-ap | `/sales` 접두사 읽기·쓰기 | 영업팀 |
| analytics-ap | 두 접두사 모두 읽기만 | 분석팀 |

- 액세스 포인트마다 **자기 DNS 이름**이 있습니다.
- 네트워크 출처를 **인터넷**이나 **VPC**로 정합니다. VPC 출처면 그 VPC 안에서만 접근하고, VPC 엔드포인트가 필요합니다. 엔드포인트 정책은 대상 버킷과 액세스 포인트 접근을 허용해야 합니다.
- 버킷 정책에서는 "액세스 포인트를 거쳐 오는 요청은 액세스 포인트 정책에 맡긴다"는 위임만 해 두면 됩니다.

#### S3 Object Lambda

객체를 **꺼내 주기 직전에 Lambda로 바꿔서** 돌려줍니다. 원본은 하나만 두고, 쓰는 쪽마다 다른 모습으로 보여 줄 수 있습니다.

- 구성: 버킷 → **S3 액세스 포인트** → Lambda 함수 → **S3 Object Lambda 액세스 포인트** → 앱
- 쓰임: 분석팀에 줄 때 **개인정보(PII) 가리기**, XML을 JSON으로 **형식 바꾸기**, 요청한 사람에 맞춰 이미지 **크기 조정이나 워터마크**

> **바뀐 점** S3 Object Lambda는 2025년 11월 7일부터 **기존 사용 고객**(과 일부 파트너)만 쓸 수 있습니다. AWS는 대안으로 CloudFront·API Gateway·함수 URL로 Lambda를 부르는 방법, 클라이언트에서 변환하는 방법, 이미지라면 Dynamic Image Transformation for Amazon CloudFront를 안내합니다. 시험에는 "원본 하나, 요청마다 PII 가리기 → S3 Object Lambda"로 나올 수 있습니다.

> **시험 포인트** "여러 팀이 한 버킷을 쓰는데 버킷 정책이 너무 복잡" → 액세스 포인트. "VPC 안에서만 버킷 데이터에 접근" → VPC 출처 액세스 포인트(+ VPC 엔드포인트). "원본은 그대로 두고 앱마다 개인정보를 가린 버전을 제공" → S3 Object Lambda.

@analogy
**액세스 포인트**: 큰 창고에 팀마다 **전용 입구**를 따로 내요. 재무팀 입구에는 "재무 칸만 넣고 꺼내기", 영업팀 입구에는 "영업 칸만", 분석팀 입구에는 "둘 다 보기만" 안내를 붙여요. 창고 정문의 안내문은 짧게 "각 입구 안내를 따르세요"만 적으면 돼요. 단지 안(VPC)에서만 쓰는 입구도 만들 수 있어요.

**Object Lambda**: 입구에 **손질 담당 심부름꾼**을 세워요. 분석팀이 손님 명단을 꺼내 가면, 심부름꾼이 전화번호를 검은 펜으로 가려서 건네줘요. 원본 명단은 그대로예요. 다만 이 손질 담당은 이제 원래 쓰던 가게만 부를 수 있어요.

| 창고 | S3 |
|---|---|
| 팀 전용 입구 | 액세스 포인트 |
| 입구마다 붙인 안내 | 액세스 포인트 정책 |
| 단지 안에서만 쓰는 입구 | VPC 출처 액세스 포인트 |
| 손질 담당 심부름꾼 | S3 Object Lambda |

@quiz
Q: 암호화 키 사용 기록을 감사해야 하고, 키 권한을 직접 통제해야 합니다. 어떤 방식인가요?
A: SSE-KMS(고객 관리형 KMS 키)입니다. 키 사용이 CloudTrail에 남습니다.
Q: SSE-KMS로 바꾼 뒤 요청이 많은 버킷에서 스로틀링 오류가 납니다. 대책은?
A: S3 버킷 키를 켜서 KMS 호출을 줄이거나, KMS 요청 한도 증가를 요청합니다.
Q: 회사 규정상 암호화 키를 AWS에 저장할 수 없지만 S3가 서버 측에서 암호화하게 하고 싶습니다. 무엇을 쓰나요? 2026년 4월 이후 새 버킷이라면 무엇을 더 해야 하나요?
A: SSE-C입니다. 새 버킷은 SSE-C가 기본으로 막혀 있으므로 기본 암호화 설정에서 SSE-C를 허용해야 하고, 요청은 HTTPS로 보냅니다.
Q: `my-html` 버킷의 정적 웹사이트가 `my-assets` 버킷의 이미지를 불러오지 못하고 브라우저에 CORS 오류가 납니다. 어디에 무엇을 설정하나요?
A: `my-assets` 버킷에 `my-html` 웹사이트 출처를 허용하는 CORS 규칙을 설정합니다.
Q: 비공개 버킷의 파일을 특정 고객에게 24시간 동안만 내려받게 하려면? 콘솔에서 만들어도 되나요?
A: 미리 서명된 URL을 씁니다. 콘솔은 최대 12시간이므로 CLI나 SDK로 만듭니다(최대 7일).
Q: MFA Delete를 켤 수 있는 사람과 방법은?
A: 버킷 소유자(루트 사용자)가 CLI, SDK, API로 켭니다. 버전 관리가 켜져 있어야 합니다.
Q: 서버 액세스 로그를 켰더니 로그 버킷이 끝없이 커집니다. 원인은?
A: 로그를 감시 대상 버킷 자신에 쓰고 있어 로그 쓰기가 다시 로그를 만듭니다. 다른 버킷으로 바꿉니다.
Q: 감사 자료를 5년 동안 루트 사용자를 포함해 누구도 지우거나 덮어쓰지 못하게 해야 합니다.
A: 버전 관리를 켜고 S3 객체 잠금 규정 준수 모드로 5년 보존 기간을 둡니다.
Q: 객체 잠금을 쓰되, 보안팀 관리자만은 필요할 때 객체를 지울 수 있어야 합니다.
A: 거버넌스 모드를 쓰고, 관리자에게 `s3:BypassGovernanceRetention` 권한을 줍니다.
Q: 데이터 레이크 버킷을 쓰는 팀이 20개로 늘어 버킷 정책 관리가 어렵습니다. 대책은?
A: 팀별 S3 액세스 포인트를 만들고 액세스 포인트마다 정책을 둡니다.
