**IAM(Identity and Access Management)**은 AWS 계정 안에서 **누가(사용자, 역할) 무엇을(작업) 어디에(리소스) 할 수 있는지**를 관리하는 글로벌 서비스입니다. 요금이 없고, 리전을 고르지 않습니다.

#### 루트 사용자

계정을 만들 때 쓴 이메일과 비밀번호로 로그인하는 사용자가 **루트 사용자**입니다. 계정의 모든 권한을 가지며 정책으로 막을 수 없습니다(조직의 SCP를 받는 멤버 계정은 예외, [25.1](#c25-org)). 그래서 루트 사용자는

- MFA를 걸어 금고에 넣듯 보관하고,
- 결제 정보 변경, 계정 해지, 루트만 할 수 있는 몇 가지 작업에만 씁니다.
- 액세스 키를 만들지 않습니다.

#### 사용자와 그룹

- **IAM 사용자**는 사람이나 프로그램 하나를 나타냅니다. 한 사람에게 한 사용자를 주고, 계정을 같이 쓰지 않습니다.
- **IAM 그룹**은 사용자의 묶음입니다. 그룹에 정책을 붙이면 그룹의 모든 사용자가 그 권한을 받습니다.
- 그룹에는 **사용자만** 들어갑니다. 그룹 안에 그룹을 넣을 수 없고, 역할도 넣지 않습니다.
- 사용자는 그룹에 속하지 않아도 되고, 여러 그룹에 동시에 속할 수도 있습니다. 이때 권한은 모든 그룹 정책과 사용자 자신의 정책을 합친 것입니다.

요즘은 사람 사용자를 IAM 사용자로 하나씩 만들기보다 **IAM Identity Center**로 회사 계정에 연결해 임시 자격 증명을 쓰는 방식을 권장합니다([25.4](#c25-identity-center)). 강의와 시험은 두 방식을 모두 다룹니다.

#### 비밀번호 정책과 MFA

계정의 **비밀번호 정책**으로 최소 길이, 대문자·숫자·특수 문자 요구, 만료 기간, 이전 비밀번호 재사용 금지, 사용자가 자기 비밀번호를 바꿀 수 있는지를 정합니다.

**MFA(멀티 팩터 인증)**는 비밀번호(아는 것)에 기기(가진 것)를 더하는 로그인입니다. 비밀번호가 새도 기기가 없으면 들어올 수 없습니다.

| MFA 기기 | 예 |
|---|---|
| 가상 MFA 앱 | Google Authenticator, Authy 같은 휴대폰 앱의 6자리 코드 |
| 패스키·보안 키(FIDO) | YubiKey 같은 USB 키, 휴대폰·노트북의 패스키 |
| 하드웨어 TOTP 토큰 | 숫자가 바뀌는 열쇠고리형 장치 |

사용자 하나에 MFA 기기를 여러 개(최대 8개) 등록할 수 있습니다.

#### 콘솔 동시 로그인

브라우저 하나에서 여러 계정·사용자로 동시에 로그인할 수 있습니다(멀티 세션, 최대 5개). 개발 계정과 운영 계정을 오갈 때 로그아웃하지 않아도 됩니다. 시험보다는 실습 편의 기능입니다.

> **시험 포인트** "루트 사용자를 보호하라"는 보기에서는 *MFA 활성화*와 *루트 액세스 키 삭제(또는 만들지 않기)*가 정답입니다. "루트 사용자로 일상 작업"이나 "루트 자격 증명을 팀과 공유"가 들어간 보기는 틀립니다.

@practice
- **루트 사용자**: 계정을 만든 직후 MFA를 걸고, 루트 비밀번호와 MFA 기기는 대표나 보안 담당자가 따로 보관합니다. 결제 수단 변경, 계정 해지처럼 루트만 할 수 있는 일에만 꺼냅니다.
- **그룹으로 권한 주기**: 개발자 10명 남짓한 스타트업은 `Admins`, `Developers`, `ReadOnly` 같은 그룹을 만들고 입사자를 그룹에 넣어 권한을 줍니다. 부서를 옮기면 그룹만 바꾸고, 퇴사하면 사용자를 지웁니다.
- **Identity Center로 넘어가기**: 직원이 수십 명을 넘거나 AWS 계정이 여러 개가 되면 IAM 사용자를 하나씩 만들지 않고, Identity Center를 회사 Google Workspace나 Microsoft Entra ID와 연결합니다. 회사 로그인 한 번으로 여러 계정에 들어가고, 퇴사 처리도 회사 계정 하나만 막으면 끝납니다.
- **MFA**: 보안 점검에서 가장 먼저 보는 항목이 관리자 계정의 MFA 적용 여부입니다. 콘솔에 로그인하는 모든 사람에게 MFA를 요구하는 회사가 많습니다.

@easy
IAM은 회사 건물의 출입 관리 시스템과 같습니다. 사람마다 사원증(IAM 사용자)을 하나씩 발급하고, 부서(그룹)에 따라 들어갈 수 있는 층을 정합니다. 개발팀은 개발 서버실까지, 재무팀은 재무 시스템까지만 들어가는 식입니다. 사원증을 여럿이 돌려 쓰면 누가 무엇을 했는지 알 수 없으니 한 사람에 하나씩 줍니다.

루트 사용자는 건물주의 마스터키입니다. 모든 문이 열리고 막을 방법이 없으니, 평소에는 금고에 넣어 두고 계약 변경 같은 일에만 꺼냅니다.

MFA는 비밀번호에 "지금 손에 든 기기"를 더하는 확인입니다. 은행 이체 때 OTP를 함께 입력하는 것과 같은 원리로, 비밀번호가 새도 기기가 없으면 들어올 수 없습니다.

**IAM 정책**은 "어떤 작업을 어떤 리소스에 대해 허용(또는 거부)한다"를 적은 JSON 문서입니다. 사용자, 그룹, 역할에 붙이는 정책을 **자격 증명 기반 정책**이라 하고, S3 버킷처럼 리소스에 붙이는 정책은 **리소스 기반 정책**이라 합니다([25.3](#c25-resource)).

#### 정책의 구조

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadReports",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::company-reports",
        "arn:aws:s3:::company-reports/*"
      ],
      "Condition": { "IpAddress": { "aws:SourceIp": "203.0.113.0/24" } }
    }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `Version` | 정책 언어 버전. 항상 `"2012-10-17"`을 씁니다 |
| `Statement` | 규칙 목록. 하나 이상의 문장(statement)으로 이루어집니다 |
| `Sid` | 문장 이름(선택) |
| `Effect` | `Allow` 또는 `Deny` |
| `Principal` | 이 문장이 적용되는 주체. **리소스 기반 정책에만** 씁니다 |
| `Action` | 허용·거부할 API 작업. `서비스:작업` 형식(`s3:GetObject`, `ec2:*`) |
| `Resource` | 대상 리소스의 ARN |
| `Condition` | 적용 조건(출발지 IP, MFA 여부, 태그, 리전 등)(선택) |

**ARN(Amazon Resource Name)**은 리소스의 전체 주소입니다. `arn:aws:서비스:리전:계정ID:리소스` 형식이고, S3처럼 리전·계정이 비는 서비스도 있습니다. 위 예에서 `company-reports`는 버킷 자체(목록 보기용), `company-reports/*`는 버킷 안의 객체(읽기용)라 둘을 따로 적었습니다.

#### 평가 규칙 세 줄

1. 아무것도 허용하지 않으면 **기본은 거부**입니다(암묵적 거부).
2. 어느 정책이든 `Allow`가 있으면 허용됩니다.
3. 어느 정책이든 **명시적 `Deny`가 있으면 무조건 거부**됩니다. Deny가 Allow를 이깁니다.

더 자세한 평가 순서(SCP, 권한 경계, 리소스 정책까지)는 [25.2](#c25-policy-adv)에서 다룹니다.

#### 관리형 정책과 인라인 정책

| 종류 | 설명 | 언제 |
|---|---|---|
| AWS 관리형 정책 | AWS가 만들고 갱신하는 정책(`AdministratorAccess`, `ReadOnlyAccess`) | 빠르게 시작할 때 |
| 고객 관리형 정책 | 내가 만들어 여러 곳에 붙이는 정책. 버전 관리됨 | 회사 표준 권한 |
| 인라인 정책 | 사용자·그룹·역할 하나에만 들어 있는 정책 | 딱 한 곳에만 필요한 예외 |

> **시험 포인트** 보기에 `"Action": "*"`, `"Resource": "*"`처럼 넓게 연 정책이 있으면 **최소 권한 원칙**에 어긋납니다. 필요한 작업과 리소스만 적은 보기를 고릅니다. 정책 JSON이 문제에 나오면 Effect, Action, Resource, Condition 순서로 읽고, Deny 문장이 있는지 먼저 봅니다.

@practice
- **최소 권한 정책**: 데이터 분석가에게 `AdministratorAccess`를 주는 대신 "분석용 버킷 읽기 + Athena 쿼리 실행"만 허용하는 고객 관리형 정책을 만들어 분석팀 그룹에 붙입니다.
- **조건으로 좁히기**: 사내 IP 대역에서만 작업을 허용하거나(`aws:SourceIp`), MFA로 로그인한 경우에만 EC2 종료를 허용합니다(`aws:MultiFactorAuthPresent`). 태그가 `Team=payments`인 자원만 그 팀이 다루게 하는 조건도 자주 씁니다.
- **명시적 Deny로 사고 막기**: 개발자 그룹에 운영 DB 삭제(`rds:DeleteDBInstance`)를 Deny로 걸어 두면, 다른 정책이 실수로 넓게 열려 있어도 삭제할 수 없습니다.
- **정책도 코드로**: 정책을 Terraform이나 CloudFormation으로 관리하고 코드 리뷰를 거쳐 바꾸는 회사가 많습니다. IAM Access Analyzer는 CloudTrail 기록을 보고 실제로 쓴 권한만 담은 정책 초안을 만들어 줍니다.

@easy
IAM 정책은 "누가 / 무엇을 / 어디에 / 어떤 조건에서" 할 수 있는지 적은 규칙입니다. 회사 전결 규정에 "팀장은 / 지출을 / 자기 팀 예산에서 / 100만 원 이하일 때" 승인할 수 있다고 적는 것과 구조가 같습니다. JSON의 `Action`이 무엇을, `Resource`가 어디에, `Condition`이 어떤 조건에서입니다.

판정 규칙은 세 줄입니다. 적혀 있지 않으면 안 됩니다. 허용이 하나라도 있으면 됩니다. 그러나 어딘가에 금지가 적혀 있으면 다른 허용이 있어도 안 됩니다. 규정집 한 곳에 "이 금고는 누구도 열 수 없다"고 쓰여 있으면 다른 조항으로 풀 수 없는 것과 같습니다.

AWS를 다루는 길은 세 가지입니다. 사람이 브라우저로 쓰는 **관리 콘솔**, 터미널에서 명령으로 쓰는 **AWS CLI**, 코드에서 부르는 **SDK**입니다. 세 길 모두 결국 같은 **AWS API**를 부릅니다.

#### 무엇으로 로그인하나

| 길 | 자격 증명 |
|---|---|
| 관리 콘솔 | 사용자 이름 + 비밀번호 + MFA |
| CLI | 액세스 키(키 ID + 비밀 액세스 키) 또는 Identity Center 로그인(`aws sso login`) |
| SDK | 액세스 키, 또는 실행 환경의 IAM 역할 |

**액세스 키**는 사용자 이름·비밀번호와 같은 것입니다. 키 ID(`AKIA…`)와 비밀 액세스 키 한 쌍으로, 비밀 키는 만들 때 한 번만 보여 줍니다.

```bash
aws configure                  # 키 ID, 비밀 키, 기본 리전, 출력 형식을 입력
aws sts get-caller-identity    # 지금 누구로 호출하는지 확인
aws iam list-users             # IAM 사용자 목록
aws s3 ls                      # 버킷 목록
```

#### CloudShell

**AWS CloudShell**은 콘솔에서 바로 여는 브라우저 터미널입니다. 로그인한 사용자 권한으로 이미 인증돼 있고 AWS CLI가 설치돼 있어, `aws configure`가 필요 없습니다. 리전마다 홈 디렉터리(1GB)가 따로 유지되고, 일부 리전에서는 쓸 수 없습니다. 시험 범위 밖 서비스 목록에 들어 있어 시험에는 나오지 않습니다.

> **주의** 액세스 키를 코드, 설정 파일, EC2 안에 넣어 두는 것은 시험에서 항상 틀린 보기입니다. EC2나 Lambda에서 AWS를 부를 때는 **IAM 역할**을 붙입니다([4.4](#c04-role)). 키가 새면 바로 비활성화하고 새 키로 바꿉니다.

@practice
- **CLI로 반복 작업**: 운영자는 콘솔을 클릭하는 대신 CLI 스크립트로 반복 작업을 합니다. 매일 밤 개발 계정의 EC2를 끄는 스크립트, 모든 리전의 공개 S3 버킷을 찾는 점검 스크립트가 흔한 예입니다.
- **SDK로 서비스 호출**: 백엔드 서버(Java, Python, Node.js)는 SDK로 S3에 파일을 올리고 SQS에 메시지를 넣습니다. 이때 키는 코드에 적지 않고 서버에 붙인 IAM 역할에서 자동으로 받습니다.
- **배포 파이프라인**: GitHub Actions 같은 CI에서 AWS로 배포할 때는 장기 액세스 키를 저장하지 않고, OIDC로 역할을 맡아 임시 자격 증명을 받는 방식이 표준입니다.
- **키 유출 사고**: 공개 저장소에 올라간 액세스 키는 자동 수집 봇이 금방 가져가 비싼 인스턴스를 띄우는 데 씁니다. AWS도 공개된 키를 찾으면 계정 주인에게 알리고 그 키의 권한을 제한하지만, 키를 비활성화하고 피해를 확인하는 일은 고객이 해야 합니다.

@easy
콘솔은 웹 화면에서 버튼을 눌러 일하는 방식이고, CLI는 같은 일을 터미널 명령으로, SDK는 프로그램 코드로 하는 방식입니다. 은행 업무를 인터넷 뱅킹 화면으로 하든, 은행 API를 쓰는 회계 프로그램으로 하든 결국 같은 은행 시스템에 요청이 가는 것과 같습니다. AWS에서는 그 시스템이 AWS API입니다.

액세스 키는 프로그램용 아이디와 비밀번호입니다. 코드에 적어 저장소에 올리면 그대로 유출됩니다. AWS 안에서 도는 프로그램(EC2, Lambda)은 키 대신 역할로 권한을 받습니다.

**IAM 역할(Role)**은 사람이 아닌 주체가 **잠시 맡는** 권한 묶음입니다. EC2, Lambda 같은 AWS 서비스나 다른 계정의 사용자가 역할을 맡으면(assume), **STS(Security Token Service)**가 몇 분에서 몇 시간만 유효한 **임시 자격 증명**을 발급합니다. 장기 액세스 키를 어디에도 저장하지 않으므로 새어 나갈 것이 없습니다.

#### 역할이 쓰이는 곳

| 상황 | 역할 |
|---|---|
| EC2 안의 앱이 S3를 읽음 | EC2 인스턴스 역할(인스턴스 프로파일로 붙임) |
| Lambda 함수가 DynamoDB에 씀 | Lambda 실행 역할 |
| 다른 계정의 사용자가 우리 계정 작업 | 교차 계정 역할([25.3](#c25-resource)) |
| 회사 로그인으로 AWS 사용 | 페더레이션으로 맡는 역할([25.4](#c25-identity-center)) |

역할에는 두 가지 정책이 붙습니다. **신뢰 정책**은 "누가 이 역할을 맡을 수 있는가"(예: `ec2.amazonaws.com`), **권한 정책**은 "맡으면 무엇을 할 수 있는가"입니다.

#### 요청 하나의 흐름

1. EC2를 만들 때 S3 읽기 권한이 든 역할을 붙입니다.
2. EC2 안의 앱(SDK)은 인스턴스 메타데이터에서 임시 자격 증명을 자동으로 받습니다. 받는 과정은 STS가 처리합니다.
3. 앱은 그 자격 증명으로 S3를 읽습니다. 자격 증명은 만료 전에 자동으로 갱신됩니다.

#### IAM 보안 도구

| 도구 | 범위 | 보여 주는 것 |
|---|---|---|
| 자격 증명 보고서 | 계정 전체 | 모든 사용자의 비밀번호, 액세스 키, MFA 상태(CSV) |
| 마지막 액세스 정보(Access Advisor) | 사용자·역할 하나 | 서비스별 마지막 사용 시각. 안 쓰는 권한을 걷어 낼 근거 |

#### IAM 모범 사례

- 루트 사용자는 계정 설정에만 쓰고 MFA를 겁니다.
- 사람마다 사용자 하나(가능하면 Identity Center), 권한은 그룹으로 줍니다.
- 강한 비밀번호 정책과 MFA를 겁니다.
- AWS 서비스에는 역할을 붙이고, 액세스 키는 CLI·SDK용으로만 만듭니다.
- 자격 증명 보고서와 마지막 액세스 정보로 권한을 정기적으로 점검합니다.
- 키와 비밀번호를 절대 공유하지 않습니다.

#### 공동 책임 모델

**AWS는 클라우드 자체의 보안**(데이터 센터, 하드웨어, 네트워크, 가상화 계층)을, **고객은 클라우드 안의 보안**을 책임집니다. IAM으로 보면 고객이 맡는 일은 다음과 같습니다.

- 사용자, 그룹, 역할, 정책을 만들고 관리하기
- MFA를 걸고 키를 교체하기
- 권한을 점검하고 최소 권한으로 줄이기
- 접근 패턴을 분석하기

> **시험 포인트** "EC2의 애플리케이션이 S3에 접근해야 한다. 가장 안전한 방법은?"의 답은 거의 항상 **필요한 권한만 가진 IAM 역할을 EC2에 붙인다**입니다. 액세스 키를 EC2에 저장하거나 사용자 데이터에 넣는 보기는 틀립니다.

@practice
- **EC2 인스턴스 역할**: 사진 업로드 API 서버(EC2)에 "uploads 버킷 쓰기"만 되는 역할을 붙입니다. 코드에 키가 없고, 서버가 뚫려도 공격자가 할 수 있는 일이 그 버킷 쓰기로 제한됩니다.
- **Lambda 실행 역할**: 주문 처리 Lambda에는 "주문 테이블 쓰기 + 주문 대기열 메시지 받기"만 허용합니다. 함수마다 역할을 따로 만드는 것이 기본입니다.
- **교차 계정 역할**: 보안팀 계정의 점검 도구가 각 서비스 계정의 `SecurityAudit` 역할을 맡아 설정을 검사합니다. Datadog 같은 외부 모니터링 서비스를 연결할 때도 우리 계정에 역할을 만들고, 그 회사 계정이 외부 ID 조건을 지켜 맡게 합니다.
- **보안 도구로 정리**: 분기마다 자격 증명 보고서로 90일 넘게 안 쓴 액세스 키를 찾아 지우고, 마지막 액세스 정보로 쓰지 않는 서비스 권한을 걷어 냅니다.
- **공동 책임 모델**: 실제 클라우드 보안 사고는 대부분 고객 몫에서 시작합니다. 공개로 열린 S3 버킷, 유출된 키, 전 세계에 열어 둔 보안 그룹이 대표적입니다. 데이터 센터 출입 통제나 디스크 폐기는 AWS가 맡고, 그 감사 보고서는 AWS Artifact에서 받습니다.

@easy
역할은 사원증보다 **방문증**에 가깝습니다. 들어올 때 받아서 정해진 시간만 쓰고, 시간이 지나면 저절로 쓸 수 없게 됩니다. EC2나 Lambda 같은 서비스, 다른 회사 직원이 이 방문증을 받아 일합니다. 반면 액세스 키는 영구 열쇠라서, 복사되면 누군가 바꿀 때까지 계속 쓸 수 있습니다. 그래서 AWS 안에서 도는 프로그램에는 열쇠 대신 방문증을 줍니다.

공동 책임 모델은 건물 임대 계약과 같습니다. 건물주(AWS)는 건물 구조, 전기, 경비를 책임지고, 입주사(고객)는 사무실 문 잠금과 직원 출입 권한을 관리합니다. 사무실 문을 열어 두고 퇴근해서 생긴 도난은 입주사 책임입니다.

@quiz
Q: IAM 그룹에 다른 그룹이나 역할을 넣을 수 있나요?
A: 없습니다. 그룹에는 사용자만 들어갑니다. 사용자는 여러 그룹에 동시에 속할 수 있습니다.
Q: 한 사용자에게 붙은 정책 중 하나는 `s3:*`를 Allow하고, 다른 하나는 `s3:DeleteObject`를 Deny합니다. 이 사용자는 객체를 지울 수 있나요?
A: 없습니다. 명시적 Deny는 어떤 Allow보다 우선합니다.
Q: IAM 정책에서 `Principal` 필드는 어떤 정책에 쓰나요?
A: S3 버킷 정책 같은 리소스 기반 정책에 씁니다. 사용자·그룹·역할에 붙이는 자격 증명 기반 정책에는 붙은 대상이 곧 주체라 쓰지 않습니다.
Q: EC2의 앱이 DynamoDB에 써야 합니다. 가장 안전한 자격 증명 방법은?
A: DynamoDB에 필요한 권한만 가진 IAM 역할을 만들어 인스턴스 프로파일로 EC2에 붙입니다. 앱은 임시 자격 증명을 자동으로 받습니다.
Q: 6개월 동안 쓰지 않은 서비스 권한을 사용자에게서 걷어 내려 합니다. 어떤 IAM 도구를 보나요?
A: 마지막 액세스 정보(Access Advisor)입니다. 서비스별 마지막 사용 시각을 보여 줍니다.
Q: 공동 책임 모델에서 EC2 게스트 OS의 보안 패치는 누구 책임인가요?
A: 고객입니다. AWS는 하드웨어와 가상화 계층까지 책임집니다.
