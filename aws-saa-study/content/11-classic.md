@part ch11 | Classic Solutions Architecture Discussions: 설계 사례 | 강의 섹션 11 | 11. 설계 사례
지금까지 배운 EC2, ELB, ASG, RDS, ElastiCache, Route 53, EFS를 엮어 실제 웹 서비스를 단계별로 키워 봅니다. 시험 문제는 이런 "지금 구조의 문제 → 더 나은 구조"를 묻습니다. 각 단계에서 무엇이 문제였고 어떤 서비스가 그 문제를 풀었는지를 따라가세요.

@topic c11-stateless | WhatsTheTime.com: 무상태 웹 앱 키우기 | dom=2,4 | prio=3 | les=Solutions Architecture Discussions Overview; WhatsTheTime.com
**WhatsTheTime.com**은 지금 시각을 알려 주는 단순한 웹 앱입니다. DB가 필요 없고 서버가 아무것도 기억하지 않는 **무상태(stateless)** 앱이라, 확장 방법을 순수하게 보여 줍니다. 강의의 단계를 그대로 따라갑니다.

#### 단계별 진화

| 단계 | 구조 | 남은 문제 |
|---|---|---|
| 1 | EC2 한 대 + 탄력적 IP | 사용자가 늘면 한 대로 못 버팀 |
| 2 | 더 큰 인스턴스(수직 확장), 잠시 중단 | 확장할 때마다 중단, 한계 |
| 3 | EC2 여러 대 + 각자 탄력적 IP, 사용자가 IP 목록 관리 | IP가 늘면 사용자가 관리 못 함 |
| 4 | Route 53 A 레코드(TTL 1시간)에 EC2 IP 여러 개 | 인스턴스를 빼도 TTL 동안 옛 IP로 감 |
| 5 | **ELB + 상태 확인**, Route 53은 **Alias**로 ELB를 가리킴, EC2 보안 그룹은 ELB만 허용 | 인스턴스를 손으로 늘리고 줄임 |
| 6 | **ASG**로 자동 확장 | AZ 하나가 멈추면 전체 중단 |
| 7 | **다중 AZ** ELB와 ASG | 비용 최적화 여지 |
| 8 | 최소 용량만큼 **예약 인스턴스**, 넘는 부분은 온디맨드·스팟 | 완성 |

#### 이 사례에서 배운 것

- 공인 IP 대신 **DNS 이름과 ELB**를 앞에 둡니다. 서버가 바뀌어도 사용자는 모릅니다.
- **상태 확인**이 있어야 고장 난 서버로 트래픽이 가지 않습니다.
- **Alias 레코드**로 루트 도메인을 ELB에 잇습니다.
- **보안 그룹을 사슬로**: EC2는 ELB 보안 그룹만 허용합니다.
- **ASG + 다중 AZ**로 가용성과 탄력성을 함께 얻습니다.
- 늘 필요한 최소 용량은 **예약(또는 Savings Plans)**으로, 변동분은 온디맨드·스팟으로 사서 비용을 줄입니다.

설계를 평가하는 다섯 기준(비용, 성능, 안정성, 보안, 운영 우수성)은 Well-Architected 프레임워크의 기둥과 같습니다([31.1](#c31-wa)).

> **시험 포인트** 문제는 보통 이 표의 한 단계를 "현재 구조"로 주고 다음 단계를 묻습니다. "Route 53이 EC2 IP 여러 개를 가리키는데 인스턴스 장애 때 일부 사용자가 오류를 본다" → ELB + 상태 확인 + Alias. "트래픽에 따라 대수를 자동 조절" → ASG. "AZ 장애에도" → 다중 AZ.

**시각 알려 주는 가게**를 키워 가는 이야기예요. 손님 정보를 기억할 필요가 없는 아주 단순한 가게예요.

1. 작업실 하나에 내 이름 주소판을 달았어요. 손님이 많아지자 작업실 하나로는 부족해요.
2. 더 큰 작업실로 옮겼어요. 옮기는 동안 가게 문을 닫아야 했어요.
3. 작업실을 여러 개 빌리고 주소판도 여러 개 달았어요. 손님이 주소를 다 외우기 힘들어요.
4. 주소 안내소에 주소 여러 개를 적었어요. 작업실 하나를 닫아도 손님은 한동안 그 주소로 와요.
5. **안내 데스크**를 두고, 데스크가 "괜찮아요?"를 확인해 문 연 작업실로만 보내요. 안내소는 데스크를 바로 가리켜요.
6. **직원 수 조절 매니저**가 손님 수에 맞춰 작업실을 늘리고 줄여요.
7. 두 동네에 나눠서 정전에도 버텨요.
8. 늘 필요한 작업실은 1년 약속으로 싸게, 바쁠 때만 그날 빌려요.

| 가게 키우기 | AWS |
|---|---|
| 주소판 여러 개 | 탄력적 IP 여러 개 |
| 안내소에 주소 여러 개 | Route 53 A 레코드 다중 값 |
| 안내 데스크 + 확인 | ELB + 상태 확인 |
| 매니저 | ASG |
| 두 동네 | 다중 AZ |
| 1년 약속 | 예약 인스턴스 |

대부분의 앱은 장바구니, 로그인 세션, 업로드 파일 같은 **상태(state)**를 가집니다. 서버가 여러 대가 되면 이 상태를 어디에 둘지부터 정해야 합니다.

#### MyClothes.com: 장바구니와 사용자 정보

쇼핑몰 MyClothes.com은 수백 명이 동시에 장바구니를 쓰고, 사용자 정보(주소 등)를 DB에 저장합니다. ELB + 다중 AZ ASG까지 만든 뒤에 생기는 문제와 해결은 이렇습니다.

| 문제 | 해결 | 특징 |
|---|---|---|
| 다른 서버로 가면 장바구니가 사라짐 | ELB **고정 세션** | 간단하지만 서버가 죽으면 그 세션도 잃음, 부하 쏠림 |
| 서버가 상태를 갖지 않게 하고 싶음 | 장바구니를 **웹 쿠키**에 담음 | 서버는 무상태. 대신 요청이 커지고 쿠키 위조 위험, 4KB 한도 |
| 쿠키는 위험하고 작음 | 쿠키에는 **세션 ID만**, 세션 데이터는 **ElastiCache**(또는 DynamoDB)에 | 서버 무상태, 안전, 빠름 |
| 사용자 정보를 영구 저장 | **RDS**에 저장 | |
| 읽기가 많아 RDS가 느림 | **읽기 전용 복제본**(최대 15개) 또는 **ElastiCache 지연 로딩** | 캐시는 앱 코드 변경 필요 |
| AZ 장애 대비 | ELB·ASG 다중 AZ, **RDS 다중 AZ**, **ElastiCache 다중 AZ** | |
| 보안 | ELB는 인터넷의 HTTP·HTTPS, EC2는 ELB 보안 그룹만, RDS·ElastiCache는 EC2 보안 그룹만 | 보안 그룹 사슬 |

#### MyWordPress.com: 업로드 파일 공유

WordPress 블로그는 글은 DB에, **사진 같은 업로드 파일은 서버 디스크**에 저장합니다.

| 단계 | 구조 | 문제·해결 |
|---|---|---|
| 1 | 글은 RDS(또는 Aurora MySQL 다중 AZ + 읽기 복제본) | 확장되는 DB |
| 2 | 사진을 EC2 한 대의 **EBS**에 저장 | 서버가 하나면 문제없음 |
| 3 | EC2를 여러 대로 늘림 | 사진이 올라간 서버가 아닌 다른 서버로 요청이 가면 **사진이 안 보임**(EBS는 인스턴스 하나에만 붙음) |
| 4 | 사진을 **EFS**에 저장하고 모든 EC2가 마운트 | 어느 서버로 가도 같은 사진. 여러 AZ에서 공유 |

> **시험 포인트** "세션을 잃지 않으면서 서버를 무상태로" → 세션을 ElastiCache나 DynamoDB에. "여러 EC2가 같은 업로드 파일을 공유" → EFS(리눅스), 또는 앱을 고쳐 S3에 저장. "로그인한 사용자가 서버가 바뀌면 다시 로그인해야 한다" → 외부 세션 저장소(근본 해결) 또는 고정 세션(임시).

@analogy
**옷 가게(MyClothes)**에는 손님마다 장바구니가 있어요.

- 손님이 다른 작업실로 가면 장바구니가 사라졌어요.
- 처음엔 **단골 도장**을 찍어 늘 같은 작업실로 보냈어요. 그 작업실이 문을 닫으면 장바구니도 사라져요.
- 다음엔 장바구니를 **손님 손에 들려** 보냈어요(쿠키). 무겁고, 손님이 몰래 가격표를 바꿀 수도 있어요.
- 결국 **공용 메모판(ElastiCache)**에 장바구니를 적고, 손님에게는 **번호표(세션 ID)**만 줬어요. 어느 작업실에 가도 번호표로 메모판을 찾아봐요.
- 손님 주소 같은 중요한 건 **기록실(RDS)**에 적고, 보러 오는 손님이 많으면 **열람용 복사본**을 둬요.

**블로그 가게(MyWordPress)**는 사진을 받아요. 처음엔 작업실 **개인 사물함(EBS)**에 넣었는데, 작업실이 여러 개가 되자 다른 작업실에서는 그 사진을 못 찾았어요. 그래서 모든 작업실이 함께 쓰는 **공용 서류실(EFS)**에 넣었어요.

| 가게 | AWS |
|---|---|
| 단골 도장 | 고정 세션 |
| 손에 들려 보낸 장바구니 | 쿠키 |
| 공용 메모판 + 번호표 | ElastiCache + 세션 ID |
| 사진 넣는 공용 서류실 | EFS |

#### 애플리케이션을 빨리 띄우는 방법

전체 스택(EC2, EBS, RDS)을 처음부터 설치하면 시간이 오래 걸립니다. 확장할 때마다 몇 분씩 기다리지 않으려면 미리 준비해 둡니다.

| 대상 | 방법 |
|---|---|
| EC2 | **골든 AMI**: 앱과 의존성을 미리 설치한 AMI로 띄움. 부팅 후 바로 서비스 |
| EC2 | **사용자 데이터**: 그때그때 달라지는 설정(환경 변수 등)만 부팅 때 적용 |
| EC2 | **하이브리드**: 공통 부분은 골든 AMI, 바뀌는 부분만 사용자 데이터(Elastic Beanstalk 방식) |
| RDS | **스냅샷에서 복원**: 스키마와 데이터가 이미 들어 있음 |
| EBS | **스냅샷에서 복원**: 이미 포맷되고 데이터가 들어 있음 |

#### Elastic Beanstalk

지금까지 사례마다 ELB, ASG, EC2, RDS, 보안 그룹을 손으로 엮었습니다. **Elastic Beanstalk**은 **코드만 올리면** 이 구조를 대신 만들어 주는 개발자용 서비스(PaaS)입니다. 서비스 자체는 무료이고 만들어진 자원 값만 냅니다.

- **구성 요소**: 애플리케이션(묶음), 애플리케이션 버전(올린 코드), 환경(실행 중인 자원 묶음, dev·prod처럼 여러 개).
- **플랫폼**: Java, .NET, PHP, Node.js, Python, Ruby, Go, Docker 등.
- **용량 프로비저닝, 로드 밸런싱, 자동 확장, 상태 모니터링, 인스턴스 설정**을 Beanstalk이 맡고, 개발자는 코드에 집중합니다. 만들어진 자원은 직접 들여다보고 설정을 바꿀 수 있습니다.

| 환경 계층 | 구성 | 쓰임 |
|---|---|---|
| 웹 서버 환경 | ELB + ASG + EC2 | 웹 요청 처리 |
| 작업자(worker) 환경 | SQS 대기열 + ASG + EC2 | 오래 걸리는 백그라운드 작업. 대기열 길이로 확장 |

| 배포 모드 | 구성 |
|---|---|
| 단일 인스턴스 | EC2 한 대 + 탄력적 IP. 개발용 |
| 고가용성 | ALB + 다중 AZ ASG(+ RDS 다중 AZ). 운영용 |

> **시험 포인트** "개발자가 인프라를 관리하지 않고 웹 앱을 빠르게 배포, 운영 오버헤드 최소" → Elastic Beanstalk. "웹 요청과 오래 걸리는 작업을 분리" → 웹 서버 환경 + 작업자 환경(SQS). "새 인스턴스가 시작되자마자 서비스" → 골든 AMI.

@analogy
**빨리 문 여는 법**: 새 작업실을 열 때마다 책상을 조립하면 오래 걸려요. 그래서 **책상까지 다 놓인 설계도(골든 AMI)**를 미리 만들어 두고, 그날그날 바뀌는 것(오늘의 메뉴)만 첫날 쪽지(사용자 데이터)에 적어요. 기록실도 사진(스냅샷)에서 바로 채워요.

**Elastic Beanstalk**은 **인테리어 업체 패키지**예요. 사장님은 "우리 가게 레시피(코드)"만 건네면, 업체가 작업실, 안내 데스크, 직원 수 조절 매니저까지 알아서 꾸며 줘요. 패키지 값은 따로 없고 빌린 시설 값만 내요.

- **손님 받는 가게(웹 서버 환경)**: 안내 데스크와 작업실이 있어요.
- **뒷방 작업장(작업자 환경)**: 주문서 꽂이(SQS)에 쌓인 오래 걸리는 일을 처리해요. 꽂이가 가득 차면 작업자를 늘려요.

| 가게 | AWS |
|---|---|
| 책상까지 놓인 설계도 | 골든 AMI |
| 오늘의 메뉴 쪽지 | 사용자 데이터 |
| 인테리어 업체 패키지 | Elastic Beanstalk |
| 손님 받는 가게 / 뒷방 작업장 | 웹 서버 환경 / 작업자 환경 |

@quiz
Q: Route 53 A 레코드에 EC2 IP 여러 개를 적었는데, 한 인스턴스를 종료한 뒤에도 일부 사용자가 오류를 봅니다. 왜 그렇고 어떻게 고치나요?
A: 클라이언트가 TTL 동안 옛 IP를 캐시하기 때문입니다. 상태 확인이 있는 ELB를 앞에 두고 Route 53 Alias로 ELB를 가리킵니다.
Q: 장바구니를 잃지 않으면서 웹 서버를 무상태로 만들려면?
A: 쿠키에는 세션 ID만 두고, 세션 데이터는 ElastiCache나 DynamoDB에 저장합니다.
Q: WordPress를 EC2 여러 대로 늘렸더니 일부 요청에서 업로드한 사진이 보이지 않습니다. 해결책은?
A: 업로드 파일을 EFS에 저장하고 모든 EC2가 마운트하게 합니다(또는 S3에 저장하도록 앱을 바꿉니다).
Q: 새 인스턴스가 시작 즉시 서비스할 수 있게 하려면?
A: 앱을 미리 설치한 골든 AMI로 시작하고, 바뀌는 설정만 사용자 데이터로 적용합니다.
Q: 개발자가 인프라 관리 없이 Python 웹 앱을 배포하고, 오래 걸리는 작업은 따로 처리하려 합니다. 어떤 구성인가요?
A: Elastic Beanstalk 웹 서버 환경과, SQS를 쓰는 작업자 환경입니다.
