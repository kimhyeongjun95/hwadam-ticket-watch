@part ch10 | Route 53: DNS와 라우팅 정책 | 강의 섹션 10 | 10. Route 53
도메인 이름을 IP로 바꾸는 DNS의 원리와, AWS의 DNS 서비스 Route 53을 배웁니다. 레코드 종류(CNAME과 Alias), TTL, 여덟 가지 라우팅 정책과 상태 확인으로 다중 리전 장애 조치를 설계하는 문제가 자주 나옵니다.

@topic c10-dns | DNS 기초 | dom=3 | prio=2 | les=What is a DNS ?
**DNS(Domain Name System)**는 `www.example.com` 같은 사람이 읽는 이름을 `93.184.216.34` 같은 IP 주소로 바꿔 주는 인터넷의 전화번호부입니다.

#### 용어

| 용어 | 뜻 |
|---|---|
| 도메인 등록 기관(registrar) | 도메인 이름을 사고 갱신하는 곳(Route 53, GoDaddy 등) |
| DNS 레코드 | 이름과 값의 짝(A, AAAA, CNAME, NS 등) |
| 영역 파일(zone file) | 한 도메인의 레코드 모음 |
| 네임 서버 | DNS 질문에 답하는 서버. 권한 있는(authoritative) 서버가 최종 답을 줌 |
| TLD | 최상위 도메인(`.com`, `.kr`, `.org`) |
| SLD | 2단계 도메인(`example.com`의 `example`) |
| FQDN | 끝까지 다 쓴 이름(`api.www.example.com.`) |

#### 이름 하나를 찾는 순서

1. 브라우저가 컴퓨터에 설정된 **로컬 DNS 서버**(회사·통신사가 운영)에 `www.example.com`을 묻습니다.
2. 로컬 DNS 서버는 모르면 **루트 DNS 서버**에 묻고, "`.com`은 이 서버에 물어보라"는 답을 받습니다.
3. **`.com` TLD 서버**에 묻고, "`example.com`은 이 네임 서버들(예: Route 53)이 관리한다"는 답을 받습니다.
4. **권한 있는 네임 서버**(Route 53 호스팅 영역)에 묻고, 최종 IP를 받습니다.
5. 로컬 DNS 서버는 답을 **TTL 동안 캐시**하고 브라우저에 돌려줍니다.

> **시험 포인트** DNS 답은 곳곳에 캐시되므로 레코드를 바꿔도 **TTL이 지나야** 모든 사용자에게 반영됩니다. 이전 계획이 있으면 미리 TTL을 짧게 줄여 둡니다([10.2](#c10-r53)).

@practice
- **도메인 이전과 서버 교체**: 서비스를 새 서버나 새 클라우드로 옮길 때, 며칠 전에 TTL을 300초 이하로 줄여 두고 당일 레코드를 바꿉니다. TTL을 줄이지 않으면 일부 사용자가 하루 가까이 옛 서버로 접속합니다.
- **장애 원인 찾기**: "어떤 사용자는 접속되고 어떤 사용자는 안 된다"는 문의는 DNS 캐시가 서로 다른 값을 들고 있는 경우가 많습니다. `dig`나 `nslookup`으로 각 단계의 답을 확인합니다.
- **사내 도메인**: 회사 내부 시스템(`erp.corp.company`)은 공개 DNS가 아니라 사내 DNS에서만 풀리게 해 외부에 노출하지 않습니다.

@easy
DNS는 이름을 주소로 바꿔 주는 안내 체계입니다. 사람에게는 `www.example.com`이 기억하기 쉽지만, 컴퓨터는 IP 주소로만 연결합니다. 그래서 이름을 받으면 단계별로 물어 주소를 찾습니다. 루트 서버는 "`.com`은 저쪽에 물어보세요", `.com` 서버는 "`example.com`은 이 네임 서버가 관리합니다"라고 안내하고, 마지막 네임 서버가 실제 주소를 알려 줍니다.

찾은 답은 TTL 동안 여기저기에 저장해 두고 다시 묻지 않습니다. 그래서 주소를 바꿔도 저장해 둔 기간이 끝날 때까지 옛 주소로 가는 사람이 남습니다.

@topic c10-r53 | Route 53: 호스팅 영역, 레코드, TTL, CNAME과 Alias | dom=2,3 | prio=3 | les=Route 53 Overview; Route 53 - Registering a domain; Route 53 - Creating our first records; Route 53 - EC2 Setup; Route 53 - TTL; Route 53 CNAME vs Alias
**Route 53**은 AWS의 **권한 있는 DNS 서비스**이자 **도메인 등록 기관**이고, 대상이 살아 있는지 보는 **상태 확인** 기능도 갖췄습니다. AWS 서비스 중 유일하게 **100% 가용성 SLA**를 약속합니다(53은 DNS 포트 번호).

#### 레코드

레코드는 `이름 · 유형 · 값 · 라우팅 정책 · TTL`로 이루어집니다.

| 유형 | 값 |
|---|---|
| A | 이름 → IPv4 주소 |
| AAAA | 이름 → IPv6 주소 |
| CNAME | 이름 → 다른 이름. **루트 도메인(`example.com`)에는 못 씀** |
| NS | 이 호스팅 영역을 관리하는 네임 서버 |
| 그 밖 | MX(메일), TXT(검증), CAA, SRV, PTR 등 |

#### 호스팅 영역

한 도메인의 레코드를 담는 그릇이고, 하나에 월 0.50 USD입니다.

- **퍼블릭 호스팅 영역**: 인터넷에서 질문에 답합니다(`app.example.com`).
- **프라이빗 호스팅 영역**: 연결한 VPC 안에서만 답합니다(`db.internal.company`).

#### TTL

DNS 답을 클라이언트가 얼마 동안 캐시할지 정합니다.

| TTL | 장점 | 단점 |
|---|---|---|
| 길게(예: 24시간) | Route 53 질문 수(요금) 감소 | 레코드를 바꿔도 오래 옛 값이 남음 |
| 짧게(예: 60초) | 바꾼 값이 빨리 퍼짐 | 질문이 많아 요금 증가 |

Alias 레코드를 뺀 모든 레코드는 TTL이 필수입니다.

#### CNAME과 Alias

AWS 리소스(ALB, CloudFront 등)는 IP가 바뀌므로 IP 대신 **이름**을 가리켜야 합니다. 방법이 둘입니다.

| 비교 | CNAME | Alias |
|---|---|---|
| 가리키는 것 | 아무 호스트 이름 | **AWS 리소스**(ELB, CloudFront, API Gateway, Elastic Beanstalk, S3 웹사이트, VPC 인터페이스 엔드포인트, Global Accelerator, 같은 호스팅 영역의 레코드) |
| 루트 도메인 | **안 됨** | **됨** (`example.com` → ALB) |
| 요금 | 질문마다 요금 | **Alias 질문은 무료** |
| TTL | 직접 정함 | 정할 수 없음(Route 53이 정함) |
| 상태 확인 | 따로 | 대상의 상태를 따라감 |
| 유형 | CNAME | A 또는 AAAA로 만듦 |

**Alias는 EC2의 DNS 이름을 가리킬 수 없습니다.** EC2는 A 레코드에 IP(또는 탄력적 IP)를 적습니다.

#### 도메인 등록

Route 53에서 도메인을 사면 호스팅 영역이 자동으로 만들어지고 NS 레코드가 연결됩니다. 다른 등록 기관(예: 가비아)에서 산 도메인을 Route 53으로 관리하려면, Route 53에 퍼블릭 호스팅 영역을 만들고 **등록 기관에서 네임 서버(NS)를 Route 53의 네임 서버 4개로 바꿉니다**([10.6](#c10-resolver)).

> **시험 포인트** "`example.com`(루트 도메인)을 ALB로 연결" → Alias 레코드(CNAME은 루트에 불가). "Route 53 질문 요금을 줄이면서 CloudFront를 가리킴" → Alias(무료). "DNS 변경이 사용자에게 늦게 반영" → TTL 때문. 서버 교체 계획이 있으면 미리 TTL을 낮춥니다.

@practice
- **회사 도메인 관리**: 대부분의 AWS 사용 회사는 Route 53에 퍼블릭 호스팅 영역을 두고 `www`, `api`, `admin` 레코드를 관리합니다. 도메인 자체는 국내 등록 기관에서 사고 네임 서버만 Route 53으로 돌리는 경우가 많습니다.
- **Alias로 루트 도메인 연결**: `example.com`(루트)과 `www.example.com`을 모두 CloudFront나 ALB에 연결할 때 Alias를 씁니다. 다른 DNS 서비스에서는 루트 도메인을 로드 밸런서에 연결하기가 까다로워, 이 때문에 Route 53으로 옮기는 회사도 있습니다.
- **프라이빗 호스팅 영역**: VPC 안에서만 쓰는 `db.internal`, `redis.internal` 같은 이름을 만들어, DB 엔드포인트가 바뀌어도 앱 설정은 그대로 두고 레코드만 바꿉니다.
- **인증서 발급 검증**: ACM에서 인증서를 발급할 때 Route 53에 검증용 CNAME 레코드를 자동으로 추가합니다.

@easy
Route 53은 회사의 대표 주소록을 관리하는 서비스입니다. "`www`는 이 서버, `api`는 저 로드 밸런서"처럼 이름과 주소를 적어 두고, 누가 물으면 답합니다.

CNAME은 "이 이름은 저 이름과 같다"는 별칭이고, Alias는 Route 53이 AWS 자원의 실제 주소를 직접 찾아 답해 주는 별칭입니다. 루트 도메인(`example.com`)에는 DNS 규칙상 CNAME을 쓸 수 없어서, 로드 밸런서나 CloudFront를 연결할 때는 Alias를 씁니다. Alias 조회는 요금도 없습니다.

@topic c10-routing | 라우팅 정책 1: 단순, 가중치, 지연 시간 | dom=2,3 | prio=3 | les=Routing Policy - Simple; Routing Policy - Weighted; Routing Policy - Latency
**라우팅 정책**은 같은 이름에 대한 DNS 질문에 **어떤 답을 돌려줄지** 정합니다. 로드 밸런서처럼 트래픽을 직접 나르는 것이 아니라, **답만** 골라 줍니다.

#### 단순(Simple)

레코드 하나에 값을 하나 또는 여러 개 적습니다. 값이 여러 개면 모두 돌려주고 **클라이언트가 그중 하나를 무작위로** 고릅니다. 상태 확인을 붙일 수 없습니다.

#### 가중치(Weighted)

같은 이름의 레코드 여러 개에 **가중치**를 주고, 가중치 비율대로 답을 나눕니다.

- 레코드별 트래픽 비율 = 그 레코드 가중치 ÷ 전체 가중치 합. 예: 70, 20, 10이면 70%, 20%, 10%.
- 가중치 합이 100일 필요는 없습니다.
- 가중치 0이면 그 레코드로 보내지 않습니다. 모두 0이면 똑같이 나눕니다.
- 상태 확인을 붙여 unhealthy한 레코드를 뺄 수 있습니다.
- 새 버전에 10%만 보내는 **카나리 배포**, 리전 간 비율 조정에 씁니다.

#### 지연 시간(Latency-based)

사용자와 **가장 지연 시간이 짧은 AWS 리전**의 레코드로 답합니다. 거리가 아니라 측정된 네트워크 지연이 기준입니다(독일 사용자가 미국 리전으로 갈 수도 있음). 상태 확인을 붙여 장애 리전을 뺍니다.

> **시험 포인트** "새 버전에 트래픽 10%만 보내 테스트" → 가중치. "전 세계 사용자를 가장 빠른 리전으로" → 지연 시간 기반. DNS 라우팅 정책은 캐시 때문에 즉시 반영되지 않으므로, 초 단위로 빠른 전환이 필요하면 Global Accelerator를 함께 봅니다([15.3](#c15-ga)).

@practice
- **가중치로 카나리 배포**: 새 버전 서버 묶음을 따로 띄우고 가중치를 5 → 25 → 100으로 올리며 조금씩 옮깁니다. 문제가 생기면 가중치를 0으로 돌립니다.
- **가중치로 이전**: 온프레미스에서 AWS로 옮길 때 처음에는 10%만 AWS로 보내 확인한 뒤 점점 늘립니다.
- **지연 시간 기반**: 서울·미국·유럽 리전에 같은 서비스를 둔 글로벌 서비스는 사용자를 가장 응답이 빠른 리전으로 보냅니다.
- **주의할 점**: DNS 답은 캐시되므로 비율이 정확히 지켜지지 않고 바꾼 설정도 바로 반영되지 않습니다. 정밀한 비율이 필요하면 ALB 가중치 대상 그룹을 씁니다.

@easy
라우팅 정책은 같은 이름을 물었을 때 어떤 주소를 알려 줄지 고르는 규칙입니다. Route 53은 손님을 직접 데려가지 않고 "이쪽으로 가세요"라고 주소만 알려 줍니다.

- **단순**: 아는 주소를 모두 알려 주고 손님이 고르게 합니다.
- **가중치**: 열 명 중 일곱 명에게는 1호점, 세 명에게는 2호점 주소를 알려 줍니다.
- **지연 시간**: 그 손님에게서 가장 빨리 닿는 지점의 주소를 알려 줍니다.

@topic c10-health-failover | 상태 확인과 장애 조치 라우팅 | dom=2 | prio=3 | les=Route 53 - Health Checks; Route 53 - Health Checks Hands On; Routing Policy - Failover
Route 53 **상태 확인**은 엔드포인트가 살아 있는지 주기적으로 검사하고, 그 결과로 DNS 답에서 unhealthy한 레코드를 뺍니다. 이것으로 **DNS 수준의 장애 조치**를 만듭니다.

#### 상태 확인 세 가지

| 종류 | 무엇을 보나 |
|---|---|
| 엔드포인트 확인 | 앱·서버·AWS 리소스에 직접 HTTP·HTTPS·TCP 요청 |
| 계산된(calculated) 확인 | 다른 상태 확인 여러 개(최대 256개)를 AND·OR·임계값으로 묶음 |
| CloudWatch 경보 확인 | CloudWatch 경보 상태를 따라감. **프라이빗 리소스**를 확인할 때 |

#### 엔드포인트 확인의 동작

- 전 세계 **약 15곳의 상태 확인기**가 요청을 보냅니다. 간격은 30초(빠른 확인은 10초)입니다.
- 연속 실패 횟수(기본 3번)를 넘으면 unhealthy로 봅니다.
- 상태 확인기의 **18%를 넘게** healthy라고 보고하면 healthy로 판정합니다.
- 2xx·3xx 응답이면 통과입니다. 응답 본문 처음 5,120바이트에서 특정 문자열을 찾게 할 수도 있습니다.
- 대상의 보안 그룹·방화벽이 **Route 53 상태 확인기 IP 대역**을 허용해야 합니다.

상태 확인기는 VPC 밖(인터넷)에 있으므로 **프라이빗 서브넷의 리소스에는 직접 닿지 못합니다.** 이때는 CloudWatch 지표 → CloudWatch 경보 → 경보를 보는 상태 확인으로 만듭니다.

#### 장애 조치 라우팅(Failover, 액티브-패시브)

1. **기본(primary)** 레코드에 상태 확인을 붙이고, **보조(secondary)** 레코드를 하나 둡니다.
2. 기본이 healthy이면 항상 기본으로 답합니다.
3. 기본이 unhealthy가 되면 보조로 답합니다. 보조에도 상태 확인을 붙일 수 있습니다.

보조로 다른 리전의 서비스, 또는 S3 정적 웹사이트의 "점검 중" 페이지를 둡니다.

> **시험 포인트** "리전 A 장애 시 리전 B로 자동 전환(액티브-패시브)" → 장애 조치 라우팅 + 기본 레코드 상태 확인. "프라이빗 서브넷의 서버 상태를 Route 53이 확인" → CloudWatch 경보 기반 상태 확인. "여러 하위 서비스가 모두 살아 있을 때만 healthy" → 계산된 상태 확인.

@practice
- **리전 장애 대비**: 서울 리전 ALB를 기본, 도쿄 리전 ALB를 보조로 두고 기본에 상태 확인을 붙입니다. 서울이 응답하지 않으면 DNS 답이 도쿄로 바뀝니다.
- **점검 페이지**: 보조 레코드로 S3 정적 웹사이트의 "점검 중" 페이지를 두면, 서비스 전체가 멈췄을 때 사용자가 빈 화면 대신 안내를 봅니다.
- **상태 확인 경로**: `/health`가 DB와 핵심 외부 API까지 확인하도록 만들어, 앱은 떠 있지만 실제로는 동작하지 않는 상황도 잡아냅니다.
- **프라이빗 리소스 감시**: 내부 API 서버처럼 인터넷에서 닿지 않는 대상은 CloudWatch 경보를 만들고, 그 경보를 Route 53 상태 확인이 보게 합니다.

@easy
상태 확인은 전 세계 여러 곳에서 주기적으로 우리 서비스에 "응답하세요"라고 묻는 것입니다. 일정 횟수 넘게 대답이 없으면 그 주소를 안내 목록에서 뺍니다.

장애 조치 라우팅은 비상 연락망과 같습니다. 평소에는 본사 번호를 알려 주다가, 본사가 전화를 받지 않으면 비상 사무실 번호를 알려 줍니다. 비상 사무실은 평소에 쉬고 있어서 액티브-패시브라고 부릅니다.

나머지 네 가지 정책은 **사용자가 어디에 있는지**나 **여러 답을 함께 주는 것**에 관한 것입니다.

#### 지리적 위치(Geolocation)

사용자의 **실제 위치**(대륙, 국가, 미국 주)에 따라 답합니다. 지연 시간과 관계없이 위치가 기준입니다.

- 가장 구체적인 위치가 먼저 맞춰집니다(주 → 국가 → 대륙).
- 어디에도 맞지 않는 사용자를 위해 **기본(Default) 레코드**를 꼭 둡니다.
- 쓰임: 국가별 언어로 된 사이트, **콘텐츠 배포 제한**(저작권 지역 제한), 지역별 부하 분산.
- 상태 확인을 붙일 수 있습니다.

#### 지리 근접(Geoproximity)

사용자와 리소스의 **지리적 거리**로 보내되, **편향값(bias)**으로 리소스의 담당 범위를 넓히거나 줄입니다.

- 편향을 1~99로 올리면 그 리소스로 오는 트래픽이 늘고, -1~-99로 내리면 줄어듭니다.
- AWS 리소스는 리전으로, AWS 밖 리소스는 위도·경도로 위치를 정합니다.
- **Route 53 트래픽 플로(Traffic Flow)** 기능으로 설정합니다.
- 쓰임: 한 리전의 용량이 커서 더 넓은 지역의 사용자를 그쪽으로 옮길 때.

#### IP 기반(IP-based)

사용자의 **출발지 IP 대역(CIDR)**에 따라 답합니다. CIDR 컬렉션을 만들어 대역별로 어느 엔드포인트로 보낼지 정합니다. 쓰임: 특정 통신사(ISP) 사용자를 특정 엔드포인트로 보내 네트워크 비용·성능을 최적화할 때.

#### 다중 값(Multi-Value)

여러 리소스의 값을 **최대 8개까지, healthy한 것만** 돌려줍니다. 클라이언트가 그중 하나를 고릅니다. 상태 확인을 붙일 수 있다는 점이 단순 정책과 다르지만, **로드 밸런서를 대신하지는 못합니다**(클라이언트 측 분산일 뿐).

#### 여덟 가지 정리

| 정책 | 기준 | 상태 확인 |
|---|---|---|
| 단순 | 그냥 모두 | 없음 |
| 가중치 | 비율 | 있음 |
| 지연 시간 | 가장 빠른 리전 | 있음 |
| 장애 조치 | 기본 → 보조 | 기본 필수 |
| 지리적 위치 | 사용자 위치(국가 등) | 있음 |
| 지리 근접 | 거리 + 편향 | 있음 |
| IP 기반 | 출발지 CIDR | 있음 |
| 다중 값 | healthy 최대 8개 | 있음 |

> **시험 포인트** "프랑스 사용자에게는 프랑스어 사이트, 법적으로 특정 국가에서만 서비스" → 지리적 위치. "서울 리전 용량을 늘려 더 많은 아시아 사용자를 받게" → 지리 근접 + 편향. "DNS 답에서 고장 난 서버를 빼고 여러 IP를 돌려줌, 로드 밸런서 없이" → 다중 값. "사용자에게 가장 빠른 리전"은 지리 정책이 아니라 지연 시간 기반입니다.

@practice
- **지리적 위치, 국가별 사이트**: 한국 사용자는 한국어 사이트, 일본 사용자는 일본어 사이트로 보내고, 그 밖의 나라는 영어 기본 사이트로 보냅니다.
- **지리적 위치, 서비스 지역 제한**: 라이선스 계약상 국내에서만 볼 수 있는 콘텐츠는 국내 사용자에게만 서비스 주소를 주고 나머지는 안내 페이지로 보냅니다(더 정확한 차단은 CloudFront 지리적 제한과 함께).
- **지리 근접**: 서울 리전 용량을 늘린 뒤 편향값을 올려, 원래 싱가포르로 가던 동남아 일부 사용자까지 서울로 받습니다.
- **IP 기반**: 특정 통신사 사용자를 그 통신사와 직접 연결된 엔드포인트로 보내 전송 비용과 지연을 줄입니다.
- **다중 값**: 로드 밸런서 없이 서버 몇 대를 운영하는 작은 서비스에서, 살아 있는 서버 주소만 여러 개 돌려줍니다.

@easy
네 정책은 "어디서 왔는지"를 다르게 봅니다.

- **지리적 위치**는 손님의 국적이나 주소를 보고 정해진 지점으로 보냅니다. 거리와 상관없이 "한국 손님은 서울 지점"입니다.
- **지리 근접**은 가까운 지점으로 보내되, 큰 지점은 담당 구역을 넓혀 더 먼 손님까지 받습니다.
- **IP 기반**은 손님이 어느 통신사 회선으로 왔는지를 봅니다.
- **다중 값**은 영업 중인 지점 주소 여러 개를 한꺼번에 알려 주고 손님이 고르게 합니다.

#### 다른 등록 기관에서 산 도메인

**도메인 등록 기관**(이름을 사는 곳)과 **DNS 서비스**(레코드를 관리하는 곳)는 달라도 됩니다. 가비아에서 산 도메인을 Route 53으로 관리하려면 다음 순서로 합니다.

1. Route 53에 그 도메인의 **퍼블릭 호스팅 영역**을 만듭니다.
2. 호스팅 영역의 **NS 레코드에 적힌 네임 서버 4개**를 확인합니다.
3. 가비아(등록 기관) 관리 화면에서 네임 서버를 그 4개로 바꿉니다.

#### Route 53 Resolver와 하이브리드 DNS

VPC 안의 인스턴스는 기본으로 **Route 53 Resolver**(VPC CIDR의 +2 주소, 예: `10.0.0.2`)에 DNS를 묻습니다. Resolver는 프라이빗 호스팅 영역, VPC 내부 이름, 퍼블릭 DNS에 답합니다. 회사 데이터 센터와 VPC가 VPN·Direct Connect로 이어져 있을 때, 서로의 **사설 도메인 이름**을 풀려면 Resolver 엔드포인트가 필요합니다.

| 엔드포인트 | 방향 | 예 |
|---|---|---|
| **인바운드** 엔드포인트 | 회사 → AWS | 회사 DNS 서버가 `app.aws.company`(프라이빗 호스팅 영역)를 AWS에 물음 |
| **아웃바운드** 엔드포인트 | AWS → 회사 | VPC의 앱이 `ad.corp.company`(회사 DNS)를 물으면, **Resolver 규칙**(전달 규칙)에 따라 회사 DNS 서버로 넘김 |

엔드포인트는 VPC 안에 ENI로 만들어지고(AZ 여러 개 권장), Resolver 규칙은 RAM으로 다른 계정과 공유할 수 있습니다.

> **시험 포인트** "온프레미스 서버가 AWS 프라이빗 호스팅 영역의 이름을 풀어야 한다" → 인바운드 엔드포인트. "EC2가 회사 데이터 센터의 내부 도메인을 풀어야 한다" → 아웃바운드 엔드포인트 + 전달 규칙. 방향을 헷갈리지 않게 **질문이 들어오는 쪽이 인바운드**라고 기억합니다.

@practice
- **도메인은 다른 곳, DNS는 Route 53**: 국내 등록 기관에서 산 도메인의 네임 서버를 Route 53으로 바꾸는 것이 가장 흔한 구성입니다. 도메인 갱신 결제는 원래 등록 기관에서 합니다.
- **하이브리드 DNS**: 사내 데이터 센터와 AWS를 VPN·Direct Connect로 연결한 회사는 두 방향 모두 이름을 풀어야 합니다. AWS의 앱이 사내 Active Directory 도메인을 찾을 때는 아웃바운드 엔드포인트와 전달 규칙을, 사내 서버가 AWS의 내부 이름을 찾을 때는 인바운드 엔드포인트를 씁니다.
- **여러 계정 공유**: 계정이 여러 개인 회사는 네트워크 계정에 Resolver 규칙을 만들고 RAM으로 다른 계정의 VPC와 공유합니다.

@easy
등록 기관과 DNS 서비스는 도메인을 산 곳과 주소록을 관리하는 곳의 차이입니다. 휴대폰 번호를 산 통신사와 그 번호를 저장한 연락처 앱이 다를 수 있는 것과 같습니다. 등록 기관에 "주소록은 Route 53이 관리한다"고 알려 주면(네임 서버 변경) 됩니다.

Resolver 엔드포인트는 회사 전화망과 AWS 전화망 사이에 둔 연결 교환원입니다. 회사에서 AWS 쪽 내선 번호를 물으면 인바운드 교환원이 답하고, AWS에서 회사 내선을 물으면 아웃바운드 교환원이 회사 쪽에 대신 물어봐 줍니다.

@quiz
Q: `example.com`(루트 도메인)을 ALB로 연결하려면 어떤 레코드를 쓰나요?
A: Alias 레코드(A 유형)입니다. CNAME은 루트 도메인에 쓸 수 없습니다.
Q: Alias 레코드로 가리킬 수 없는 것은? ALB, CloudFront, EC2 DNS 이름, S3 웹사이트
A: EC2 DNS 이름입니다. EC2는 A 레코드에 IP를 적습니다.
Q: DNS 레코드를 바꿨는데 일부 사용자가 계속 옛 서버로 갑니다. 왜 그런가요?
A: 클라이언트와 로컬 DNS가 TTL 동안 옛 답을 캐시하기 때문입니다.
Q: 새 버전에 트래픽의 5%만 보내려면 어떤 라우팅 정책인가요?
A: 가중치 라우팅입니다(예: 95와 5).
Q: 리전 A가 정상일 때는 A로만, 장애면 리전 B로 보내려면?
A: 장애 조치 라우팅으로 A를 기본(상태 확인 연결), B를 보조로 둡니다.
Q: 프라이빗 서브넷의 내부 서비스 상태로 Route 53 장애 조치를 하려면 상태 확인을 어떻게 만드나요?
A: CloudWatch 지표에 경보를 만들고, 그 경보를 보는 상태 확인을 만듭니다. 상태 확인기는 VPC 안에 닿지 못합니다.
Q: 독일 사용자에게는 독일어 사이트를, 법적 이유로 특정 국가에만 콘텐츠를 보여 주려면?
A: 지리적 위치 라우팅(기본 레코드 포함)입니다.
Q: 회사 데이터 센터의 DNS 서버가 AWS 프라이빗 호스팅 영역의 이름을 풀어야 합니다. 무엇을 만드나요?
A: Route 53 Resolver 인바운드 엔드포인트입니다.
