앱을 컨테이너로 묶어 실행하는 방법을 배웁니다. AWS 고유의 오케스트레이터인 ECS, 서버를 관리하지 않는 실행 방식 Fargate, 이미지 저장소 ECR, 쿠버네티스를 관리형으로 쓰는 EKS입니다. 시험은 "서버 관리 없이 컨테이너를 실행", "이미 쿠버네티스를 쓰고 있다" 같은 조건으로 서비스를 고르게 합니다.

**Docker**는 앱과 그 앱이 필요한 라이브러리, 런타임, 설정을 **컨테이너**라는 하나의 단위로 묶어 어디서든 똑같이 실행하는 플랫폼입니다.

#### 컨테이너가 푸는 문제

- "내 노트북에서는 되는데 서버에서는 안 된다"가 없어집니다. 실행에 필요한 것이 이미지에 다 들어 있습니다.
- 언어와 버전이 다른 앱(Java 17, Python 3.12, Node.js)을 한 서버에서 서로 간섭 없이 실행합니다.
- 몇 초 만에 시작하고 멈추므로 확장과 배포가 빠릅니다.

#### 컨테이너와 가상 머신

| | 가상 머신(EC2) | 컨테이너 |
|---|---|---|
| 가상화 대상 | 하드웨어(각자 OS를 가짐) | OS(호스트 OS 커널을 함께 씀) |
| 크기 | 수 GB | 수십~수백 MB |
| 시작 시간 | 수십 초~수 분 | 수 초 |
| 한 서버에 올리는 수 | 적음 | 많음 |

#### 이미지와 레지스트리

1. **Dockerfile**에 베이스 이미지, 설치할 것, 실행 명령을 적습니다.
2. `docker build`로 **이미지**를 만듭니다.
3. 이미지를 **레지스트리**에 올립니다(`docker push`).
4. 실행할 곳에서 이미지를 내려받아(`docker pull`) **컨테이너**로 실행합니다.

레지스트리는 Docker Hub 같은 공개 저장소와 회사 전용 비공개 저장소가 있습니다.

#### Amazon ECR(Elastic Container Registry)

AWS의 컨테이너 이미지 저장소입니다.

- **비공개 저장소**와 **공개 저장소**(ECR Public Gallery)를 제공합니다. 이미지는 내부적으로 S3에 저장됩니다.
- ECS, EKS, Lambda(컨테이너 이미지)와 바로 연결되고, 이미지를 내려받는 권한은 **IAM**으로 줍니다(ECS 작업 실행 역할 등).
- **이미지 취약점 스캔**(기본 스캔, Amazon Inspector를 쓰는 향상된 스캔), 태그로 버전 관리, **수명 주기 정책**(오래된 이미지 자동 삭제), **리전 간·계정 간 복제**, Docker Hub 같은 외부 저장소의 **풀스루 캐시**를 지원합니다.

> **시험 포인트** "컨테이너 이미지를 AWS 안에 비공개로 저장하고 IAM으로 접근 통제" → ECR. "이미지에 알려진 취약점이 있는지 자동 검사" → ECR 이미지 스캔(향상된 스캔은 Inspector). "다른 리전의 ECS가 같은 이미지를 빠르게 받아야" → ECR 리전 간 복제.

@practice
- **배포 단위**: 요즘 백엔드 서비스는 대부분 Docker 이미지로 빌드해 배포합니다. CI(GitHub Actions, CodeBuild)가 커밋마다 이미지를 만들어 ECR에 올리고, ECS·EKS가 그 이미지로 새 버전을 띄웁니다.
- **태그 규칙**: 이미지 태그에 Git 커밋 해시나 버전 번호를 붙여, 어떤 코드가 운영에 떠 있는지 추적하고 문제가 생기면 이전 태그로 되돌립니다.
- **보안 점검**: ECR 향상된 스캔으로 운영 이미지의 OS 패키지·라이브러리 취약점을 계속 검사하고, 심각한 취약점이 나오면 이미지를 다시 빌드합니다.
- **비용과 정리**: 수명 주기 정책으로 "최근 30개 태그만 남기고 삭제"를 걸어 저장 비용을 관리합니다.
- **Docker Hub 제한 피하기**: 공개 이미지를 매번 Docker Hub에서 받으면 다운로드 횟수 제한에 걸릴 수 있어, ECR 풀스루 캐시로 한 번 받아 둔 이미지를 씁니다.

컨테이너는 이삿짐을 규격 컨테이너 박스에 담는 것과 같습니다. 무엇이 들었든 박스 규격이 같으니, 어떤 배·트럭·항구(서버)에서도 똑같이 싣고 내릴 수 있습니다. 앱과 필요한 부품을 모두 한 박스(이미지)에 넣어 두면 어느 서버에서 실행해도 같은 결과가 나옵니다.

가상 머신은 집을 통째로 옮기는 것이고, 컨테이너는 같은 건물 안의 방 하나를 쓰는 것입니다. 건물의 기반 설비(OS 커널)를 함께 쓰니 가볍고 빨리 뜹니다.

ECR은 이 박스들을 보관하는 회사 전용 창고입니다. 창고 출입은 IAM으로 통제하고, 박스에 문제 있는 부품이 들었는지 검사도 해 줍니다.

@topic c18-ecs | Amazon ECS: 시작 유형, IAM 역할, 로드 밸런서, 볼륨 | dom=2,3 | prio=3 | rev=1 | les=Amazon ECS; Creating ECS Cluster - Hands On; Creating ECS Service - Hands On; Amazon ECS - Clean Up - Hands On
**ECS(Elastic Container Service)**는 AWS의 컨테이너 오케스트레이션 서비스입니다. 컨테이너를 어느 서버에 몇 개 띄울지, 죽으면 다시 띄울지, 로드 밸런서에 어떻게 연결할지를 대신 관리합니다.

#### 용어

| 용어 | 뜻 |
|---|---|
| 클러스터 | 작업을 실행하는 논리적 묶음 |
| 작업 정의(task definition) | 이미지, CPU·메모리, 포트, 환경 변수, IAM 역할을 적은 실행 설계서(JSON) |
| 작업(task) | 작업 정의로 실행 중인 컨테이너 묶음 하나 |
| 서비스 | 원하는 작업 수를 유지하고 로드 밸런서에 연결하는 관리 단위 |

#### 시작 유형(Launch Type)

| 유형 | 서버 관리 | 특징 |
|---|---|---|
| **EC2** | 직접 | ECS 에이전트가 설치된 EC2를 내가 띄우고 관리(패치, 크기). 인스턴스 유형을 고를 수 있고, 꾸준한 부하는 예약·스팟으로 싸게 |
| **Fargate** | **없음(서버리스)** | 작업 정의에 CPU·메모리만 정하면 AWS가 알아서 실행. 작업 단위로 요금. 확장은 작업 수를 늘리기만 하면 됨 |
| ECS Managed Instances | AWS가 대신 | 2025년 9월 추가. ECS가 내 계정의 EC2를 고르고 띄우고 패치까지 관리(EC2 요금 + 관리 요금) |

#### IAM 역할 두 가지

| 역할 | 누가 쓰나 | 무엇에 |
|---|---|---|
| **EC2 인스턴스 프로파일** | EC2 시작 유형의 ECS 에이전트 | ECS API 호출, CloudWatch Logs로 로그 전송, ECR에서 이미지 받기, Secrets Manager·Parameter Store의 값 읽기 |
| **ECS 작업 역할(task role)** | 작업 안의 앱 | 앱이 부르는 AWS API(예: S3 읽기, DynamoDB 쓰기). **작업 정의마다** 다르게 줌 |

Fargate에서는 인스턴스 프로파일 대신 **작업 실행 역할(task execution role)**이 이미지 받기와 로그 전송을 맡습니다. 서비스마다 작업 역할을 따로 두어 권한을 나눕니다.

#### 로드 밸런서 연결

- **ALB**: 대부분의 경우. 같은 EC2에 여러 작업이 다른 포트로 떠도 **동적 포트 매핑**으로 연결합니다.
- **NLB**: 아주 높은 처리량·성능이 필요하거나, PrivateLink로 서비스를 내보낼 때.

#### 데이터 볼륨

- **EFS**를 작업에 마운트하면 EC2·Fargate 모두에서, 여러 AZ의 작업이 같은 파일을 공유하고 작업이 죽어도 데이터가 남습니다. **Fargate + EFS = 완전 서버리스 + 영구 저장**입니다.
- EBS 볼륨을 작업에 붙일 수도 있습니다(작업마다 따로 쓰는 블록 스토리지).
- **S3는 파일 시스템으로 마운트하지 않습니다**(앱이 SDK로 읽고 씀).

> **시험 포인트** "컨테이너를 실행하되 서버(EC2) 관리는 하기 싫다" → ECS on Fargate. "작업마다 다른 AWS 권한" → ECS 작업 역할. "여러 작업이 같은 파일을 공유하고 영구 저장(Fargate 포함)" → EFS. "하나의 EC2에 같은 서비스 작업 여러 개를 띄우고 ALB에 연결" → 동적 포트 매핑.

> **후기에서** 2026년 6월 합격 후기는 문제를 풀며 헷갈려 따로 정리한 개념에 *ECS와 Fargate*를 넣었습니다. "운영 오버헤드 최소", "서버 관리 없이"가 보이면 Fargate, "특정 인스턴스 유형·GPU", "예약 인스턴스로 비용 절감"이 보이면 EC2 시작 유형입니다.

@practice
- **마이크로서비스 운영**: 주문, 회원, 결제 서비스를 각각 ECS 서비스로 만들고 하나의 ALB 뒤에서 경로로 나눕니다. 배포는 새 작업 정의 버전으로 서비스를 갱신하면 롤링으로 바뀝니다.
- **Fargate로 시작**: 인프라 담당자가 적은 팀은 Fargate로 시작해 서버 패치와 용량 계획을 없앱니다. 트래픽이 커지고 비용이 중요해지면 일부를 EC2 시작 유형이나 Fargate Spot으로 옮깁니다.
- **작업 역할로 권한 나누기**: 같은 클러스터에서 돌아도 결제 서비스 작업만 결제 비밀 값과 결제 테이블에 접근하게 작업 역할을 나눕니다.
- **비밀 값 주입**: DB 비밀번호는 작업 정의에 직접 적지 않고, Secrets Manager의 값을 환경 변수로 주입하도록 설정합니다.
- **배치 작업**: 매일 밤 데이터 정리처럼 잠깐 도는 일도 ECS 작업으로 띄웠다가 끝나면 사라지게 합니다.

@easy
ECS는 컨테이너 박스를 어느 트럭에 몇 개 실을지 정하는 배차 관리자입니다. "이 박스를 항상 4개 운행"이라고 정해 두면, 하나가 고장 나도 새 박스를 띄워 4개를 유지하고 로드 밸런서에 연결합니다.

트럭을 어떻게 준비하느냐가 시작 유형입니다. EC2 방식은 회사 트럭을 직접 사서 정비하는 것이고, Fargate는 택배 회사에 박스만 맡기는 것입니다. Fargate에서는 트럭 정비나 배차 걱정 없이 박스 크기(CPU, 메모리)만큼 요금을 냅니다.

작업 역할은 박스마다 다는 출입증입니다. 같은 트럭에 실려도 결제 박스는 결제 금고만, 주문 박스는 주문 장부만 열 수 있습니다.

@topic c18-ecs-scaling | ECS 자동 확장과 아키텍처 패턴 | dom=2,3 | prio=3 | les=Amazon ECS - Auto Scaling; Amazon ECS - Solutions Architectures
#### 서비스 자동 확장

ECS 서비스의 **원하는 작업 수**를 Application Auto Scaling으로 자동 조절합니다.

| 지표 | 예 |
|---|---|
| 서비스 평균 CPU 사용률 | 60% 유지 |
| 서비스 평균 메모리 사용률 | 70% 유지 |
| ALB 대상당 요청 수 | 작업 하나당 초당 500 요청 |

정책은 대상 추적, 단계 조정, 예약 조정을 씁니다.

#### 작업 수와 서버 수는 따로 늘어난다

**EC2 시작 유형**에서는 작업을 늘려도 그 작업을 올릴 **EC2가 모자라면** 작업이 대기합니다. 서버 수도 함께 늘려야 합니다.

| 방법 | 설명 |
|---|---|
| ASG 조정 | EC2 인스턴스의 CPU 등으로 ASG를 늘림. 작업 수와 맞지 않을 수 있음 |
| **ECS 용량 공급자(Capacity Provider)** | 작업이 필요로 하는 용량에 맞춰 ASG를 **자동으로** 늘리고 줄임. 권장 |

**Fargate**는 서버가 없으므로 작업 수만 늘리면 됩니다. 확장이 가장 간단합니다.

#### 자주 나오는 아키텍처 네 가지

1. **S3 업로드 → EventBridge → ECS 작업**: 파일이 올라오면 EventBridge 규칙이 Fargate 작업을 띄워 처리하고 결과를 DynamoDB에 씁니다. 작업은 ECS 작업 역할로 S3와 DynamoDB에 접근합니다.
2. **EventBridge 일정 → ECS 작업**: 매시간·매일 정해진 시각에 Fargate 작업을 띄워 S3의 데이터를 배치 처리합니다.
3. **SQS 대기열 → ECS 서비스**: 서비스의 작업들이 대기열을 폴링해 메시지를 처리하고, 대기열 길이에 따라 작업 수를 늘립니다.
4. **작업 상태 이벤트 → EventBridge → SNS**: 작업이 비정상 종료(`STOPPED`)되면 EventBridge 규칙이 SNS로 관리자에게 이메일을 보냅니다.

> **시험 포인트** "ECS on EC2에서 작업 수에 맞춰 인스턴스도 자동으로" → 용량 공급자. "업로드된 파일마다 컨테이너로 처리, 서버리스" → S3 → EventBridge → ECS Fargate 작업. "컨테이너 배치 작업을 일정에 맞춰" → EventBridge 일정 규칙 + ECS 작업.

@practice
- **트래픽 기반 확장**: API 서비스는 "작업 하나당 요청 수"로 대상 추적을 걸어, 점심시간 피크에 작업을 10개에서 40개로 늘렸다가 줄입니다.
- **용량 공급자와 스팟**: EC2 시작 유형 클러스터에 온디맨드 ASG와 스팟 ASG 용량 공급자를 함께 두고, "기본 2개는 온디맨드, 나머지는 스팟 비율 3:1"처럼 섞어 비용을 줄입니다. Fargate에서도 Fargate Spot을 섞을 수 있습니다.
- **파일 처리 파이프라인**: 고객이 올린 대용량 엑셀을 S3 이벤트로 받아 Fargate 작업이 검증·적재합니다. Lambda의 15분 제한을 넘는 작업이라 컨테이너를 씁니다.
- **장애 알림**: 작업이 반복해서 죽으면 EventBridge 규칙으로 Slack 채널에 알리는 구성을 거의 모든 팀이 둡니다.

@easy
ECS에서 늘리는 것은 두 가지입니다. 운행하는 박스 수(작업 수)와 그 박스를 실을 트럭 수(EC2 수)입니다. 박스를 더 보내라고 했는데 트럭이 꽉 차 있으면 박스는 출발하지 못하고 기다립니다. 용량 공급자는 박스 수를 보고 트럭을 알아서 더 부르는 배차 담당입니다. Fargate는 트럭을 택배 회사가 대니 박스 수만 늘리면 됩니다.

@topic c18-eks | Amazon EKS | dom=3 | prio=2 | les=Amazon EKS - Overview; Amazon EKS - Hands On
**EKS(Elastic Kubernetes Service)**는 오픈 소스 컨테이너 오케스트레이터 **쿠버네티스(Kubernetes)**를 관리형으로 제공합니다. AWS가 쿠버네티스 컨트롤 플레인(API 서버, etcd)을 여러 AZ에 운영하고, 우리는 워커 노드와 앱을 다룹니다.

#### ECS와 무엇이 다른가

| | ECS | EKS |
|---|---|---|
| API | AWS 고유 | 쿠버네티스 표준(kubectl, Helm) |
| 이식성 | AWS 안에서 | 다른 클라우드·온프레미스와 같은 방식 |
| 학습·운영 부담 | 작음 | 큼(쿠버네티스 지식 필요) |
| 고를 때 | AWS만 쓰고 단순하게 | 이미 쿠버네티스를 쓰거나 여러 클라우드에서 같은 도구를 쓸 때 |

#### 노드 유형

| 유형 | 설명 |
|---|---|
| 관리형 노드 그룹 | EKS가 EC2 노드를 만들고 관리(ASG 기반). 온디맨드·스팟 지원 |
| 자체 관리형 노드 | 직접 만든 EC2를 클러스터에 등록. 사용자 지정 AMI 등 자유도 높음 |
| **AWS Fargate** | 노드 없이 파드를 서버리스로 실행 |
| EKS Auto Mode | 2024년 12월 추가. 노드 선택·확장·패치·핵심 애드온을 EKS가 맡음 |

#### 데이터 볼륨

쿠버네티스 **StorageClass**와 **CSI 드라이버**로 저장소를 붙입니다. 지원하는 것은 EBS, **EFS(Fargate에서도 됨)**, FSx for Lustre, FSx for NetApp ONTAP입니다.

#### 그 밖의 쿠버네티스·컨테이너 선택지

- **EKS Anywhere**: 온프레미스 데이터 센터에서 EKS와 같은 쿠버네티스 클러스터를 운영합니다.
- **EKS Distro**: EKS가 쓰는 쿠버네티스 배포판을 어디서든 직접 설치해 씁니다.
- **ECS Anywhere**: 온프레미스 서버를 ECS 클러스터에 등록해 ECS로 컨테이너를 관리합니다.

> **시험 포인트** "온프레미스에서 쿠버네티스로 운영하던 앱을 AWS로, 도구를 바꾸지 않고" → EKS. "여러 클라우드에서 같은 방식으로 컨테이너 운영" → EKS(쿠버네티스). "쿠버네티스 노드 관리 없이 파드 실행" → EKS on Fargate. "EKS 파드가 여러 AZ에서 같은 파일 공유" → EFS CSI 드라이버.

@practice
- **쿠버네티스 표준화**: 여러 클라우드나 온프레미스에서 같은 배포 도구(Helm, Argo CD)를 쓰려는 회사가 EKS를 고릅니다. 개발자는 어느 환경에서든 같은 매니페스트로 배포합니다.
- **플랫폼 팀 운영**: 큰 회사는 플랫폼 팀이 EKS 클러스터를 운영하고, 서비스 팀은 네임스페이스 단위로 앱만 배포합니다. Karpenter나 EKS Auto Mode로 노드를 자동으로 늘리고 줄입니다.
- **ML·배치 워크로드**: GPU 노드 그룹을 따로 두고 학습 작업이나 추론 서버를 쿠버네티스로 관리합니다.
- **온프레미스 연결**: 공장이나 매장처럼 현장에 서버가 있어야 하는 곳은 EKS Anywhere로 같은 운영 방식을 씁니다.
- **고려할 점**: 쿠버네티스 버전 업그레이드를 1년에 몇 번씩 해야 하고 학습 비용이 커서, 팀이 작고 AWS만 쓴다면 ECS가 더 간단한 경우가 많습니다.

@easy
쿠버네티스는 업계 표준 배차 시스템이고, EKS는 그 시스템의 본부(컨트롤 플레인)를 AWS가 대신 운영해 주는 서비스입니다. ECS가 AWS 전용 배차 관리자라면, 쿠버네티스는 어느 회사·어느 클라우드에서나 같은 사용법으로 쓰는 공통 시스템입니다. 이미 쿠버네티스를 쓰던 회사는 사용법을 바꾸지 않고 AWS로 옮길 수 있습니다. 대신 기능이 많은 만큼 배우고 운영할 것도 많습니다.

@quiz
Q: 컨테이너 이미지를 AWS 안에 비공개로 저장하고, ECS 작업만 내려받게 하려면?
A: Amazon ECR 비공개 저장소에 올리고, ECS 작업 실행 역할(또는 인스턴스 프로파일)에 ECR 읽기 권한을 줍니다.
Q: 컨테이너 앱을 운영하되 EC2 인스턴스의 패치와 용량 관리를 하고 싶지 않습니다.
A: ECS(또는 EKS)를 Fargate로 실행합니다.
Q: 같은 ECS 클러스터의 서비스마다 접근할 수 있는 AWS 리소스를 다르게 하려면?
A: 작업 정의마다 다른 ECS 작업 역할을 지정합니다.
Q: Fargate로 실행하는 여러 작업이 같은 파일을 공유하고, 작업이 재시작돼도 데이터가 남아야 합니다.
A: Amazon EFS를 작업에 마운트합니다.
Q: ECS on EC2에서 서비스 작업 수를 늘렸는데 새 작업이 시작되지 않고 대기합니다. 원인과 해결은?
A: 작업을 올릴 EC2 용량이 부족하기 때문입니다. ECS 용량 공급자로 ASG가 작업 수에 맞춰 자동으로 늘어나게 합니다.
Q: S3에 파일이 올라올 때마다 15분 넘게 걸리는 처리를 서버 관리 없이 하려 합니다.
A: S3 이벤트를 EventBridge로 보내고, 규칙이 ECS Fargate 작업을 실행하게 합니다(Lambda 15분 제한을 넘기 때문).
Q: 온프레미스에서 쿠버네티스로 운영하던 서비스를 도구 변경 없이 AWS로 옮기려 합니다.
A: Amazon EKS입니다.
