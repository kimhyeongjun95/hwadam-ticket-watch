@part ch12 | Amazon S3 Introduction: 객체 스토리지 기초 | 강의 섹션 12 | 12. S3 Introduction
S3는 AWS에서 가장 많이 쓰이고 시험에도 가장 자주 나오는 서비스입니다. 버킷과 객체, 접근 통제(IAM 정책과 버킷 정책), 정적 웹사이트, 버전 관리와 복제, 스토리지 클래스까지 기초를 다집니다.

@topic c12-s3 | S3 기초: 버킷, 객체, 키 | dom=3,4 | prio=3 | les=S3 Overview; S3 Hands On
**S3(Simple Storage Service)**는 파일을 **객체**로 저장하는 **무제한 객체 스토리지**입니다. 백업, 정적 웹사이트, 미디어 호스팅, 데이터 레이크, 로그 보관, 소프트웨어 배포 등 쓰임이 아주 넓습니다.

#### 버킷

- 객체를 담는 최상위 그릇입니다. **리전을 골라** 만듭니다(S3는 글로벌 서비스처럼 보이지만 버킷은 리전에 있습니다).
- 범용 버킷 이름은 **모든 계정과 리전을 통틀어 하나뿐**이어야 합니다.
- 이름 규칙: 3–63자, 소문자·숫자·하이픈(점도 가능), 문자나 숫자로 시작, IP 주소 모양 금지, `xn--`로 시작하거나 `-s3alias`로 끝나면 안 됨.

#### 객체와 키

- **키(key)**는 객체의 **전체 경로 이름**입니다. `s3://my-bucket/photos/2026/cat.jpg`에서 키는 `photos/2026/cat.jpg`이고, `photos/2026/`을 **접두사(prefix)**, `cat.jpg`를 객체 이름이라 부릅니다.
- S3에는 진짜 폴더가 없습니다. 콘솔이 접두사의 `/`를 폴더처럼 보여 줄 뿐입니다.
- 객체 하나의 최대 크기는 **50TB**입니다(2025년 12월에 5TB에서 늘어남). 한 번의 PUT으로는 5GB까지 올리고, 그보다 크면 **멀티파트 업로드**를 씁니다([13.3](#c13-performance)).
- 객체에는 내용 외에 **메타데이터**(키-값 쌍), **태그**(최대 10개, 수명 주기·보안에 씀), **버전 ID**(버전 관리 시)가 붙습니다.

#### 내구성과 가용성

| 지표 | 값 | 뜻 |
|---|---|---|
| 내구성 | 99.999999999%(11 nines), 모든 클래스 | 1,000만 개 객체를 저장하면 평균 1만 년에 1개를 잃는 수준 |
| 가용성 | Standard 99.99%, Standard-IA 99.9%, One Zone-IA 99.5% 등 | 1년에 얼마나 접근하지 못할 수 있는지 |

내구성은 데이터를 **잃지 않는** 정도, 가용성은 데이터에 **접근할 수 있는** 정도입니다. One Zone 클래스는 한 AZ에만 저장하므로 그 AZ가 파괴되면 데이터를 잃습니다.

> **시험 포인트** "용량 제한 없이, 내구성 높게, 싸게 파일 저장" → S3. "파일을 직접 마운트해 여러 서버가 POSIX로 같이 씀"은 S3가 아니라 EFS입니다. S3는 HTTP API로 객체를 통째로 넣고 꺼냅니다(블록·파일 시스템이 아님).

@practice
- **사용자 업로드 저장**: 프로필 사진, 상품 이미지, 첨부 파일을 S3에 두고 DB에는 객체 키(`users/123/profile.jpg`)만 저장합니다. 서버 디스크에 두지 않으니 서버를 몇 대로 늘려도 문제가 없습니다.
- **프런트엔드와 정적 파일 배포**: React·Vue로 빌드한 웹 프런트엔드, 이미지, JS·CSS를 S3에 올리고 CloudFront로 배포합니다.
- **로그와 백업 보관**: ALB 접근 로그, CloudTrail 로그, DB 덤프, 서버 백업이 모두 S3에 쌓입니다. 용량 걱정이 없고 수명 주기로 오래된 것은 싼 클래스로 옮깁니다.
- **데이터 레이크**: 서비스 DB, 로그, 외부 데이터를 S3 한곳에 모으고 Athena·Glue·EMR로 분석합니다. 키에 날짜를 넣어(`logs/2026/10/19/`) 분석 도구가 필요한 날짜만 읽게 합니다.

@easy
S3는 용량 제한 없는 파일 보관 서비스입니다. 클라우드 드라이브와 비슷하지만 몇 가지가 다릅니다. 진짜 폴더가 없고 파일마다 긴 이름(키)이 붙어 있으며, 파일을 통째로 넣고 통째로 꺼냅니다. 파일의 일부만 고쳐 쓰는 일은 없고, 바꾸려면 새 파일을 다시 올립니다. 사람보다 프로그램이 API로 쓰는 경우가 대부분입니다.

내구성과 가용성은 다른 말입니다. 내구성은 맡긴 파일을 잃어버리지 않는 정도이고, 가용성은 꺼내고 싶을 때 바로 꺼낼 수 있는 정도입니다. S3는 파일을 거의 잃어버리지 않지만, 아주 드물게 잠깐 꺼내지 못하는 순간은 있을 수 있습니다.

@topic c12-policy | S3 보안: IAM 정책, 버킷 정책, 퍼블릭 액세스 차단 | dom=1 | prio=3 | les=S3 Security: Bucket Policy; S3 Security: Bucket Policy Hands On
S3 객체에 누가 접근할 수 있는지는 **사용자 쪽 정책(IAM)**과 **리소스 쪽 정책(버킷 정책)**이 함께 정합니다.

| 수단 | 붙는 곳 | 예 |
|---|---|---|
| IAM 정책 | 사용자·그룹·역할 | "이 역할은 `reports` 버킷을 읽을 수 있다" |
| 버킷 정책 | 버킷 | "다른 계정 111122223333이 이 버킷에 쓸 수 있다", "모두 읽기 가능" |
| ACL(객체·버킷) | 객체·버킷 | 옛 방식. 새 버킷은 **ACL이 꺼져 있음**(객체 소유권: 버킷 소유자 강제) |
| 암호화 | 객체 | 키가 없으면 내용을 읽을 수 없음([14.1](#c14-encryption)) |

같은 계정 안에서는 **IAM 정책이나 버킷 정책 중 하나가 허용하고, 어디에도 명시적 Deny가 없으면** 접근할 수 있습니다. 다른 계정이 접근하려면 **양쪽 모두**(그 계정의 IAM 정책과 이 버킷의 정책) 허용해야 합니다.

#### 버킷 정책

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "PublicRead",
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-website-bucket/*"
  }]
}
```

`Principal`이 있다는 점이 IAM 정책과 다릅니다. 버킷 정책의 대표 용도는 다음과 같습니다.

- 정적 웹사이트처럼 **공개 읽기** 허용
- **다른 계정**에 접근 허용
- `aws:SecureTransport`가 false이면 Deny → **HTTPS 강제**
- 특정 **VPC 엔드포인트**나 IP에서만 허용
- 암호화 헤더 없는 업로드 거부

#### 누가 무엇으로 들어오나

| 상황 | 쓰는 것 |
|---|---|
| 우리 계정의 IAM 사용자 | IAM 정책 |
| EC2 안의 앱 | IAM 역할(인스턴스 프로파일) |
| 다른 계정의 사용자 | 버킷 정책(교차 계정) + 그 계정의 IAM 정책 |
| 인터넷 누구나 | 버킷 정책의 `"Principal": "*"` (퍼블릭 액세스 차단을 꺼야 함) |

#### 퍼블릭 액세스 차단(Block Public Access)

정책이나 ACL을 잘못 써서 버킷이 공개되는 사고를 막는 **안전장치**입니다. 켜져 있으면 공개를 허용하는 정책이 있어도 공개되지 않습니다. 새 버킷은 기본으로 켜져 있고, **계정 단위**로도 켤 수 있습니다. 공개할 일이 없는 계정이면 계정 단위로 켜 둡니다.

> **시험 포인트** "다른 AWS 계정이 우리 버킷에 업로드" → 버킷 정책에 그 계정을 Principal로 허용(+ 상대 계정 IAM 정책). "EC2에서 S3 접근" → IAM 역할. "회사 데이터가 실수로 공개되는 것을 계정 전체에서 막음" → 계정 수준 퍼블릭 액세스 차단. "HTTPS가 아닌 요청 거부" → `aws:SecureTransport` 조건의 Deny.

@practice
- **공개 사고 막기**: 보안 사고에서 자주 보이는 원인이 실수로 공개된 버킷입니다. 계정 단위 퍼블릭 액세스 차단을 켜 두고, 공개해야 하는 정적 파일은 CloudFront + OAC로만 내보냅니다.
- **로그 수집 계정**: 회사의 여러 AWS 계정이 CloudTrail·ALB 로그를 보안팀 계정의 로그 버킷 하나에 쓰도록, 그 버킷의 정책에서 각 계정과 서비스를 허용합니다.
- **HTTPS 강제와 경로 제한**: 고객 데이터 버킷에는 `aws:SecureTransport` Deny로 HTTPS를 강제하고, 특정 VPC 엔드포인트에서 오는 요청만 허용해 사내망 밖에서는 아예 접근하지 못하게 합니다.
- **앱 권한 좁히기**: 서버의 IAM 역할에는 버킷 전체가 아니라 필요한 접두사(`uploads/*`)만 허용합니다.

@easy
S3 접근은 두 곳의 규칙으로 정해집니다. 하나는 직원 쪽 권한표(IAM 정책)이고, 하나는 자료실 문에 붙은 출입 규칙(버킷 정책)입니다. 같은 회사 직원은 둘 중 한쪽만 허락해도 들어가지만, 협력사 직원은 소속 회사의 권한표와 우리 자료실 규칙이 모두 허락해야 들어옵니다. 어느 쪽이든 "금지"가 적혀 있으면 들어갈 수 없습니다.

퍼블릭 액세스 차단은 출입 규칙 위에 거는 안전장치입니다. 누가 실수로 "누구나 열람 가능"이라고 적어도 이 장치가 켜져 있으면 공개되지 않습니다.

@topic c12-website | S3 정적 웹사이트 호스팅 | dom=3,4 | prio=2 | les=S3 Website Overview; S3 Website Hands On
S3는 HTML, CSS, 이미지, JavaScript 같은 **정적 파일**로 된 웹사이트를 서버 없이 호스팅할 수 있습니다. 서버에서 실행되는 코드(PHP, DB 조회)는 없고, 브라우저에서 실행되는 JavaScript는 됩니다.

#### 켜는 방법

1. 버킷 속성에서 **정적 웹사이트 호스팅**을 켜고 인덱스 문서(`index.html`)와 오류 문서(`error.html`)를 지정합니다.
2. **퍼블릭 액세스 차단을 끄고**, 버킷 정책으로 `s3:GetObject`를 모두에게 허용합니다.
3. 웹사이트 엔드포인트로 접속합니다. 리전에 따라 `http://버킷이름.s3-website-리전.amazonaws.com` 또는 `http://버킷이름.s3-website.리전.amazonaws.com` 형식입니다.

공개 읽기를 허용하지 않으면 **403 Forbidden** 오류가 납니다. 웹사이트 엔드포인트는 **HTTPS를 지원하지 않으므로**, 실제 서비스에서는 **CloudFront**를 앞에 두어 HTTPS, 사용자 지정 도메인, 캐싱을 붙이고 버킷은 비공개로 둡니다([15.1](#c15-cloudfront)).

> **시험 포인트** "서버 관리 없이 정적 웹사이트를 가장 싸게" → S3 정적 웹사이트(+ CloudFront). "웹사이트에 접속하면 403 오류" → 버킷 정책의 공개 읽기나 퍼블릭 액세스 차단 설정. "HTTPS가 필요" → CloudFront 앞단.

@practice
- **랜딩 페이지와 회사 소개 사이트**: 서버 없이 S3와 CloudFront로 운영하면 월 비용이 아주 적고, 트래픽이 몰려도 서버가 다운될 일이 없습니다.
- **SPA 프런트엔드**: React·Vue 앱의 빌드 결과를 S3에 올리고, API는 별도의 API Gateway나 ALB로 받습니다. 실무에서는 S3 웹사이트 엔드포인트보다 비공개 버킷 + OAC + CloudFront 구성을 더 많이 씁니다.
- **배포 자동화**: CI에서 빌드 → `aws s3 sync`로 업로드 → CloudFront 캐시 무효화 순서로 배포합니다.

@easy
정적 웹사이트는 미리 인쇄해 둔 안내 책자와 같습니다. 누가 와도 같은 내용을 보여 주므로 요리사(서버)가 필요 없습니다. 반면 로그인한 사용자마다 다른 화면을 만들어 주는 동적 사이트는 주문을 받아 요리하는 주방이 필요합니다.

S3 웹사이트 호스팅은 이 책자를 진열하는 기능입니다. 다만 웹사이트 주소가 HTTPS를 지원하지 않고 버킷을 공개해야 해서, 실제 서비스는 앞에 CloudFront를 둡니다. 브라우저에서 실행되는 JavaScript는 정적 파일이라 그대로 동작합니다.

#### 버전 관리(Versioning)

버킷 단위로 켜는 기능입니다. 켜면 같은 키에 다시 올릴 때마다 **새 버전**이 생기고 이전 버전이 남습니다.

- 실수로 덮어쓰거나 지워도 이전 버전으로 되돌릴 수 있습니다.
- 객체를 지우면(버전 ID 없이) 실제로 지워지는 대신 **삭제 마커**가 맨 위에 생깁니다. 삭제 마커를 지우면 객체가 되살아납니다. 특정 버전 ID를 지정해 지우면 그 버전은 **영구 삭제**됩니다.
- 버전 관리를 켜기 전에 있던 객체의 버전 ID는 `null`입니다.
- 버전 관리를 **일시 중지**해도 기존 버전은 지워지지 않습니다. 한 번 켠 버킷은 완전히 끌 수 없고 중지만 됩니다.
- 버전마다 저장 요금이 붙으므로 수명 주기 규칙으로 이전 버전을 정리합니다([13.1](#c13-lifecycle)).

#### 복제(Replication)

한 버킷의 객체를 다른 버킷으로 **비동기 복사**합니다.

| 종류 | 대상 | 쓰임 |
|---|---|---|
| **CRR**(교차 리전 복제) | 다른 리전의 버킷 | 규정 준수, 다른 리전 사용자의 지연 단축, 계정 간 복제 |
| **SRR**(동일 리전 복제) | 같은 리전의 버킷 | 로그를 한 버킷에 모으기, 운영 → 테스트 계정 실시간 복제 |

복제 규칙은 이렇습니다.

- **원본과 대상 버킷 모두 버전 관리**가 켜져 있어야 합니다.
- 버킷은 다른 AWS 계정에 있어도 됩니다. S3가 복제할 수 있도록 IAM 역할 권한을 줍니다.
- **켠 뒤에 새로 들어온 객체만** 복제됩니다. 기존 객체는 **S3 Batch Replication**으로 복제합니다.
- 삭제 작업: **삭제 마커는 설정하면 복제**되고, **버전 ID를 지정한 영구 삭제는 복제되지 않습니다**(악의적 삭제 방지).
- **연쇄 복제는 안 됩니다.** 버킷 1 → 2, 2 → 3으로 설정해도 1의 객체가 3으로 가지 않습니다.
- 복제 시간 보장이 필요하면 **S3 Replication Time Control(RTC)**로 대부분의 객체를 15분 안에 복제합니다.

> **시험 포인트** "실수로 지우거나 덮어쓴 객체를 복구" → 버전 관리. "다른 리전에 재해 복구용 사본, 규정상 데이터를 두 리전에" → CRR(양쪽 버전 관리 필수). "이미 있는 객체도 복제" → S3 Batch Replication. "누군가 원본 버전을 영구 삭제해도 대상은 남아야 한다" → 영구 삭제는 복제되지 않으므로 대상에 남습니다.

@practice
- **실수 복구**: 운영자가 설정 파일을 잘못 덮어쓰거나 지워도 이전 버전으로 되돌립니다. 중요한 버킷은 버전 관리를 켜고, 이전 버전은 수명 주기로 90일 뒤 지워 비용을 관리합니다.
- **랜섬웨어 대비**: 공격자가 파일을 암호화한 새 버전으로 덮어써도 이전 버전이 남습니다. 더 강하게 지키려면 객체 잠금을 함께 씁니다([14.4](#c14-lock)).
- **CRR, 재해 복구와 규정**: 서울 리전 데이터를 다른 리전에 복제해 리전 장애에 대비하거나, 원격지 보관 규정을 지킵니다. 원본 계정이 털려도 남도록 **다른 계정**의 버킷으로 복제하기도 합니다.
- **SRR, 로그 모으기**: 여러 서비스 버킷의 로그를 분석용 버킷 하나로 실시간 복제하거나, 운영 데이터를 테스트 계정 버킷으로 복제합니다.

@easy
버전 관리는 문서 편집기의 버전 기록과 같습니다. 같은 이름으로 다시 저장해도 이전 버전이 기록에 남아서 언제든 되돌릴 수 있습니다. 파일을 지우면 실제로 지워지는 대신 "삭제됨" 표시가 붙고, 그 표시를 지우면 파일이 다시 나타납니다. 휴지통에서 복원하는 것과 비슷합니다.

복제는 새로 들어온 파일을 다른 버킷에 자동으로 한 부 더 보내는 것입니다. 다른 지역에 보내면 교차 리전 복제, 같은 지역이면 동일 리전 복제입니다. 복제를 켜기 전부터 있던 파일은 따로 한꺼번에 보내야 합니다.

@topic c12-classes | 스토리지 클래스 | dom=3,4 | prio=3 | les=S3 Storage Classes Overview; S3 Storage Classes Hands On; S3 Express One Zone
객체마다 **스토리지 클래스**를 고릅니다. 자주 꺼내는 데이터는 저장료가 비싸고 꺼내는 값이 싼 클래스에, 거의 안 꺼내는 데이터는 저장료가 싸고 꺼내는 값과 시간이 드는 클래스에 둡니다.

| 클래스 | 가용성 | AZ | 최소 보관 기간 | 꺼내는 시간 | 꺼내는 요금 | 언제 |
|---|---|---|---|---|---|---|
| S3 Standard | 99.99% | 3개 이상 | 없음 | 밀리초 | 없음 | 자주 쓰는 데이터, 웹 콘텐츠, 분석 |
| S3 Intelligent-Tiering | 99.9% | 3개 이상 | 없음 | 밀리초(보관 계층은 다름) | **없음**(객체당 모니터링 요금) | 접근 패턴을 모를 때 |
| S3 Standard-IA | 99.9% | 3개 이상 | 30일 | 밀리초 | 있음 | 가끔 꺼내지만 꺼낼 땐 빨라야 함(백업, DR) |
| S3 One Zone-IA | 99.5% | **1개** | 30일 | 밀리초 | 있음 | 다시 만들 수 있는 데이터, 다른 곳의 보조 사본 |
| S3 Glacier Instant Retrieval | 99.9% | 3개 이상 | 90일 | **밀리초** | 있음 | 분기에 한 번쯤 꺼내지만 즉시 필요 |
| S3 Glacier Flexible Retrieval | 99.99% | 3개 이상 | 90일 | 신속 1–5분, 표준 3–5시간, 대량 5–12시간 | 있음(대량은 무료) | 연 1–2회 꺼내는 백업·아카이브 |
| S3 Glacier Deep Archive | 99.99% | 3개 이상 | 180일 | 표준 12시간, 대량 48시간 | 있음 | 수년 보관하는 규정 준수 데이터(가장 쌈) |
| S3 Express One Zone | 99.95% | **1개**(고른 AZ) | 없음 | **한 자릿수 밀리초** | 없음 | 아주 낮은 지연이 필요한 분석·ML. 디렉터리 버킷 |

- **IA(Infrequent Access)** 클래스는 객체 하나에 최소 128KB로 요금을 매깁니다. 작은 파일이 많으면 오히려 비쌀 수 있습니다.
- **Intelligent-Tiering**은 30일 동안 안 꺼낸 객체를 Infrequent Access 계층으로, 90일이면 Archive Instant Access 계층으로 자동으로 옮기고, 선택하면 Archive Access(90일 이상)·Deep Archive Access(180일 이상) 계층도 씁니다. 다시 꺼내면 Frequent 계층으로 돌아옵니다.
- 모든 클래스의 내구성은 11 nines입니다. One Zone 계열은 AZ 하나가 파괴되면 데이터를 잃습니다.
- 클래스는 업로드할 때 고르거나, 수명 주기 규칙으로 자동으로 옮깁니다([13.1](#c13-lifecycle)).

> **시험 포인트** "30일 동안은 자주, 이후 가끔 즉시 접근" → Standard → Standard-IA. "접근 패턴을 예측할 수 없고 꺼내는 요금이 없어야" → Intelligent-Tiering. "다시 만들 수 있는 썸네일, 가장 싸게, 즉시 접근" → One Zone-IA. "7년 보관, 꺼낼 때 48시간 걸려도 됨, 가장 싸게" → Glacier Deep Archive. "보관 데이터를 분기에 한 번 즉시(밀리초) 꺼냄" → Glacier Instant Retrieval. "몇 분 안에 꺼내야 하는 아카이브" → Glacier Flexible Retrieval 신속 검색.

@practice
- **Standard**: 서비스 화면에 바로 나가는 이미지와 파일, 자주 분석하는 최근 데이터.
- **Intelligent-Tiering**: 데이터 레이크처럼 어떤 데이터를 얼마나 자주 볼지 예측하기 어려운 버킷의 기본 클래스로 많이 씁니다.
- **Standard-IA**: 서버 백업, 한 달 지난 첨부 파일처럼 가끔 꺼내지만 꺼낼 때는 바로 필요한 데이터.
- **One Zone-IA**: 원본에서 다시 만들 수 있는 썸네일이나 다른 곳에 원본이 있는 보조 사본.
- **Glacier Instant Retrieval**: 오래된 의료 영상이나 뉴스 사진 아카이브처럼 드물게 보지만 요청하면 바로 보여 줘야 하는 데이터.
- **Glacier Flexible·Deep Archive**: 법령상 수년간 보관해야 하는 거래 기록과 감사 로그, 테이프 백업을 대신하는 장기 보관.

@easy
스토리지 클래스는 물류 창고의 보관 구역과 같습니다. 매일 나가는 상품은 출고장 바로 옆에 두고(Standard), 가끔 나가는 상품은 안쪽 선반에(IA), 거의 안 나가는 상품은 외곽 보관 창고에(Glacier) 둡니다. 안쪽일수록 보관료는 싸지만, 꺼낼 때 수수료와 시간이 더 듭니다. 그리고 안쪽 구역은 "최소 며칠은 맡겨야 한다"는 조건이 붙습니다.

One Zone 계열은 창고 건물 한 곳에만 두는 대신 싼 보관입니다. 그 건물에 문제가 생기면 물건을 잃을 수 있으니, 다시 만들 수 있는 것만 둡니다.

@quiz
Q: S3 버킷 이름에 대한 규칙 중 맞는 것은? (a) 계정 안에서만 유일하면 된다 (b) 모든 계정과 리전을 통틀어 유일해야 한다
A: (b)입니다. 범용 버킷 이름은 전 세계에서 하나뿐이어야 합니다. 버킷 자체는 특정 리전에 만듭니다.
Q: 다른 AWS 계정의 역할이 우리 버킷에 객체를 올려야 합니다. 무엇을 설정하나요?
A: 우리 버킷 정책에 그 계정(또는 역할)을 Principal로 허용하고, 그 계정의 IAM 정책에서도 해당 작업을 허용합니다.
Q: S3 정적 웹사이트에 접속하니 403 Forbidden이 뜹니다. 확인할 것은?
A: 퍼블릭 액세스 차단이 꺼져 있는지와, 버킷 정책이 `s3:GetObject`를 공개 허용하는지입니다.
Q: 버전 관리가 켜진 버킷에서 객체를 지웠습니다(버전 ID 없이). 어떻게 되돌리나요?
A: 생긴 삭제 마커를 지우면 이전 버전이 다시 보입니다.
Q: CRR을 켰는데 기존 객체가 복제되지 않습니다. 왜 그렇고 어떻게 하나요?
A: 복제는 켠 뒤의 새 객체만 대상입니다. 기존 객체는 S3 Batch Replication으로 복제합니다.
Q: 접근 패턴을 알 수 없고, 꺼낼 때 추가 요금이 없어야 하는 데이터에 알맞은 클래스는?
A: S3 Intelligent-Tiering입니다.
Q: 규정상 10년 보관해야 하고 꺼낼 일이 거의 없으며, 꺼낼 때 48시간이 걸려도 되는 데이터의 가장 싼 클래스는?
A: S3 Glacier Deep Archive입니다.
Q: 분기에 한 번 즉시(밀리초) 꺼내야 하는 보관 이미지에 알맞은 클래스는?
A: S3 Glacier Instant Retrieval입니다.
