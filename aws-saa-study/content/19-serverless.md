서버를 띄우고 관리하지 않고 코드와 데이터만 다루는 서버리스 서비스를 배웁니다. Lambda(함수), DynamoDB(NoSQL DB), API Gateway(API 입구), Step Functions(작업 흐름), Cognito(사용자 인증)입니다. 시험에서 "운영 오버헤드가 가장 적은", "트래픽이 들쭉날쭉한", "쓴 만큼만 내는" 같은 조건이 보이면 서버리스부터 떠올립니다.

@topic c19-lambda | 서버리스와 AWS Lambda | dom=2,3,4 | prio=3 | les=About the Serverless Section; Serverless Introduction; Lambda Overview; Lambda Hands-On; Lambda Limits
**서버리스(serverless)**는 서버가 없다는 뜻이 아니라, **서버를 직접 띄우고 관리하지 않는다**는 뜻입니다. 용량 계획, OS 패치, 확장을 AWS가 맡고, 우리는 코드와 설정만 다룹니다. Lambda, DynamoDB, API Gateway, S3, SNS, SQS, Kinesis Data Firehose, Aurora Serverless, Step Functions, Fargate가 대표적인 서버리스 서비스입니다.

#### Lambda

**AWS Lambda**는 이벤트가 오면 함수를 실행하고 끝나면 사라지는 서비스입니다.

| | EC2 | Lambda |
|---|---|---|
| 실행 | 켜 두는 서버 | 요청이 올 때만 실행되는 함수 |
| 실행 시간 | 제한 없음 | **최대 15분** |
| 확장 | ASG로 직접 | 요청 수에 맞춰 자동 |
| 요금 | 켜져 있는 시간 | **요청 수 + 실행 시간(GB·초)**. 매달 100만 요청과 40만 GB·초 무료 |

- 언어: Node.js, Python, Java, .NET, Ruby, 그리고 **사용자 지정 런타임**(Go, Rust 등). 컨테이너 이미지로도 배포합니다(Lambda 런타임 API를 구현해야 함).
- 메모리를 정하면 CPU와 네트워크 성능이 비례해 늘어납니다.
- CloudWatch로 모니터링이 바로 됩니다.
- **이벤트 원천**: API Gateway, ALB, S3, DynamoDB Streams, Kinesis, SQS, SNS, EventBridge(일정 포함), Cognito, CloudFront 등.

#### 대표 패턴

- **썸네일 만들기**: S3에 이미지가 올라오면 Lambda가 썸네일을 만들어 다른 버킷에 저장하고 메타데이터를 DynamoDB에 씁니다.
- **서버리스 크론**: EventBridge 일정 규칙이 매시간 Lambda를 실행해 정기 작업을 합니다(EC2를 켜 둘 필요 없음).

#### Lambda 한도(리전마다)

| 항목 | 한도 |
|---|---|
| 메모리 | 128MB–10,240MB(1MB 단위) |
| 최대 실행 시간 | 900초(15분) |
| 환경 변수 | 4KB |
| 임시 저장소 `/tmp` | 512MB–10,240MB |
| 동시 실행 | 기본 1,000(늘릴 수 있음) |
| 배포 패키지 | zip 50MB(압축), 250MB(압축 해제, 레이어 포함). 컨테이너 이미지 10GB |
| 요청 크기 | 동기 6MB, **비동기 1MB**(2025년 10월에 256KB에서 늘어남) |

> **시험 포인트** "15분 넘게 걸리는 작업"은 Lambda가 아니라 ECS·Fargate나 Batch입니다. "10GB 넘는 메모리", "GPU"도 Lambda로 안 됩니다. "정해진 시각마다 짧은 작업, 서버 관리 없이" → EventBridge 일정 + Lambda. "트래픽이 거의 없다가 가끔 몰리는 API, 가장 싸게" → API Gateway + Lambda.

@practice
- **API 백엔드**: 하루 요청이 수천 건인 사내 API나 초기 서비스는 API Gateway + Lambda + DynamoDB로 만들면 서버 비용이 거의 0에 가깝고, 사용자가 늘어도 자동으로 따라갑니다.
- **파일 처리**: 사용자가 올린 이미지의 썸네일 생성, 영수증 PDF의 텍스트 추출 요청, CSV 업로드 후 검증 같은 짧은 작업을 S3 이벤트로 Lambda가 처리합니다.
- **운영 자동화**: 매일 밤 개발 계정의 EC2 끄기, 미사용 EBS 스냅샷 정리, 보안 그룹 변경 감지 후 Slack 알림처럼 운영팀의 반복 작업을 Lambda로 자동화합니다.
- **이벤트 연결**: 결제 완료 이벤트를 받아 정산 시스템에 넘기거나, 외부 웹훅(GitHub, 결제사 알림)을 받아 내부 이벤트로 바꾸는 접착제 역할을 합니다.
- **맞지 않는 경우**: 15분을 넘는 배치, 늘 높은 트래픽을 받는 API(이 경우 컨테이너가 더 쌀 수 있음), 연결을 오래 유지해야 하는 서버에는 쓰지 않습니다.

@easy
EC2가 매달 임대료를 내는 사무실이라면, Lambda는 회의가 있을 때만 시간 단위로 빌리는 회의실입니다. 쓰지 않을 때는 돈이 나가지 않고, 동시에 회의가 많이 잡히면 회의실이 저절로 더 생깁니다. 대신 한 번에 15분까지만 빌릴 수 있고, 회의실에 짐을 두고 갈 수 없습니다(실행이 끝나면 상태가 남지 않음).

함수는 "이런 일이 생기면 이 코드를 실행"하는 규칙으로 동작합니다. 파일이 올라오면, API가 호출되면, 매시 정각이 되면 같은 사건이 함수를 깨웁니다.

@topic c19-concurrency | Lambda 동시성, 콜드 스타트, SnapStart | dom=2,3 | prio=3 | les=Lambda Concurrency; Lambda Concurrency - Hands On; Lambda SnapStart
**동시성(concurrency)**은 같은 순간에 실행 중인 함수 인스턴스 수입니다. 요청이 몰리면 Lambda는 실행 환경을 더 만들어 늘어납니다.

#### 계정 한도와 예약 동시성

- 계정의 리전 전체 동시 실행 기본 한도는 **1,000**입니다. 함수 하나가 이 한도를 다 쓰면 **다른 함수까지 스로틀링**됩니다.
- **예약 동시성(reserved concurrency)**을 함수에 정하면 그 함수의 최대치를 묶고, 그만큼은 그 함수 몫으로 보장됩니다.
- 함수마다 10초에 실행 환경 1,000개씩 늘어날 수 있습니다(계정 한도까지).

#### 한도를 넘으면

| 호출 방식 | 동작 |
|---|---|
| 동기(API Gateway 등) | `429 ThrottleError`를 돌려줌 |
| 비동기(S3 이벤트 등) | 최대 6시간 동안 자동 재시도(지수 백오프) 후, 실패하면 DLQ나 실패 대상으로 |

#### 콜드 스타트와 프로비저닝된 동시성

새 실행 환경을 만들 때는 코드를 내려받고 초기화 코드(SDK 연결, 라이브러리 로딩)를 실행하느라 첫 요청이 느립니다. 이것이 **콜드 스타트**입니다.

- **프로비저닝된 동시성(provisioned concurrency)**: 정한 수만큼 실행 환경을 미리 데워 두어 콜드 스타트를 없앱니다. Application Auto Scaling으로 일정이나 사용률에 맞춰 늘리고 줄입니다. 켜 둔 만큼 요금이 붙습니다.
- **SnapStart**: 함수 버전을 게시할 때 초기화를 미리 해 두고 그 상태의 **스냅숏**을 저장합니다. 새 실행 환경은 스냅숏에서 바로 시작해 콜드 스타트가 크게 줄어듭니다. Java(11 이상)에서 시작해 2024년 11월부터 Python(3.12 이상)과 .NET(8 이상)도 지원합니다.

> **시험 포인트** "한 함수가 몰려서 다른 중요한 함수까지 스로틀링" → 예약 동시성으로 나눔. "첫 요청 지연을 없애야 하는 API" → 프로비저닝된 동시성. "Java 함수의 시작 지연을 추가 비용 없이 줄이고 싶다" → SnapStart.

@practice
- **중요 함수 보호**: 결제 처리 함수에 예약 동시성 200을 걸어 두면, 마케팅 이벤트로 이미지 처리 함수가 폭주해도 결제 함수의 몫이 남습니다. 반대로 외부 API를 부르는 함수에 낮은 예약 동시성을 걸어 상대 시스템을 과부하로부터 보호하기도 합니다.
- **지연에 민감한 API**: 로그인, 결제 승인처럼 첫 요청이 느리면 안 되는 API는 업무 시간에만 프로비저닝된 동시성을 켜고 밤에는 줄입니다.
- **Java 함수**: Spring 기반 Java 함수는 콜드 스타트가 수 초까지 걸릴 수 있어 SnapStart를 켜는 경우가 많습니다.
- **한도 증설**: 이벤트가 큰 서비스는 계정 동시성 한도를 미리 늘려 달라고 요청해 둡니다.

@easy
동시성은 동시에 열려 있는 상담 창구 수입니다. 손님이 몰리면 창구를 더 열지만, 건물 전체에 열 수 있는 창구 수(계정 한도)가 정해져 있습니다. 한 부서가 창구를 다 차지하면 다른 부서 손님은 기다려야 해서, 중요한 부서에는 창구 몇 개를 따로 떼어 둡니다(예약 동시성).

콜드 스타트는 창구를 새로 열 때 컴퓨터를 켜고 업무 시스템에 로그인하는 시간입니다. 프로비저닝된 동시성은 손님이 오기 전에 창구 몇 개를 미리 열어 두는 것이고, SnapStart는 로그인까지 끝난 화면을 저장해 두었다가 새 창구를 열 때 그 화면부터 시작하는 것입니다.

@topic c19-edge | Lambda@Edge와 CloudFront Functions | dom=3 | prio=2 | les=Lambda@Edge & CloudFront Functions
CloudFront 엣지에서 요청과 응답을 바꾸는 코드를 실행하는 방법이 두 가지 있습니다. 서버 없이 사용자 가까이에서 실행되므로 지연이 짧습니다.

#### 실행 시점

- **뷰어 요청**: CloudFront가 사용자의 요청을 받은 직후
- **오리진 요청**: CloudFront가 오리진으로 요청을 보내기 직전
- **오리진 응답**: 오리진의 응답을 받은 직후
- **뷰어 응답**: 사용자에게 응답을 보내기 직전

#### 두 방식 비교

| | CloudFront Functions | Lambda@Edge |
|---|---|---|
| 언어 | JavaScript | Node.js, Python |
| 실행 시점 | **뷰어 요청·뷰어 응답만** | 네 시점 모두 |
| 처리량 | 초당 수백만 요청 | 리전당 초당 최대 1만 요청 |
| 실행 시간 | 1ms 미만 | 수 초까지 |
| 메모리·코드 | 2MB · 10KB | 128MB 이상 · MB 단위 |
| 네트워크·파일 접근 | 안 됨 | 됨 |
| 요청 본문 읽기 | 안 됨 | 됨 |
| 작성 위치 | CloudFront에서 직접 | us-east-1에 만들고 CloudFront가 복제 |

#### 쓰임

| CloudFront Functions | Lambda@Edge |
|---|---|
| 캐시 키 정규화(헤더·쿼리 정리), 헤더 추가·수정, URL 다시 쓰기·리디렉션, JWT 토큰 검증 같은 가벼운 요청 인증 | 외부 서비스·SDK를 부르는 처리, 본문까지 보는 처리, 오리진 선택, 이미지 리사이즈, 무거운 A/B 테스트 |

> **시험 포인트** "엣지에서 아주 가볍고 많은 요청을 처리(헤더 조작, URL 재작성, 토큰 검증), 가장 싸게" → CloudFront Functions. "엣지에서 외부 API를 부르거나 오리진 요청·응답을 바꿈" → Lambda@Edge.

@practice
- **URL 정리와 리디렉션**: 옛 주소(`/old-path`)를 새 주소로 리디렉션하거나, SPA에서 `/about` 같은 경로를 `index.html`로 다시 쓰는 일을 CloudFront Functions로 합니다.
- **보안 헤더 추가**: 모든 응답에 `Strict-Transport-Security`, `Content-Security-Policy` 같은 보안 헤더를 붙입니다.
- **간단한 인증**: 서명된 토큰이 없는 요청을 엣지에서 바로 거절해 오리진까지 오지 않게 합니다.
- **A/B 테스트와 개인화**: 사용자 쿠키를 보고 오리진이나 페이지 버전을 고르는 일을 Lambda@Edge로 합니다.
- **이미지 리사이즈**: 요청한 크기에 맞게 원본 이미지를 줄여 돌려주는 일은 Lambda@Edge나 별도 이미지 처리 서비스로 합니다.

@easy
두 기능은 지역 물류 거점(엣지)에서 상자를 내보내기 직전에 하는 간단한 작업입니다. CloudFront Functions는 상자에 라벨을 붙이거나 주소를 고쳐 쓰는 정도의 아주 빠른 작업만 하고, 대신 엄청난 양을 처리합니다. Lambda@Edge는 상자를 열어 내용을 확인하거나 본사에 전화해 물어보는 일까지 할 수 있지만 그만큼 느리고 비쌉니다.

@topic c19-lambda-vpc | Lambda를 VPC에 연결하기, RDS에서 Lambda 부르기 | dom=1,3 | prio=2 | les=Lambda in VPC; RDS - Invoking Lambda & Event Notifications
#### 기본 위치와 VPC 연결

Lambda는 기본으로 **AWS가 관리하는 VPC**에서 실행됩니다. 인터넷과 퍼블릭 AWS API(S3, DynamoDB 등)에는 닿지만, **우리 VPC 안의 프라이빗 리소스**(RDS, ElastiCache, 내부 ALB)에는 닿지 못합니다.

함수에 **VPC ID, 서브넷, 보안 그룹**을 정하면 Lambda가 그 서브넷에 **ENI**를 만들어 연결합니다.

- 실행 역할에 ENI를 만들 권한이 필요합니다(관리형 정책 `AWSLambdaVPCAccessExecutionRole`).
- VPC에 연결한 Lambda에는 **공인 IP가 붙지 않습니다.** 인터넷(외부 API)에 나가려면 프라이빗 서브넷 + **NAT 게이트웨이**가 필요하고, AWS 서비스는 **VPC 엔드포인트**로 가면 됩니다.

#### Lambda와 RDS

Lambda가 VPC 안의 RDS에 직접 연결하면 함수가 늘어날 때 DB 연결이 폭증합니다. **RDS Proxy**를 앞에 두어 연결을 모읍니다([9.6](#c09-proxy)). RDS Proxy는 VPC 안에서만 접근할 수 있으므로 Lambda도 VPC에 연결해야 합니다.

#### RDS에서 Lambda 호출

**DB 안에서** 데이터가 바뀔 때 Lambda를 부를 수 있습니다(RDS for PostgreSQL, Aurora MySQL). 예를 들어 회원 테이블에 행이 추가되면 환영 이메일을 보내는 Lambda를 호출합니다.

- DB 인스턴스에서 Lambda로 가는 네트워크 경로가 있어야 합니다(퍼블릭 IP, NAT 게이트웨이, 또는 VPC 엔드포인트).
- DB 인스턴스에 Lambda를 호출할 IAM 권한(역할)이 있어야 합니다.

#### RDS 이벤트 알림

**DB 인스턴스 자체에 일어난 일**(생성, 중지, 시작, 백업 시작, 장애 조치, 파라미터 그룹 변경 등)을 SNS나 EventBridge로 거의 실시간 알립니다. **데이터 변경은 알려 주지 않습니다.** 데이터 변경에 반응하려면 위의 DB 내 Lambda 호출이나, Aurora·DynamoDB의 변경 스트림을 씁니다.

> **시험 포인트** "Lambda가 프라이빗 서브넷의 RDS에 접근해야 한다" → 함수를 VPC에 연결(서브넷 + 보안 그룹) + RDS Proxy. "VPC에 연결한 Lambda가 외부 API를 못 부른다" → NAT 게이트웨이. "DB 인스턴스 장애 조치·재부팅을 운영팀에 알림" → RDS 이벤트 알림 → SNS. "테이블에 행이 추가되면 함수 실행" → 이벤트 알림이 아니라 DB에서 Lambda 호출.

@practice
- **사내 DB를 쓰는 함수**: 주문 데이터를 RDS에서 읽어 리포트를 만드는 Lambda를 프라이빗 서브넷에 연결하고, RDS 보안 그룹은 Lambda 보안 그룹만 허용합니다.
- **NAT 비용 주의**: VPC에 연결한 Lambda가 S3나 DynamoDB를 많이 부르면 NAT 게이트웨이 데이터 처리 요금이 커집니다. 게이트웨이 엔드포인트로 바꾸면 이 요금이 사라집니다.
- **운영 알림**: RDS 이벤트 알림을 EventBridge로 받아, 장애 조치나 예정에 없던 재부팅이 생기면 온콜 담당자에게 알립니다.
- **DB 변경에 반응**: 신규 가입 행이 들어오면 Aurora MySQL에서 Lambda를 불러 환영 메일 발송 대기열에 넣는 식으로 씁니다. 다만 DB 안에 업무 로직이 숨어 추적이 어려워지므로, 앱에서 이벤트를 발행하는 방식을 더 선호하는 팀도 많습니다.

@easy
Lambda는 평소 AWS가 마련한 공용 공간에서 일해서, 회사 사내망(VPC) 안의 서버에는 들어가지 못합니다. VPC에 연결하면 사내망에 자리를 하나 받아 사내 DB에 접근할 수 있게 되지만, 대신 사내망의 규칙을 따라야 해서 인터넷에 나갈 때는 사내망의 출입구(NAT 게이트웨이)를 거칩니다.

RDS 이벤트 알림은 DB 서버 자체의 상태 소식(켜짐, 꺼짐, 백업 시작)을 알려 주는 것이고, 표 안의 데이터가 바뀐 것은 알려 주지 않습니다.

@topic c19-dynamodb | Amazon DynamoDB 기초 | dom=2,3,4 | prio=3 | les=Amazon DynamoDB; Amazon DynamoDB - Hands-On
**DynamoDB**는 완전 관리형·서버리스 **NoSQL 키-값·문서 데이터베이스**입니다. 서버나 DB 인스턴스를 만들지 않고 테이블만 만듭니다.

#### 특징

- 여러 AZ에 자동으로 복제되어 고가용성입니다.
- 초당 수백만 요청, 수조 개 행, 수백 TB까지 확장되면서 **한 자릿수 밀리초** 응답을 냅니다.
- IAM으로 보안·인증·인가를 통제합니다.
- 비용이 낮고 자동 확장됩니다. 유지 관리나 패치가 없습니다.
- 테이블 클래스: **Standard**, 자주 안 읽는 데이터용 **Standard-IA**.

#### 데이터 모델

- 테이블마다 **기본 키**가 있습니다. **파티션 키**만 쓰거나, 파티션 키 + **정렬 키**를 함께 씁니다. 기본 키는 테이블을 만들 때 정합니다.
- 테이블에는 **항목(item, 행)**이 무한히 들어가고, 항목마다 **속성(열)**을 자유롭게 추가할 수 있습니다(스키마가 고정되지 않음).
- 항목 하나의 최대 크기는 **400KB**입니다.
- 데이터 유형: 문자열·숫자·바이너리·불리언·null, 리스트·맵(문서), 세트

#### 읽기·쓰기 용량 모드

| 모드 | 방식 | 언제 |
|---|---|---|
| **프로비저닝** | 초당 읽기(RCU)·쓰기(WCU) 용량을 미리 정하고 그만큼 냄. 오토 스케일링 가능 | 트래픽을 예측할 수 있고 꾸준할 때. 더 쌈 |
| **온디맨드** | 용량 계획 없이 요청 수만큼 냄 | 트래픽을 예측할 수 없거나 급증할 때, 새 서비스 |

#### 일관성

기본 읽기는 **최종적 일관성**이라 방금 쓴 값이 아주 잠깐 안 보일 수 있습니다. 읽기 요청에서 **강력한 일관성**을 고르면 최신 값을 읽지만 용량을 두 배로 씁니다.

> **시험 포인트** "스키마가 자주 바뀌고, 초당 수백만 요청, 한 자릿수 밀리초, 서버 관리 없음" → DynamoDB. "트래픽이 예측 불가하고 갑자기 몰림" → 온디맨드 모드. "조인, 복잡한 SQL 쿼리, 트랜잭션 중심의 관계형 데이터" → DynamoDB가 아니라 RDS·Aurora. 항목이 400KB를 넘으면 큰 데이터는 S3에 두고 키만 DynamoDB에 저장합니다.

@practice
- **세션·장바구니·사용자 설정**: 키 하나로 바로 찾는 데이터를 저장합니다. 사용자 ID를 파티션 키로 두면 아무리 사용자가 늘어도 속도가 같습니다.
- **게임과 광고**: 게임 유저의 진행 상태, 아이템, 광고 노출 기록처럼 쓰기가 아주 많고 빠른 응답이 필요한 데이터에 씁니다.
- **서버리스 백엔드**: API Gateway + Lambda와 짝을 이뤄, 연결 수나 서버 관리 걱정 없이 데이터를 저장합니다.
- **IoT·로그 메타데이터**: 기기 ID를 파티션 키, 시각을 정렬 키로 두어 "이 기기의 최근 1시간 기록"을 빠르게 읽습니다.
- **설계 습관**: 관계형 DB처럼 테이블을 나누지 않고, 어떤 화면에서 어떤 조건으로 읽을지(접근 패턴)를 먼저 정한 뒤 키를 설계합니다. 이 설계를 잘못하면 나중에 바꾸기 어렵습니다.

@easy
DynamoDB는 번호표가 붙은 거대한 보관함 벽과 같습니다. 번호(키)만 알면 수억 개 칸 중에서도 원하는 칸을 바로 엽니다. 칸마다 넣는 물건의 종류와 개수가 달라도 됩니다(정해진 스키마가 없음). 대신 "빨간 물건이 든 칸을 모두 찾아라" 같은 검색은 모든 칸을 열어 봐야 해서 느립니다. 그래서 어떻게 찾을지를 먼저 정하고 번호 체계를 짭니다.

관계형 DB가 여러 장부를 엮어 복잡한 질문에 답하는 회계 시스템이라면, DynamoDB는 정해진 방식으로 아주 빠르게 꺼내는 물류 창고 시스템입니다.

@topic c19-dynamodb-adv | DynamoDB 고급: DAX, 스트림, 전역 테이블, TTL, 백업 | dom=2,3 | prio=3 | les=Amazon DynamoDB - Advanced Features
#### DAX(DynamoDB Accelerator)

DynamoDB 전용 **인메모리 캐시**입니다. 읽기가 몰리는 "핫 키"를 캐시해 응답을 **마이크로초** 단위로 줄입니다. DynamoDB API와 호환되어 **앱 코드를 거의 바꾸지 않습니다**. 기본 TTL은 5분입니다.

| DAX | ElastiCache |
|---|---|
| DynamoDB 항목·쿼리 결과를 그대로 캐시 | 앱이 계산한 집계 결과 등 무엇이든 저장 |

#### 스트림 처리

테이블의 항목이 추가·수정·삭제될 때마다 변경 내용을 순서대로 흘려보냅니다.

| | DynamoDB Streams | Kinesis Data Streams for DynamoDB |
|---|---|---|
| 보존 | 24시간 | 최대 1년 |
| 소비자 | 적음(Lambda 트리거, KCL) | 많음(Firehose, Flink, Glue 등) |

쓰임: 변경에 반응하는 처리(환영 메일 발송), 실시간 분석, 다른 테이블로 복사, OpenSearch에 넣어 검색.

#### 전역 테이블(Global Tables)

여러 리전에 테이블을 두고 **양방향(액티브-액티브)**으로 복제합니다. 어느 리전에서나 읽고 쓸 수 있어 전 세계 사용자에게 지연이 짧고, 리전 장애에도 계속 씁니다. **DynamoDB Streams를 켜야** 만들 수 있습니다. 기본 모드는 리전 간 최종적 일관성이고, 2025년 6월부터 **여러 리전에서 강력한 일관성**(MRSC) 모드도 고를 수 있습니다(서울 포함 일부 리전).

#### TTL(Time To Live)

항목에 만료 시각 속성을 두면 그 시각이 지난 항목을 **자동으로 지웁니다**(쓰기 용량을 쓰지 않음). 세션 데이터, 임시 데이터, 규정상 일정 기간 뒤 지워야 하는 데이터에 씁니다.

#### 백업과 S3 연동

| 기능 | 설명 |
|---|---|
| 특정 시점 복구(PITR) | 켜 두면 최근 1–35일 안의 아무 시점으로 **새 테이블**에 복원 |
| 온디맨드 백업 | 지울 때까지 보관. AWS Backup으로 리전 간 복사 등 관리 |
| S3로 내보내기 | PITR이 켜져 있어야 함. 읽기 용량을 쓰지 않음. Athena로 분석하거나 감사용 스냅숏으로 보관 |
| S3에서 가져오기 | CSV, DynamoDB JSON, Ion 형식. 쓰기 용량을 쓰지 않고 **새 테이블**을 만듦 |

> **시험 포인트** "DynamoDB 읽기 지연을 마이크로초로, 코드 변경 최소" → DAX. "항목이 바뀌면 Lambda 실행" → DynamoDB Streams + Lambda. "여러 리전에서 읽고 쓰는 저지연 글로벌 앱" → 전역 테이블. "세션을 일정 시간 뒤 자동 삭제" → TTL. "운영 테이블 성능에 영향 없이 데이터를 S3로 내보내 분석" → S3로 내보내기(PITR 필요).

@practice
- **인기 상품 조회 폭주**: 특정 상품 페이지에 조회가 몰려 읽기 비용이 커지면 DAX를 앞에 둬 같은 항목 읽기를 캐시에서 처리합니다.
- **변경 이벤트 처리**: 주문 테이블의 스트림을 Lambda로 받아 주문 상태가 "배송 시작"으로 바뀌면 알림을 보내고, 검색용으로 OpenSearch에 동기화합니다.
- **글로벌 서비스**: 한국·미국·유럽에 사용자가 있는 게임은 전역 테이블로 각 지역 사용자가 가까운 리전에서 읽고 씁니다.
- **자동 정리**: 로그인 세션, 인증번호, 임시 장바구니에 TTL을 걸어 따로 삭제 작업을 만들지 않습니다.
- **분석 분리**: 운영 테이블을 매일 S3로 내보내 Athena로 분석해, 분석 쿼리가 운영 트래픽에 영향을 주지 않게 합니다.

@easy
다섯 기능은 DynamoDB를 실제 서비스에 쓸 때 생기는 요구를 채웁니다.

- **DAX**: 자주 꺼내는 칸의 물건을 입구 옆 선반에 꺼내 두는 캐시입니다.
- **스트림**: 보관함에 물건이 들어오고 나갈 때마다 기록되는 입출고 알림입니다. 이 알림을 받아 다른 일을 시작합니다.
- **전역 테이블**: 같은 보관함 벽을 여러 나라에 두고 서로 자동으로 맞추는 것입니다.
- **TTL**: 칸마다 "이 날짜가 지나면 비움" 스티커를 붙여 두는 것입니다.
- **백업과 내보내기**: 특정 시점으로 되돌리거나, 분석용 사본을 S3로 옮기는 기능입니다.

@topic c19-apigw | Amazon API Gateway | dom=1,3 | prio=3 | les=API Gateway Overview; API Gateway Basics Hands-On
**API Gateway**는 API를 만들고 공개하고 보호하는 완전 관리형 입구입니다. 뒤에 Lambda를 두면 **서버 없는 REST API**가 됩니다.

#### 하는 일

- API 버전 관리, 환경(dev, test, prod 스테이지) 분리
- 인증·인가, API 키와 사용량 계획, **요청 제한(throttling)**
- 요청·응답 변환과 검증, Swagger·OpenAPI 가져오기, SDK 생성
- 응답 **캐싱**
- WebSocket 실시간 API

#### 뒤에 붙일 수 있는 것

| 통합 | 예 |
|---|---|
| Lambda 함수 | 가장 흔한 서버리스 API |
| HTTP | 온프레미스 API, ALB 뒤의 서비스(인증·요청 제한·캐싱을 앞에서 추가) |
| AWS 서비스 | Lambda 없이 바로 SQS에 메시지 넣기, Step Functions 시작, Kinesis에 쓰기 |

#### 엔드포인트 유형

| 유형 | 설명 |
|---|---|
| 엣지 최적화(기본) | 전 세계 클라이언트용. CloudFront 엣지를 거쳐 들어옴(API는 한 리전에) |
| 리전 | 같은 리전의 클라이언트용. 직접 CloudFront를 앞에 둘 수도 있음 |
| 프라이빗 | VPC 안에서만 인터페이스 VPC 엔드포인트로 접근. 리소스 정책으로 허용 범위를 정함 |

#### 보안

- **IAM 인증**: 내부 앱이나 다른 AWS 서비스가 부를 때(서명 요청)
- **Cognito 사용자 풀**: 앱 사용자 로그인 토큰으로 인증([19.9](#c19-cognito))
- **Lambda 권한 부여자**(사용자 지정): 직접 만든 로직으로 토큰 검증
- **사용자 지정 도메인 HTTPS**: ACM 인증서. 엣지 최적화는 인증서가 **us-east-1**에, 리전 엔드포인트는 같은 리전에 있어야 하며, Route 53에 CNAME이나 Alias를 만듭니다.

#### 알아 둘 한도

- 통합 제한 시간 기본 **29초**(리전·프라이빗 REST API는 계정 요청 한도를 줄이는 조건으로 늘릴 수 있음, 2024년 6월). 페이로드 **10MB**.
- REST API와 더 싸고 단순한 **HTTP API**가 있습니다. 캐싱, 사용량 계획, WAF 연동 같은 기능이 필요하면 REST API입니다.

> **시험 포인트** "서버리스 REST API" → API Gateway + Lambda. "API 사용자별 호출 한도와 API 키" → 사용량 계획. "VPC 안에서만 접근되는 API" → 프라이빗 API + 인터페이스 엔드포인트. "Lambda 없이 API 호출을 SQS에 바로 넣기" → AWS 서비스 통합. "엣지 최적화 API에 사용자 지정 도메인 인증서" → us-east-1의 ACM 인증서.

@practice
- **모바일 앱 백엔드**: 앱이 부르는 API를 API Gateway로 받고, Cognito 토큰으로 인증한 뒤 Lambda로 처리합니다. 서버 없이 사용자 수에 따라 자동으로 늘어납니다.
- **파트너 공개 API**: 외부 파트너에게 API 키와 사용량 계획(예: 하루 1만 건, 초당 50건)을 나눠 주고 사용량에 따라 과금하거나 제한합니다.
- **기존 서버 앞의 관문**: 온프레미스나 ALB 뒤의 레거시 API 앞에 두어 인증, 요청 제한, 캐싱, WAF를 한곳에서 붙입니다.
- **Lambda 없는 통합**: 웹훅으로 들어오는 대량의 이벤트를 API Gateway가 SQS에 바로 넣고, 작업자가 나중에 처리합니다.
- **긴 작업은 비동기로**: 29초 안에 끝나지 않는 작업(리포트 생성)은 요청을 받아 작업 ID만 돌려주고, 결과는 나중에 조회하게 설계합니다.

@easy
API Gateway는 회사 대표 접수처입니다. 외부 요청은 모두 이곳을 거쳐, 신분 확인(인증), 하루 방문 횟수 제한(요청 제한), 자주 묻는 질문에 대한 미리 준비한 답(캐싱)을 거친 뒤 담당 부서(Lambda, 서버, SQS)로 전달됩니다. 담당 부서가 바뀌어도 바깥에 알려진 접수처 주소는 그대로입니다.

@topic c19-stepfunctions | AWS Step Functions | dom=2 | prio=2 | les=Step Functions
**Step Functions**는 여러 단계로 이루어진 작업을 **시각적인 서버리스 워크플로(상태 머신)**로 만들어 실행합니다. 단계 사이의 순서, 분기, 병렬 처리, 재시도, 오류 처리, 대기를 코드 없이 정의합니다.

- Lambda, ECS 작업, AWS Batch, DynamoDB, SNS, SQS, Glue, SageMaker AI 등 **수백 개의 AWS 서비스**와 바로 연결됩니다. 온프레미스 서버도 작업자로 붙일 수 있습니다.
- **사람의 승인 단계**를 넣을 수 있습니다. 워크플로가 토큰을 보내고 승인이 올 때까지 기다립니다.
- 실행 이력이 단계별로 남아 어디서 실패했는지 바로 봅니다.

| 유형 | 실행 시간 | 언제 |
|---|---|---|
| Standard | 최대 1년 | 오래 걸리고 정확히 한 번 실행돼야 하는 업무 흐름(주문 처리, 승인 절차) |
| Express | 최대 5분 | 초당 수많은 짧은 이벤트 처리(IoT 데이터 변환, 스트리밍 처리) |

> **시험 포인트** "여러 Lambda 함수를 순서대로 실행하고, 실패하면 재시도·보상 처리, 사람 승인 단계 포함" → Step Functions. Lambda 안에서 다른 Lambda를 부르며 기다리게 만드는 보기는 비용과 제한 시간 문제로 틀립니다.

@practice
- **주문 처리 흐름**: 결제 승인 → 재고 확보 → 배송 요청 → 알림 발송을 상태 머신으로 만들고, 재고 확보에 실패하면 결제를 취소하는 보상 단계를 둡니다.
- **데이터 파이프라인**: 매일 새벽 Glue 작업으로 데이터를 정리하고, 성공하면 Athena 쿼리를 돌리고, 실패하면 담당자에게 알리는 흐름을 만듭니다.
- **사람 승인**: 대출 심사나 큰 금액 환불처럼 담당자 승인이 필요한 단계에서 워크플로를 멈추고, 승인 버튼이 눌리면 이어서 진행합니다.
- **ML 파이프라인**: 데이터 준비 → SageMaker AI 학습 → 평가 → 기준을 넘으면 배포하는 과정을 자동화합니다.

@easy
Step Functions는 업무 흐름도를 그대로 실행해 주는 결재 시스템입니다. "1단계 결제 확인, 성공하면 2단계 재고 확인, 실패하면 환불 후 종료"처럼 흐름도를 그려 두면, 각 단계 담당자(Lambda, ECS 등)에게 차례로 일을 맡기고 결과에 따라 다음 단계를 고릅니다. 어느 단계에서 멈췄는지 화면에서 바로 보여 줍니다.

@topic c19-cognito | Amazon Cognito | dom=1 | prio=3 | les=Amazon Cognito Overview
**Cognito**는 웹·모바일 앱의 **사용자**(우리 회사 직원이 아니라 서비스 고객)에게 로그인과 AWS 접근 권한을 주는 서비스입니다.

#### 사용자 풀(User Pools): 앱 사용자 로그인

- 회원 가입, 로그인(아이디·비밀번호), 비밀번호 재설정, 이메일·전화 인증, MFA를 제공하는 **서버리스 사용자 데이터베이스**입니다.
- Google, Facebook, Apple, SAML·OIDC(회사 IdP) 같은 **외부 로그인과 연동**합니다.
- 로그인하면 **JWT 토큰**을 줍니다. **API Gateway**와 **ALB**가 이 토큰을 검증해 요청을 받아 줍니다.

#### 자격 증명 풀(Identity Pools): AWS 자원 직접 접근

- 사용자에게 **임시 AWS 자격 증명**을 주어, 앱이 S3나 DynamoDB를 **직접** 부르게 합니다.
- 사용자는 사용자 풀이나 외부 로그인으로 들어온 사람이고, 로그인하지 않은 **게스트**에게도 제한된 권한을 줄 수 있습니다.
- 권한은 IAM 역할과 정책으로 정하며, 조건으로 **사용자마다 자기 데이터만** 접근하게 할 수 있습니다(예: DynamoDB의 파티션 키가 사용자 ID인 항목만, S3의 `user/${사용자 ID}/` 접두사만).

| | 사용자 풀 | 자격 증명 풀 |
|---|---|---|
| 답하는 질문 | "이 사람은 누구인가"(인증) | "이 사람이 AWS에서 무엇을 할 수 있나"(인가) |
| 결과 | JWT 토큰 | 임시 AWS 자격 증명 |
| 붙는 곳 | API Gateway, ALB | S3, DynamoDB 등 AWS API |

> **시험 포인트** "모바일·웹 앱 사용자 수백만 명의 회원 가입과 로그인, 소셜 로그인" → Cognito 사용자 풀. "앱 사용자가 S3에 자기 폴더에만 직접 업로드" → Cognito 자격 증명 풀 + 사용자별 조건 정책. 회사 직원의 AWS 계정 로그인은 Cognito가 아니라 IAM Identity Center입니다([25.4](#c25-identity-center)).

@practice
- **앱 회원 시스템**: 스타트업이 회원 가입·로그인·비밀번호 찾기·소셜 로그인을 직접 만들지 않고 Cognito 사용자 풀로 해결합니다. 백엔드 API는 Cognito 토큰만 검증하면 됩니다.
- **B2B SaaS**: 고객사마다 자기 회사 IdP(SAML, OIDC)로 로그인하게 연결합니다.
- **사진 업로드 앱**: 자격 증명 풀로 사용자에게 `photos/${사용자 ID}/` 경로에만 쓸 수 있는 임시 권한을 주어, 앱이 서버를 거치지 않고 S3에 바로 올립니다.
- **ALB 인증**: 사내 관리자 페이지 앞의 ALB에 Cognito 인증을 걸어, 앱 코드를 고치지 않고 로그인한 사람만 들어오게 합니다.

@easy
사용자 풀은 회원 명부와 로그인 창구입니다. 가입을 받고, 비밀번호를 확인하고, 확인되면 "이 사람은 회원 김철수"라는 증명서(토큰)를 줍니다. API나 로드 밸런서는 이 증명서를 보고 요청을 받아 줍니다.

자격 증명 풀은 회원에게 AWS 창고의 임시 출입증을 내주는 곳입니다. "김철수 님은 오늘 한 시간 동안 자기 사진 폴더에만 들어갈 수 있음"처럼 범위와 기한이 정해진 출입증을 줍니다.

@quiz
Q: 작업 하나가 20분 걸립니다. Lambda로 처리할 수 있나요? 대안은?
A: 아니요. Lambda는 최대 15분입니다. ECS Fargate 작업이나 AWS Batch를 씁니다.
Q: 마케팅 이벤트 때 한 Lambda 함수가 몰리면서 결제 함수까지 스로틀링됐습니다. 대책은?
A: 결제 함수에 예약 동시성을 지정해 몫을 보장하고, 필요하면 계정 동시성 한도 증가를 요청합니다.
Q: 로그인 API의 첫 요청이 콜드 스타트로 느립니다. 지연을 확실히 없애려면?
A: 프로비저닝된 동시성을 설정합니다(Java·Python·.NET이라면 SnapStart도 검토).
Q: CloudFront에서 모든 응답에 보안 헤더를 붙이고 URL을 다시 쓰는 가벼운 처리를 가장 싸게 하려면?
A: CloudFront Functions입니다.
Q: VPC에 연결한 Lambda가 외부 결제 API를 호출하지 못합니다. 원인과 해결은?
A: VPC에 연결한 Lambda에는 공인 IP가 없습니다. 프라이빗 서브넷에 두고 NAT 게이트웨이로 나가게 합니다.
Q: 트래픽이 예측 불가능하게 몰리는 새 서비스의 DynamoDB 테이블 용량 모드는?
A: 온디맨드 모드입니다.
Q: DynamoDB 읽기 지연을 마이크로초로 줄이되 앱 코드는 거의 바꾸고 싶지 않습니다.
A: DAX를 씁니다.
Q: DynamoDB 항목이 추가될 때마다 환영 메일을 보내려면?
A: DynamoDB Streams를 켜고 Lambda 트리거로 처리합니다.
Q: 파트너마다 하루 호출 수를 제한하고 API 키를 발급하려면?
A: API Gateway의 사용량 계획과 API 키를 씁니다.
Q: 여러 Lambda 함수를 순서대로 실행하고 실패 시 재시도와 사람 승인 단계를 넣으려면?
A: Step Functions입니다.
Q: 모바일 앱 사용자가 S3의 자기 폴더에만 직접 업로드하게 하려면?
A: Cognito 자격 증명 풀로 임시 자격 증명을 주고, IAM 정책 조건으로 사용자 ID 접두사만 허용합니다.
