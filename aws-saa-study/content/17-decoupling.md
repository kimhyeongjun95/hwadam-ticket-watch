#### 동기와 비동기

| 방식 | 모습 | 문제 |
|---|---|---|
| 동기 | 주문 서비스가 배송 서비스를 직접 호출 | 갑자기 몰리면 받는 쪽이 감당 못 함 |
| 비동기(이벤트 기반) | 주문 서비스는 메시지를 남기고, 배송 서비스가 가져가 처리 | 서로 기다리지 않음 |

비동기 방식의 세 가지 모양이 이 장의 주제입니다. **대기열**(SQS), **발행·구독**(SNS), **실시간 스트리밍**(Kinesis)입니다.

#### SQS 표준 대기열

**SQS(Simple Queue Service)**는 메시지를 잠시 맡아 두는 완전 관리형 대기열입니다. **생산자**가 메시지를 넣고(`SendMessage`), **소비자**가 가져가(폴링) 처리한 뒤 지웁니다(`DeleteMessage`).

| 항목 | 값 |
|---|---|
| 처리량 | **무제한**, 대기열에 쌓을 수 있는 메시지 수도 무제한 |
| 보존 기간 | 기본 4일, **최대 14일** |
| 지연 | 넣고 받는 데 10ms 미만 |
| 메시지 크기 | **최대 1MiB**(2025년 8월에 256KiB에서 늘어남). 더 크면 S3에 두고 참조만 보내는 Extended Client Library |
| 전달 보장 | **적어도 한 번**(가끔 중복 가능) |
| 순서 | **최선 노력**(순서가 바뀔 수 있음) |

- 소비자는 한 번에 메시지를 최대 10개 받습니다. 처리한 뒤 지우지 않으면 다시 보입니다.
- 소비자를 여러 대 두면 나눠서 병렬로 처리합니다. 소비자는 EC2, Lambda, 온프레미스 서버 무엇이든 됩니다.
- 보안: 전송 중 HTTPS, 저장 시 KMS 암호화(또는 SQS 관리형 SSE), IAM 정책으로 API 접근 통제, **SQS 액세스 정책**(리소스 정책)으로 다른 계정이나 S3·SNS 같은 서비스가 넣도록 허용합니다.

#### 가시성 제한 시간(Visibility Timeout)

소비자가 메시지를 받으면 그 메시지는 **가시성 제한 시간(기본 30초)** 동안 다른 소비자에게 보이지 않습니다.

- 그 안에 지우지 않으면 메시지가 다시 보여 **다른 소비자가 또 처리**합니다(중복 처리).
- 처리가 오래 걸리면 소비자가 `ChangeMessageVisibility`로 시간을 늘립니다.
- 너무 길게 잡으면 소비자가 죽었을 때 재처리가 늦어지고, 너무 짧으면 중복 처리가 늘어납니다.

#### 긴 폴링(Long Polling)

대기열이 비었을 때 소비자가 바로 빈 응답을 받지 않고 **최대 20초까지 기다리게** 합니다. API 호출 수(비용)와 지연이 함께 줄어듭니다. 대기열 설정(`ReceiveMessageWaitTimeSeconds`)이나 요청마다(`WaitTimeSeconds`) 1–20초로 켭니다.

#### 그 밖의 설정

- **배달 못한 편지 대기열(DLQ)**: 메시지를 정한 횟수(`maxReceiveCount`) 넘게 받고도 지우지 못하면 DLQ로 옮겨 따로 살펴봅니다. 고친 뒤 원래 대기열로 되돌릴(redrive) 수 있습니다. DLQ도 보존 기간이 있으므로 넉넉하게(예: 14일) 둡니다.
- **지연 대기열**: 메시지를 넣은 뒤 최대 15분 동안 소비자에게 보이지 않게 합니다.

> **시험 포인트** "주문이 몰리면 처리 서버가 감당 못 함, 주문을 잃으면 안 됨" → SQS로 버퍼링. "같은 메시지가 두 번 처리됨" → 가시성 제한 시간이 처리 시간보다 짧음 → 늘리기. "빈 응답이 많아 비용과 CPU 낭비" → 긴 폴링. "계속 실패하는 메시지 따로 모으기" → DLQ. "1MiB보다 큰 메시지" → S3 + Extended Client Library.

@practice
- **주문 후속 처리**: 주문 API는 주문을 DB에 저장한 뒤 "알림톡 발송", "포인트 적립", "추천 데이터 갱신" 작업을 SQS에 넣고 바로 응답합니다. 알림 시스템이 잠깐 멈춰도 메시지는 대기열에 남아 나중에 처리됩니다.
- **트래픽 완충**: 선착순 쿠폰 응모나 티켓 예매 오픈처럼 순간 요청이 폭주할 때, 요청을 대기열에 받아 두고 처리 서버가 감당할 속도로 꺼내 씁니다.
- **작업자 패턴**: 이미지 변환, PDF 생성, 대용량 엑셀 내보내기처럼 오래 걸리는 일을 대기열에 넣고 작업 서버가 가져가 처리합니다.
- **운영 습관**: 모든 대기열에 DLQ를 붙이고, DLQ에 메시지가 1개라도 쌓이면 경보를 울립니다. 가시성 제한 시간은 작업 최대 처리 시간보다 넉넉하게 잡습니다.

@easy
SQS는 작업 접수함입니다. 일을 맡기는 쪽은 접수함에 요청서를 넣고 바로 자기 일로 돌아가고, 처리하는 쪽은 자기 속도로 하나씩 꺼내 처리합니다. 맡기는 쪽이 갑자기 몰려도 요청서는 접수함에 쌓일 뿐 사라지지 않습니다.

담당자가 요청서를 꺼내면 일정 시간 동안 다른 담당자에게 보이지 않게 잠깁니다(가시성 제한 시간). 그 안에 처리를 끝내고 요청서를 버리면 끝이고, 끝내지 못하면 다시 보여 다른 담당자가 처리합니다. 그래서 처리 시간보다 짧게 잡으면 같은 일을 두 번 하게 됩니다.

@topic c17-fifo | SQS FIFO 대기열 | dom=2 | prio=3 | rev=1 | les=SQS - FIFO Queues
**FIFO(First In First Out)** 대기열은 **순서를 지키고 중복 없이** 한 번만 처리하게 합니다. 이름이 `.fifo`로 끝나야 합니다.

| | 표준 대기열 | FIFO 대기열 |
|---|---|---|
| 순서 | 최선 노력 | **보장**(메시지 그룹 안에서) |
| 전달 | 적어도 한 번(중복 가능) | **정확히 한 번 처리**(중복 제거) |
| 처리량 | 무제한 | API 동작마다 초당 300건, 일괄(10개) 처리 시 3,000건. **고처리량 모드**는 리전에 따라 훨씬 높음 |

- **중복 제거**: 5분 동안 같은 **중복 제거 ID**(또는 내용 기반 해시)의 메시지가 다시 오면 버립니다.
- **메시지 그룹 ID**: 같은 그룹 안에서만 순서를 지킵니다. 그룹마다 소비자가 하나씩 붙을 수 있으므로, 고객 ID처럼 그룹을 나누면 순서를 지키면서도 병렬로 처리합니다.
- 표준 대기열을 FIFO로 바꿀 수는 없고 새로 만들어야 합니다.

> **시험 포인트** "주문 처리 순서가 바뀌면 안 되고 중복 결제가 없어야" → SQS FIFO. "고객별 순서만 지키면 되고 처리량을 늘리고 싶다" → 메시지 그룹 ID를 고객 ID로. "순서 상관없이 초당 수만 건" → 표준 대기열.

> **후기에서** 2026년 6월 합격 후기는 문제를 풀며 헷갈려 따로 정리한 개념에 *SQS FIFO*를 넣었습니다. "순서", "정확히 한 번", "중복 없이"가 보이면 FIFO, "처리량 무제한"이 보이면 표준입니다.

@practice
- **순서가 결과를 바꾸는 일**: 계좌 입출금, 재고 차감, 주문 상태 변경(생성 → 결제 → 배송)처럼 순서가 바뀌면 결과가 틀어지는 처리에 씁니다.
- **메시지 그룹 정하기**: 그룹 ID를 계좌 번호나 주문 번호로 정하면, 같은 계좌의 거래는 순서대로 처리하면서 서로 다른 계좌는 동시에 처리합니다.
- **중복 결제 방지**: 결제 요청 ID를 중복 제거 ID로 쓰면, 네트워크 재시도로 같은 요청이 두 번 들어와도 한 번만 처리됩니다.
- **고르지 않는 경우**: 순서가 상관없는 대량 로그나 알림은 처리량 한도가 없는 표준 대기열을 씁니다.

@easy
FIFO 대기열은 번호표 순서대로 부르는 은행 창구와 같습니다. 먼저 온 요청을 먼저 처리하고, 같은 요청이 실수로 두 번 접수되면 하나는 버립니다.

메시지 그룹은 창구를 업무별로 나누는 것입니다. 같은 고객의 업무는 한 줄에서 순서대로 처리하되, 다른 고객의 줄은 다른 창구에서 동시에 처리해 전체 속도를 높입니다.

@topic c17-sqs-asg | SQS와 Auto Scaling 그룹 | dom=2,3 | prio=3 | les=SQS + Auto Scaling Group
SQS 대기열의 **쌓인 메시지 수**를 보고 소비자 EC2 수를 늘리고 줄이는 구성입니다. 시험에 아주 자주 나오는 그림입니다.

1. 소비자 EC2들을 ASG로 묶습니다.
2. CloudWatch 지표 `ApproximateNumberOfMessagesVisible`(대기 중인 메시지 수)로 **CloudWatch 경보**를 만듭니다. 인스턴스 한 대가 처리할 수 있는 양으로 나눈 **인스턴스당 백로그**를 대상 추적 지표로 쓰면 더 정확합니다.
3. 경보가 울리면 ASG가 인스턴스를 늘리고, 메시지가 줄면 줄입니다.

#### 데이터베이스 쓰기 버퍼

갑자기 주문이 몰리면 앱이 DB에 직접 쓰다 실패해 주문을 잃을 수 있습니다. 앱은 주문을 **SQS에 넣고 바로 응답**하고, 별도 소비자 ASG가 SQS에서 꺼내 DB에 씁니다. SQS는 확장에 한계가 없으므로 요청을 잃지 않습니다(**쓰기 버퍼**).

#### 계층 분리

웹 계층(요청 받기)과 처리 계층(동영상 변환처럼 오래 걸리는 일)을 SQS로 나누면, 두 계층을 **각자의 지표로 따로 확장**합니다.

> **시험 포인트** "처리 서버가 대기열 길이에 맞춰 늘고 줄어야" → SQS 대기열 길이(인스턴스당 백로그) 지표 + ASG. "트래픽이 몰릴 때 DB 쓰기가 실패해 데이터 손실" → SQS로 쓰기 버퍼. "프런트엔드와 백엔드를 따로 확장" → SQS로 분리.

@practice
- **동영상·이미지 작업 서버**: 업로드가 몰리면 대기열이 길어지고, ASG가 인스턴스당 백로그를 보고 작업 서버를 늘립니다. 새벽처럼 대기열이 비면 최소 대수(0대도 가능)까지 줄여 비용을 아낍니다.
- **대량 발송**: 마케팅 이메일·푸시 수십만 건을 대기열에 넣고, 발송 서버 수를 대기열 길이에 맞춰 늘립니다.
- **DB 쓰기 보호**: 선착순 이벤트에서 응모 요청을 대기열에 받아 두고, 소비자가 DB가 감당할 속도로 씁니다. 응모자는 "접수됨"을 바로 보고, 결과는 잠시 뒤 확인합니다.

@easy
대기열 길이로 작업 서버 수를 정하는 것은, 접수함에 쌓인 요청서 수를 보고 담당자를 더 부르는 것과 같습니다. 담당자 한 명이 감당할 수 있는 양을 알면, "요청서 1,000장이면 담당자 10명"처럼 필요한 인원이 바로 나옵니다. CPU 사용률보다 실제 밀린 일의 양을 보므로 더 정확합니다.

@topic c17-sns-fanout | SNS와 팬아웃 패턴 | dom=2,3 | prio=3 | les=Amazon Simple Notification Service (AWS SNS); SNS and SQS -  Fan Out Pattern; SNS - Hands On
#### SNS(Simple Notification Service)

메시지 하나를 **여러 수신자에게 동시에** 보내는 **발행·구독(pub/sub)** 서비스입니다. 생산자는 **주제(topic)**에 한 번 발행하고, 그 주제를 **구독**한 모두가 받습니다.

- 구독자: **SQS**, **Lambda**, **Data Firehose**, HTTP(S) 엔드포인트, 이메일, SMS, 모바일 푸시
- 주제 하나에 구독 1,250만 개까지, 계정당 주제는 10만 개까지(기본 한도)
- 많은 AWS 서비스가 SNS로 알림을 보냅니다: CloudWatch 경보, ASG 알림, S3 이벤트, CloudFormation 상태 변경, AWS Budgets 등
- 보안은 SQS와 같습니다: HTTPS, KMS 암호화, IAM 정책, **SNS 액세스 정책**(다른 계정이나 S3 같은 서비스가 발행하도록 허용)
- **메시지 필터링**: 구독마다 JSON **필터 정책**을 두어 원하는 메시지만 받습니다(예: `state = "placed"`인 주문만).

#### 팬아웃(Fan-out): SNS + SQS

SNS 주제 하나에 **SQS 대기열 여러 개**를 구독시킵니다. 한 번 발행하면 모든 대기열에 사본이 들어가고, 각 대기열의 소비자가 따로 처리합니다.

- 완전히 분리되고 메시지를 잃지 않습니다. SQS가 보존, 지연 처리, 재시도를 맡습니다.
- 나중에 대기열을 더 붙이기만 하면 새 처리기를 추가할 수 있습니다.
- SQS 액세스 정책에서 SNS가 넣을 수 있게 허용해야 합니다. 다른 리전의 대기열도 구독할 수 있습니다.
- **S3 이벤트를 여러 곳에**: S3 이벤트 알림은 같은 이벤트 유형·접두사 조합에 규칙 하나만 둘 수 있으므로, SNS로 보내고 팬아웃합니다([13.2](#c13-events)).
- **SNS → Data Firehose → S3**로 메시지를 저장하거나 분석 도구로 보냅니다.

#### SNS FIFO

SNS 주제도 **FIFO**로 만들 수 있습니다(메시지 그룹 순서, 중복 제거). 구독자로 SQS FIFO와 SQS 표준 대기열을 둘 수 있습니다. 순서와 중복 제거가 필요한 팬아웃에 씁니다.

> **시험 포인트** "주문 하나가 들어오면 배송, 결제, 분석 시스템이 모두 받아야, 서로 영향 없이" → SNS + SQS 팬아웃. "S3 이벤트를 여러 대기열로" → S3 → SNS → 여러 SQS. "구독자마다 다른 메시지만" → SNS 메시지 필터링. "순서까지 지키는 팬아웃" → SNS FIFO + SQS FIFO.

@practice
- **주문 이벤트 배포**: "주문 생성" 이벤트 하나를 SNS 주제에 발행하면 결제, 배송, 정산, 데이터 분석 서비스의 SQS 대기열이 각각 받습니다. 새 서비스가 이 이벤트를 써야 하면 대기열 하나만 구독시키고, 주문 서비스는 고치지 않습니다.
- **운영 알림**: CloudWatch 경보 → SNS → 담당자 이메일·SMS, Slack 채널로 장애 알림을 보냅니다.
- **필터링**: 정산 서비스는 결제 완료 이벤트만, 배송 서비스는 실물 상품 주문만 받도록 구독마다 필터 정책을 겁니다.
- **모바일 푸시**: 앱 사용자에게 보내는 푸시 알림을 SNS 모바일 푸시로 보내기도 합니다.

@easy
SNS는 사내 공지 메일링 리스트와 같습니다. 보내는 사람은 리스트 주소로 한 번만 보내고, 구독한 사람 모두가 같은 내용을 받습니다. 누가 구독했는지 보내는 사람은 몰라도 됩니다.

팬아웃은 그 공지가 각 부서의 업무 접수함(SQS)으로 한 장씩 들어가게 하는 구성입니다. 부서마다 자기 속도로 처리하고, 한 부서가 휴가 중이어도 공지는 접수함에 남아 있습니다.

@topic c17-kinesis | Kinesis Data Streams | dom=3 | prio=3 | les=Amazon Kinesis Data Streams; Amazon Kinesis Data Streams - Hands On
**Kinesis Data Streams**는 클릭 기록, IoT 센서, 로그, 주식 시세처럼 **끊임없이 들어오는 데이터를 실시간으로** 모으고 저장하는 스트림입니다.

#### 구조

- 스트림은 **샤드(shard)**로 나뉩니다. 생산자가 보낸 **레코드**는 **파티션 키**에 따라 한 샤드로 갑니다. **같은 파티션 키는 같은 샤드**로 가므로 그 안에서 **순서가 지켜집니다**.
- 생산자: AWS SDK, Kinesis Producer Library(KPL), Kinesis 에이전트 등
- 소비자: 직접 만든 앱(SDK, KCL), **Lambda**, **Data Firehose**, Managed Service for Apache Flink
- 데이터는 **보존 기간(1일–365일)** 동안 남아 있어 **다시 읽기(재처리)**가 됩니다. 소비자가 읽어도 지워지지 않습니다. 넣은 데이터는 바꾸거나 지울 수 없습니다.
- 레코드 하나는 기본 1MiB, 스트림 설정을 바꾸면 **10MiB**까지 됩니다(2025년 10월).
- 보안: KMS 저장 암호화, HTTPS, IAM, VPC 엔드포인트

#### 용량 모드

| 모드 | 방식 | 언제 |
|---|---|---|
| **프로비저닝** | 샤드 수를 직접 정함. 샤드 하나에 **쓰기 1MB/s(또는 초당 1,000 레코드), 읽기 2MB/s**. 샤드 시간당 요금 | 처리량을 예측할 수 있을 때 |
| **온디맨드** | 샤드를 신경 쓰지 않음. 지난 30일 최대 쓰기량의 두 배까지 자동 수용. 스트림 시간당 + 데이터양 요금 | 처리량을 예측하기 어려울 때 |

> **시험 포인트** "실시간 클릭 스트림·IoT 데이터를 여러 앱이 각자 읽고, 다시 읽을 수도 있어야" → Kinesis Data Streams. "장치별로 순서 유지" → 파티션 키를 장치 ID로. "쓰기 처리량 부족(ProvisionedThroughputExceeded)" → 샤드 늘리기 또는 온디맨드 모드. "실시간으로 받아 S3에 저장만" → Data Firehose가 더 간단합니다([17.6](#c17-firehose)).

@practice
- **클릭 스트림과 앱 로그**: 웹·앱의 화면 조회, 클릭, 검색 이벤트를 실시간으로 모아 추천 시스템과 실시간 대시보드에 씁니다.
- **이상 거래 탐지**: 카드 결제 이벤트를 스트림으로 받아 몇 초 안에 의심 거래를 찾아냅니다(Managed Service for Apache Flink 같은 실시간 처리와 함께).
- **IoT와 게임 이벤트**: 차량·센서 데이터, 게임 플레이 로그처럼 끊임없이 들어오는 데이터를 받습니다.
- **여러 소비자**: 같은 스트림을 실시간 분석 애플리케이션과 저장용 Firehose(→ S3)가 동시에 읽습니다. 분석 로직에 버그가 있었다면 보존 기간 안의 데이터를 처음부터 다시 처리합니다.

@easy
Kinesis Data Streams는 데이터가 쉬지 않고 흘러가는 컨베이어 벨트입니다. 여러 레인(샤드)이 있고, 같은 키의 데이터는 늘 같은 레인으로 가서 순서가 지켜집니다.

SQS와 가장 다른 점은 꺼내 가도 사라지지 않는다는 것입니다. 데이터는 보존 기간 동안 벨트 위에 남아 있어서, 여러 팀이 같은 데이터를 각자 읽을 수 있고 필요하면 처음부터 다시 읽을 수 있습니다.

@topic c17-firehose | Amazon Data Firehose | dom=3,4 | prio=3 | les=Amazon Data Firehose; Amazon Data Firehose - Hands On
**Amazon Data Firehose**(예전 이름 Kinesis Data Firehose)는 스트리밍 데이터를 받아 **저장소로 배달**하는 완전 관리형 서비스입니다. 코드나 서버 없이 자동으로 확장하고, 쓴 만큼 냅니다.

- **원천**: 직접 PUT(SDK, Kinesis 에이전트), **Kinesis Data Streams**, MSK, CloudWatch Logs, SNS 등
- **변환**: Lambda로 레코드를 바꾸고, **Parquet·ORC로 형식 변환**, 압축(GZIP 등)
- **대상**: **S3**, **Redshift**(S3를 거쳐 COPY), **OpenSearch**, Apache Iceberg 테이블, Splunk, Datadog·New Relic·MongoDB 같은 서드파티, 사용자 지정 HTTP 엔드포인트
- **버퍼**: 크기나 시간이 찰 때까지 모았다가 한꺼번에 씁니다. 그래서 **거의 실시간**입니다(버퍼를 0초로 줄일 수도 있음).
- 배달에 실패한 데이터나 원본 전체를 **백업 S3 버킷**에 따로 남길 수 있습니다.
- 데이터를 **저장하지 않으므로 다시 읽기(재처리)는 안 됩니다.**

#### Kinesis Data Streams와 비교

| | Kinesis Data Streams | Data Firehose |
|---|---|---|
| 하는 일 | 데이터를 모으고 **저장**(재처리 가능) | 데이터를 받아 **배달**(저장·재처리 없음) |
| 소비자 코드 | 직접 작성(또는 Lambda 등) | 필요 없음(완전 관리형) |
| 지연 | **실시간**(약 200ms) | **거의 실시간**(버퍼) |
| 확장 | 샤드 관리 또는 온디맨드 | 자동 |

> **시험 포인트** "스트리밍 로그를 S3·Redshift·OpenSearch에 코드 없이 적재, 운영 부담 최소" → Data Firehose. "적재 전에 Parquet로 바꿔 Athena 비용 절감" → Firehose 형식 변환. "실시간(밀리초)으로 처리하고 재처리 필요" → Kinesis Data Streams. "Kinesis Data Streams의 데이터를 S3에 보관" → Data Streams → Firehose → S3.

> **후기에서** 2026년 5월 정리 노트는 Data Firehose를 "스트리밍 데이터를 수집해 S3, Redshift, OpenSearch 등으로 실시간 변환 및 자동 로드(배달)해 주는 서비스"로, 2월 정리 노트는 "데이터 수집 → Firehose(코드 없이 S3·DB로 전송)"으로 정리했습니다.

@practice
- **로그를 데이터 레이크로**: 웹 서버·앱 로그를 Firehose로 받아 Parquet로 바꿔 S3에 날짜별로 쌓고, Athena로 조회합니다. 코드나 서버를 따로 운영하지 않습니다.
- **로그 검색**: 같은 로그를 OpenSearch로 보내 장애 때 키워드로 검색합니다.
- **분석 DB 적재**: 이벤트 데이터를 Redshift로 보내 BI 도구에서 거의 실시간으로 봅니다.
- **외부 도구 연동**: Splunk, Datadog 같은 모니터링 서비스로 로그를 보냅니다.
- **CloudWatch Logs 장기 보관**: CloudWatch Logs 구독 필터 → Firehose → S3로 로그를 싸게 오래 보관합니다.

@easy
Firehose는 택배 집하 차량과 같습니다. 여러 곳에서 들어오는 데이터를 받아 일정량이 차거나 일정 시간이 지나면 묶어서 목적지(S3, Redshift, OpenSearch)로 배송합니다. 가는 길에 포장을 바꾸거나(형식 변환) 압축할 수 있습니다. 배송만 하고 보관하지 않으므로 지난 데이터를 다시 보내 달라고 할 수는 없습니다.

@topic c17-compare-mq | SQS·SNS·Kinesis 비교와 Amazon MQ | dom=2,3 | prio=3 | les=SQS vs SNS vs Kinesis; Amazon MQ
#### 세 서비스 비교

| | SQS | SNS | Kinesis Data Streams |
|---|---|---|---|
| 모델 | 소비자가 **가져감(pull)** | SNS가 구독자에게 **밀어 줌(push)** | 소비자가 가져감(pull 또는 확장 팬아웃 push) |
| 처리 후 | 소비자가 **지움** | 저장 안 함(전달 실패 시 재시도) | **보존 기간 동안 남음**, 재처리 가능 |
| 소비자 | 여러 소비자가 **나눠** 처리 | 모든 구독자가 **같은 메시지**를 받음 | 여러 소비자가 **같은 데이터**를 각자 읽음 |
| 순서 | FIFO 대기열에서 보장 | FIFO 주제에서 보장 | **샤드 안에서** 보장 |
| 용량 | 프로비저닝 불필요 | 프로비저닝 불필요 | 샤드(프로비저닝) 또는 온디맨드 |
| 쓰임 | 작업 대기열, 버퍼 | 알림, 팬아웃 | 실시간 빅데이터, 분석, ETL |

#### Amazon MQ

SQS와 SNS는 AWS 고유의 API를 씁니다. 온프레미스 앱이 이미 **MQTT, AMQP, STOMP, OpenWire, WSS** 같은 **개방형 프로토콜**로 메시지 브로커(ActiveMQ, RabbitMQ)를 쓰고 있다면, 코드를 고치지 않고 옮기기 위해 **Amazon MQ**를 씁니다.

- **Apache ActiveMQ**와 **RabbitMQ**를 관리형으로 제공합니다.
- 서버 위에서 돌므로 SQS·SNS처럼 무한히 확장되지는 않습니다.
- 대기열(SQS 비슷)과 주제(SNS 비슷) 기능을 모두 가집니다.
- **고가용성**: ActiveMQ는 두 AZ에 활성·대기 브로커를 두고 EFS를 공유 스토리지로 써서 장애 조치하고, RabbitMQ는 여러 AZ에 걸친 클러스터로 배포합니다.

> **시험 포인트** "온프레미스의 ActiveMQ·RabbitMQ, AMQP·MQTT를 쓰는 앱을 코드 변경 없이 이전" → Amazon MQ. "클라우드에서 새로 만드는 앱의 대기열" → SQS(무제한 확장, 관리 부담 적음). "한 메시지를 여러 시스템에" → SNS. "실시간 스트리밍을 여러 소비자가 재처리" → Kinesis.

@practice
- **고르는 기준**: 작업을 나눠 처리하면 SQS, 같은 이벤트를 여러 시스템에 알리면 SNS(+ SQS 팬아웃), 실시간 데이터를 여러 소비자가 읽고 다시 읽어야 하면 Kinesis, 스트리밍 데이터를 저장소에 적재만 하면 Firehose입니다.
- **Amazon MQ로 이전**: 사내에서 ActiveMQ나 RabbitMQ를 쓰던 주문·물류 시스템을 클라우드로 옮길 때, 코드를 거의 고치지 않으려고 Amazon MQ를 씁니다. 옮긴 뒤 새로 만드는 부분부터 SQS·SNS로 바꾸는 경우가 많습니다.
- **Spring·자바 레거시**: JMS로 메시지 브로커를 쓰는 자바 애플리케이션은 Amazon MQ(ActiveMQ)로 옮기기 쉽습니다.

@easy
세 서비스는 메시지를 받은 뒤 어떻게 하느냐가 다릅니다. SQS는 담당자 한 명이 가져가 처리하면 사라지는 접수함, SNS는 구독자 모두에게 한꺼번에 보내고 남기지 않는 공지, Kinesis는 일정 기간 남겨 두고 여러 팀이 각자 읽는 기록 장부입니다.

Amazon MQ는 업계 표준 방식(AMQP, MQTT 등)으로 말하는 메시지 중계 서버를 빌려주는 서비스입니다. 원래 그 방식으로 개발된 시스템을 그대로 옮길 때 씁니다.

@quiz
Q: 쇼핑몰 행사 때 주문이 몰려 주문 처리 서버가 일부 주문을 놓칩니다. 주문을 잃지 않으려면?
A: 주문을 SQS에 넣고, 처리 서버(ASG)가 대기열에서 꺼내 처리하게 합니다.
Q: 소비자가 메시지 하나를 처리하는 데 2분 걸리는데, 같은 메시지가 여러 번 처리됩니다. 원인과 해결은?
A: 가시성 제한 시간(기본 30초)이 처리 시간보다 짧아 메시지가 다시 보이기 때문입니다. 가시성 제한 시간을 2분보다 길게 늘리거나 처리 중에 ChangeMessageVisibility로 늘립니다.
Q: 대기열이 자주 비어 있는데 소비자가 계속 요청해 비용이 늘어납니다.
A: 긴 폴링(최대 20초 대기)을 켭니다.
Q: 결제 요청을 정확히 한 번, 들어온 순서대로 처리해야 합니다. 고객이 많아 처리량도 늘려야 합니다.
A: SQS FIFO 대기열을 쓰고 메시지 그룹 ID를 고객 ID로 정합니다(고객별 순서 유지, 고객 간 병렬 처리).
Q: 동영상 변환 작업자 EC2 수를 대기열에 쌓인 작업량에 맞춰 조절하려 합니다.
A: SQS 대기열 길이(인스턴스당 백로그) 지표로 ASG 대상 추적 조정을 설정합니다.
Q: 새 주문 이벤트를 결제, 배송, 분석 시스템이 각각 받아야 하고, 한 시스템이 멈춰도 메시지를 잃으면 안 됩니다.
A: SNS 주제에 SQS 대기열 세 개를 구독시키는 팬아웃 구성입니다.
Q: IoT 장치 수만 대의 데이터를 실시간으로 받아 여러 분석 앱이 읽고, 문제가 생기면 지난 데이터를 다시 처리해야 합니다.
A: Kinesis Data Streams입니다. 보존 기간 안의 데이터를 다시 읽을 수 있습니다.
Q: 애플리케이션 로그를 코드 없이 S3에 Parquet 형식으로 적재하려 합니다.
A: Amazon Data Firehose의 형식 변환으로 Parquet로 바꿔 S3에 배달합니다.
Q: 온프레미스에서 RabbitMQ와 AMQP를 쓰는 앱을 코드 변경 없이 AWS로 옮기려 합니다.
A: Amazon MQ(RabbitMQ)입니다.
