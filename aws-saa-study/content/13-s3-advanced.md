S3를 오래 운영하면 쌓인 객체를 싼 클래스로 옮기고, 객체가 들어올 때 다른 서비스를 움직이고, 많은 요청을 빠르게 처리해야 합니다. 이 장은 수명 주기 규칙, 이벤트 알림, 성능 기법, 그리고 대량 작업과 비용 관리 도구를 다룹니다.

@topic c13-lifecycle | 수명 주기 규칙과 스토리지 클래스 분석 | dom=4 | prio=3 | les=S3 Lifecycle Rules (with S3 Analytics); S3 Lifecycle Rules - Hands On
**수명 주기 규칙(Lifecycle rule)**은 객체가 만들어진 뒤 정해진 날짜가 지나면 클래스를 바꾸거나 지우는 규칙입니다. 손으로 옮기지 않아도 저장 비용이 저절로 내려갑니다.

#### 두 가지 작업

| 작업 | 하는 일 | 예 |
|---|---|---|
| **전환(Transition)** | 다른 스토리지 클래스로 옮김 | 60일 뒤 Standard-IA로, 180일 뒤 Glacier Flexible Retrieval로 |
| **만료(Expiration)** | 객체를 지움 | 액세스 로그를 365일 뒤 삭제, 이전 버전을 90일 뒤 삭제, 끝나지 않은 멀티파트 업로드 조각 삭제 |

- 규칙은 버킷 전체, 특정 **접두사**(`logs/`), 특정 **태그**(`dept=finance`), 객체 크기에 걸 수 있습니다.
- **현재 버전**과 **이전 버전(noncurrent)**에 따로 규칙을 줄 수 있습니다. 버전 관리 버킷에서 이전 버전이 쌓이는 비용을 이렇게 줄입니다.
- 전환은 Standard → Standard-IA·Intelligent-Tiering → One Zone-IA → Glacier 계열처럼 **더 싼 쪽으로만** 갑니다. Glacier에서 Standard로 되돌리는 수명 주기 규칙은 없습니다(복원은 따로 요청).
- Standard-IA와 One Zone-IA로는 만든 지 **30일이 지나야** 옮길 수 있습니다. Glacier 클래스는 최소 보관 기간(90일, 180일)보다 일찍 지우면 남은 기간 요금을 냅니다.
- 2024년 9월부터 새로 만들거나 고친 규칙은 **128KB보다 작은 객체를 옮기지 않는 것**이 기본입니다. 작은 객체는 옮기는 요청 비용이 아끼는 저장료보다 크기 때문입니다.

#### 강의의 두 시나리오

| 상황 | 규칙 |
|---|---|
| 원본 사진은 60일 동안 즉시 꺼내야 하고 그 뒤에는 6시간 기다려도 됨. 썸네일은 다시 만들 수 있고 60일만 보관 | 원본: Standard → 60일 뒤 Glacier Flexible Retrieval. 썸네일: One Zone-IA → 60일 뒤 만료 |
| 지운 객체를 30일 동안은 즉시 복구, 그 뒤 365일까지는 48시간 안에 복구 | 버전 관리를 켜고(지운 객체가 이전 버전으로 남음), 이전 버전을 Standard-IA로 옮긴 뒤 365일 동안 Glacier Deep Archive에 둠 |

#### 스토리지 클래스 분석(S3 Analytics)

언제 옮기면 좋을지 모를 때는 **스토리지 클래스 분석**을 켭니다. 접근 패턴을 지켜보고 **Standard → Standard-IA**로 옮길 시점을 추천합니다(One Zone-IA나 Glacier는 추천하지 않음). 보고서는 매일 갱신되고, 켠 뒤 24–48시간이 지나야 결과가 보이기 시작합니다. 이 결과를 보고 수명 주기 규칙을 만들거나 고칩니다.

> **시험 포인트** "30일 뒤에는 거의 안 쓰고, 1년 뒤에는 지워야 함, 가장 싸게" → 수명 주기 규칙(전환 + 만료). "이전 버전이 쌓여 비용이 늘었다" → 이전 버전 전환·만료 규칙. "규칙을 정할 근거가 필요" → 스토리지 클래스 분석. 접근 패턴을 아예 모르면 수명 주기보다 Intelligent-Tiering이 답입니다([12.5](#c12-classes)).

> **후기에서** 2026년 2월의 시험 대비 정리 노트는 "짧다고 고르면 틀리는 함정"으로 이 유형을 들었습니다. "Glacier Deep Archive에 다 넣는다"는 싸 보이지만 처음 30일 동안 자주 꺼내야 하면 오답이고, "30일은 Standard, 그 뒤 수명 주기로 Glacier"가 정답이라는 정리입니다.

@practice
- **로그 버킷**: ALB·CloudTrail 로그는 30일 동안 Standard, 그 뒤 Standard-IA, 1년이 지나면 Glacier로 옮기고, 회사 보존 규정(예: 5년)이 끝나면 삭제합니다. 사람이 손대지 않아도 보존 규정이 지켜집니다.
- **숨은 비용 정리**: 끝나지 않은 멀티파트 업로드 조각은 목록에 보이지 않으면서 요금만 나갑니다. "7일 지난 미완료 멀티파트 업로드 삭제" 규칙을 모든 버킷에 기본으로 거는 회사가 많습니다.
- **이전 버전 정리**: 버전 관리를 켠 버킷은 "이전 버전 30일 뒤 IA, 90일 뒤 삭제"처럼 이전 버전 규칙을 함께 겁니다.
- **근거 만들기**: 데이터가 많은 버킷은 스토리지 클래스 분석을 몇 주 켜 두고, 실제 접근 패턴을 본 뒤 전환 날짜를 정합니다.

@easy
수명 주기 규칙은 회사의 문서 보존 규정을 자동으로 집행하는 장치입니다. "1년이 지난 서류는 외부 보관 창고로, 5년이 지나면 파기"를 규정집에 적어 두면, 담당자가 날짜를 세지 않아도 그대로 처리됩니다. 옮기는 방향은 더 싼 보관 쪽으로만 정할 수 있습니다.

**이벤트 알림(Event Notifications)**은 버킷에서 일이 생기면 다른 서비스에 알려 줍니다. "사진이 올라오면 썸네일을 만든다" 같은 이벤트 기반 설계의 출발점입니다.

#### 무엇을, 어디로

- **이벤트**: `s3:ObjectCreated:*`(PUT, POST, COPY, 멀티파트 완료), `s3:ObjectRemoved:*`, `s3:ObjectRestore:*`(Glacier 복원), 복제 이벤트 등. 접두사·접미사로 거를 수 있습니다(예: `images/`로 시작하고 `.jpg`로 끝나는 객체만).
- **대상**: **SNS 표준 주제**, **SQS 표준 대기열**, **Lambda 함수**, 그리고 **EventBridge**. 알림 하나에 대상은 하나입니다.
- 보통 몇 초 안에 전달되지만 1분 이상 걸릴 때도 있습니다.

#### 권한은 대상 쪽 리소스 정책으로

S3가 SNS·SQS·Lambda를 부르려면 **대상 쪽에 리소스 기반 정책**이 있어야 합니다. IAM 역할을 S3에 붙이는 방식이 아닙니다.

| 대상 | 필요한 정책 |
|---|---|
| SNS 주제 | SNS 액세스 정책에서 S3(`s3.amazonaws.com`)의 `sns:Publish` 허용 |
| SQS 대기열 | SQS 액세스 정책에서 S3의 `sqs:SendMessage` 허용 |
| Lambda 함수 | Lambda 리소스 정책에서 S3의 `lambda:InvokeFunction` 허용 |

#### EventBridge로 보내기

버킷에서 EventBridge 연동을 켜면 **모든 S3 이벤트**가 EventBridge로 갑니다. 그 뒤 EventBridge 규칙으로 고릅니다.

- 객체 크기, 이름, 메타데이터 같은 **세밀한 필터**
- 한 이벤트를 **여러 대상**으로 동시에(Step Functions, Kinesis Data Streams, Firehose 등 수십 종)
- 이벤트 **보관(archive)과 재생(replay)**, 더 안정적인 전달
- **SQS FIFO 대기열이나 SNS FIFO 주제**로 보내야 할 때(S3 알림은 FIFO를 직접 대상으로 쓸 수 없음)

> **주의** Lambda가 결과를 **같은 버킷의 같은 접두사**에 다시 쓰면, 그 쓰기가 또 이벤트를 만들어 끝없이 돕니다. 결과는 다른 버킷이나 다른 접두사에 씁니다.

> **시험 포인트** "S3에 파일이 올라오면 자동으로 처리" → 이벤트 알림 → Lambda(또는 SQS를 거쳐 처리). "같은 이벤트를 여러 시스템이 받아야 함" → SNS 팬아웃이나 EventBridge. "객체 크기나 메타데이터로 거르기, 여러 대상, 재생" → EventBridge. "알림이 SQS에 오지 않음" → SQS 액세스 정책에서 S3 허용 여부 확인.

@practice
- **업로드 후처리**: 사용자가 이미지를 올리면 Lambda가 썸네일을 만들고, 동영상을 올리면 변환 작업을 시작하고, 정산 CSV가 올라오면 데이터 적재 파이프라인을 시작합니다.
- **안정적인 처리**: 처리할 파일이 많거나 실패하면 다시 해야 하는 일은 S3 → SQS → 작업 서버로 연결합니다. 대기열이 재시도와 DLQ를 맡아 주어 파일을 놓치지 않습니다.
- **EventBridge 연동**: 여러 팀이 같은 업로드 이벤트를 각자 받아야 하거나, "100MB 넘는 파일만"처럼 세밀하게 걸러야 할 때 EventBridge로 보냅니다.

@easy
이벤트 알림은 버킷에 일어난 일을 다른 서비스에 바로 알려 주는 설정입니다. 택배가 도착하면 문자가 오도록 설정해 두는 것과 같습니다. "`images/`에 `.jpg` 파일이 올라오면 이 함수에 알려 줘"처럼 조건과 받는 곳을 정해 둡니다.

받는 쪽이 알림을 받아도 된다고 허락해 두어야 합니다(리소스 정책). 결과 파일을 같은 위치에 다시 쓰면 그 쓰기가 또 알림을 만들어 끝없이 반복되므로, 결과는 다른 위치에 씁니다.

@topic c13-performance | S3 성능: 접두사, 멀티파트, 전송 가속, 바이트 범위 | dom=3 | prio=3 | les=S3 Performance
#### 기본 성능

S3는 요청이 늘면 자동으로 확장하며, 첫 바이트까지 지연은 보통 100–200ms입니다. 처리량은 **접두사(prefix)마다** 정해집니다.

| 요청 | 접두사당 초당 |
|---|---|
| PUT, COPY, POST, DELETE | 3,500 |
| GET, HEAD | 5,500 |

접두사 개수에는 제한이 없습니다. 객체를 `a/`, `b/`, `c/`, `d/` 네 접두사에 고르게 나누면 GET을 초당 22,000번까지 처리합니다.

#### 업로드를 빠르게

- **멀티파트 업로드**: 파일을 조각으로 나눠 **병렬로** 올립니다. **100MB 이상이면 권장**, **5GB를 넘으면 필수**입니다. 실패한 조각만 다시 올리면 되므로 불안정한 네트워크에도 강합니다. 끝나지 않은 조각은 수명 주기 규칙으로 지웁니다.
- **S3 전송 가속(Transfer Acceleration)**: 사용자는 가까운 **엣지 로케이션**으로 올리고, 엣지에서 버킷이 있는 리전까지는 **AWS 전용망**으로 옮깁니다. 멀리 떨어진 사용자가 큰 파일을 올릴 때 효과가 큽니다. 멀티파트와 함께 쓸 수 있고, 추가 요금이 있습니다.

#### 다운로드를 빠르게

- **바이트 범위 가져오기(Byte-range fetch)**: `Range` 헤더로 객체의 특정 바이트 구간만 받습니다. 여러 구간을 **병렬로** 받아 속도를 올리고, 실패한 구간만 다시 받습니다. 파일 앞부분(헤더)만 읽을 때도 씁니다.

> **바뀐 점** 강의에 나오는 **S3 Select**와 Glacier Select는 2024년 7월 25일부터 새 고객이 쓸 수 없습니다. S3 데이터를 SQL로 거르는 일은 Athena 등으로 합니다([22.1](#c22-athena)).

> **시험 포인트** "전 세계 사용자가 큰 파일을 한 버킷에 빠르게 업로드" → 전송 가속(+ 멀티파트). "5GB가 넘는 파일 업로드" → 멀티파트(필수). "GET 요청이 많아 503 Slow Down" → 접두사를 나눠 분산, 읽기가 많으면 CloudFront 캐시. "큰 객체의 일부만 빠르게 읽기" → 바이트 범위 가져오기.

> **후기에서** 2026년 2월 정리 노트의 키워드 목록에 "S3로 전 세계에서 빠르게 업로드 → S3 Transfer Acceleration"이 들어 있습니다.

@practice
- **대용량 업로드**: AWS CLI와 SDK는 일정 크기가 넘는 파일을 자동으로 멀티파트로 나눠 올립니다. 동영상 서비스처럼 브라우저에서 큰 파일을 올리는 경우에는 미리 서명된 URL을 조각마다 받아 병렬로 올립니다.
- **해외 업로드**: 해외 지사나 해외 고객이 서울 리전 버킷에 큰 파일을 올릴 때 전송 가속을 켜면 업로드 시간이 크게 줄어듭니다. 효과는 S3의 속도 비교 도구로 먼저 확인합니다.
- **요청이 아주 많은 버킷**: 초당 수만 건을 쓰는 로그 수집 서비스는 키 앞부분을 날짜나 해시로 나눠 여러 접두사에 요청을 분산합니다.
- **부분 읽기**: 동영상 플레이어는 바이트 범위 요청으로 필요한 구간만 받고, 대용량 파일 다운로드 도구는 여러 구간을 동시에 받아 속도를 냅니다.

@easy
S3의 처리 한도는 접두사(키 앞부분)마다 따로 있어서, 요청이 많으면 여러 접두사로 나눠 담는 것이 창구를 여러 개 여는 효과를 냅니다.

멀티파트 업로드는 큰 이삿짐을 여러 상자로 나눠 여러 사람이 동시에 나르는 방식입니다. 한 상자를 떨어뜨리면 그 상자만 다시 나르면 됩니다. 전송 가속은 멀리 있는 사용자가 가까운 엣지로 먼저 보내고, 거기서부터 AWS 전용망으로 버킷까지 옮기는 방식입니다.

@topic c13-ops | 요청자 지불, 배치 작업, Storage Lens | dom=3,4 | prio=2 | les=S3 Requester Pays; S3 Batch Operations; S3 Storage Lens
#### 요청자 지불(Requester Pays)

보통은 버킷 주인이 저장료와 **내려받는 요청·전송 비용**을 모두 냅니다. 요청자 지불을 켜면 저장료는 주인이, 요청과 전송 비용은 **내려받는 쪽**이 냅니다.

- 큰 데이터 세트를 다른 계정과 나눌 때 씁니다(예: 연구 데이터 공개).
- 요청자는 **인증된 AWS 계정**이어야 합니다. 익명 요청은 누구에게 청구할지 모르므로 받지 않습니다.

#### S3 배치 작업(Batch Operations)

이미 있는 객체 **수백만 개**에 같은 작업을 요청 한 번으로 실행합니다.

- **작업 종류**: 메타데이터·속성 바꾸기, 버킷 간 복사, **암호화되지 않은 객체 암호화**, ACL·태그 바꾸기, **Glacier에서 복원**, 객체마다 **Lambda 호출**(사용자 지정 작업)
- **작업(job)** = 객체 목록 + 할 일 + 옵션. 재시도, 진행 추적, 완료 알림, 보고서를 S3가 맡습니다.
- 객체 목록은 보통 **S3 Inventory** 보고서로 만들고, **Athena**로 걸러서(예: 암호화 안 된 객체만) 넘깁니다.
- 복제를 켜기 전부터 있던 객체를 복제하는 **Batch Replication**도 이 기능을 씁니다([12.4](#c12-versioning-replication)).

#### S3 Storage Lens

조직 전체의 S3 사용량과 활동을 한 화면에서 보는 분석 도구입니다. **AWS Organizations 전체, 계정, 리전, 버킷, 접두사** 단위로 모아 보고 이상한 점을 찾습니다.

- **기본 대시보드**가 미리 만들어져 있습니다(여러 리전·계정 데이터, 지울 수는 없고 끌 수는 있음). 직접 대시보드를 만들 수도 있습니다.
- 지표를 매일 CSV나 Parquet으로 S3 버킷에 내보낼 수 있습니다.
- 지표 분류: 요약(저장 용량, 객체 수), **비용 최적화**(이전 버전 용량, 끝나지 않은 멀티파트 용량), **데이터 보호**(버전 관리·MFA Delete·SSE-KMS·복제 규칙을 쓰는 버킷 수), 접근 관리, 이벤트, 성능, 활동(요청 수, 내려받은 양), 상태 코드.

| 구분 | 무료 지표 | 고급 지표와 추천(유료) |
|---|---|---|
| 데이터 보관 | **14일** | **15개월** |
| 내용 | 사용량 지표(버킷 단위) | 활동 지표, 접두사 단위 집계, 추천, CloudWatch 게시 |

> **시험 포인트** "다른 계정이 데이터를 내려받는 비용을 내게" → 요청자 지불. "버킷의 기존 객체 수백만 개를 한꺼번에 암호화·복사·태그 변경" → S3 배치 작업(+ S3 Inventory). "조직 전체 버킷 중 버전 관리나 암호화를 안 쓰는 곳 찾기, 비용 줄일 곳 찾기" → S3 Storage Lens.

@practice
- **요청자 지불**: 유전체 데이터나 위성 영상 같은 대용량 공개 데이터 세트를 제공하는 기관이, 내려받는 쪽이 전송 비용을 내도록 설정합니다.
- **배치 작업**: 수억 개 객체에 태그를 일괄로 붙이거나, 암호화 정책을 바꾼 뒤 예전 객체를 다시 암호화하거나, Glacier에 보관한 데이터를 한꺼번에 복원할 때 씁니다. 스크립트로 하나씩 처리하면 며칠 걸리는 일을 작업 하나로 맡깁니다.
- **Storage Lens**: 계정이 수십 개인 회사가 S3 비용 점검을 할 때 씁니다. "끝나지 않은 멀티파트 업로드가 많은 버킷", "이전 버전이 전체의 절반인 버킷", "암호화나 버전 관리를 안 쓰는 버킷"을 한 화면에서 찾습니다.

@easy
세 기능은 S3를 오래, 크게 쓸 때 필요한 관리 도구입니다. 요청자 지불은 "보관비는 우리가, 가져가는 택배비는 가져가는 쪽이" 내는 방식이고, 배치 작업은 창고 물건 수백만 개에 같은 작업을 한 번에 지시하는 기능이며, Storage Lens는 회사의 모든 버킷을 한눈에 보는 현황판입니다.

@quiz
Q: 로그를 30일 동안은 자주 읽고, 그 뒤 1년까지는 가끔 즉시 읽고, 1년이 지나면 지워야 합니다. 어떻게 설정하나요?
A: 수명 주기 규칙으로 30일 뒤 Standard-IA로 전환하고 365일 뒤 만료(삭제)합니다.
Q: 버전 관리 버킷의 비용이 계속 늘어납니다. 원인과 대책은?
A: 이전 버전이 쌓이기 때문입니다. 이전 버전에 전환·만료 수명 주기 규칙을 겁니다.
Q: S3 이벤트를 SQS FIFO 대기열로 보내야 합니다. 어떻게 하나요?
A: S3 이벤트 알림은 FIFO를 직접 대상으로 쓸 수 없으므로 EventBridge로 보내고, EventBridge 규칙의 대상으로 FIFO 대기열을 지정합니다.
Q: S3 이벤트 알림을 SQS로 설정했는데 메시지가 오지 않습니다. 무엇을 확인하나요?
A: SQS 대기열의 액세스 정책이 S3의 `sqs:SendMessage`를 허용하는지 확인합니다.
Q: 한 접두사에 GET 요청이 몰려 초당 5,500번을 넘습니다. 코드 변경을 최소로 하려면?
A: 객체를 여러 접두사에 나눠 저장합니다(접두사마다 GET 5,500/초). 같은 객체를 반복해서 읽는다면 CloudFront로 캐시합니다.
Q: 여러 대륙의 사용자가 수 GB 동영상을 한 버킷에 올리는데 느립니다. 무엇을 쓰나요?
A: S3 전송 가속과 멀티파트 업로드입니다.
Q: 기존 버킷의 암호화되지 않은 객체 수백만 개를 한꺼번에 암호화하려면?
A: S3 Inventory로 목록을 만들고(필요하면 Athena로 걸러) S3 배치 작업으로 암호화 복사를 실행합니다.
Q: 조직의 모든 계정에서 버전 관리를 쓰지 않는 버킷 수를 한 화면에서 보려면?
A: S3 Storage Lens 대시보드의 데이터 보호 지표를 봅니다.
