관계형 데이터베이스를 AWS가 운영해 주는 RDS와 Aurora, 그 앞에 두는 인메모리 캐시 ElastiCache를 배웁니다. 읽기 전용 복제본과 다중 AZ의 차이는 시험에서 가장 자주 묻는 비교 가운데 하나입니다.

@topic c09-rds | RDS 개요와 스토리지 자동 확장 | dom=2,3 | prio=3 | les=Amazon RDS Overview; Amazon RDS Hands On
**RDS(Relational Database Service)**는 SQL을 쓰는 관계형 DB를 AWS가 대신 운영해 주는 관리형 서비스입니다. 엔진은 PostgreSQL, MySQL, MariaDB, Oracle, Microsoft SQL Server, IBM Db2와 AWS의 Aurora([9.4](#c09-aurora))가 있습니다.

#### EC2에 직접 DB를 설치하는 것과 비교

RDS를 쓰면 다음을 AWS가 맡습니다.

- 설치와 프로비저닝, OS·DB 패치(정해 둔 유지 관리 기간에)
- 자동 백업과 특정 시점 복원([9.5](#c09-ops))
- 모니터링 대시보드
- 읽기 전용 복제본, 다중 AZ 장애 조치([9.2](#c09-replica))
- 인스턴스 크기 변경(수직 확장), 저장 공간 확장

대신 **DB 서버에 SSH로 들어갈 수 없습니다.** OS 수준 설정이 꼭 필요하면 RDS Custom([9.5](#c09-ops))이나 EC2를 씁니다.

#### 스토리지 자동 확장

DB 저장 공간이 거의 찼을 때 자동으로 늘리는 기능입니다. **최대 저장 공간 한도**를 정해 두면, 다음 조건을 모두 만족할 때 늘립니다.

- 남은 공간이 할당량의 10% 미만
- 그 상태가 5분 이상 지속
- 마지막 저장 공간 변경 후 6시간이 지남

언제 얼마나 커질지 예측하기 어려운 앱에 씁니다. 모든 RDS 엔진이 지원합니다.

> **시험 포인트** "DB 관리 부담 없이 MySQL을 쓰고 싶다" → RDS for MySQL. "DB OS에 직접 접근해 사용자 지정 패치를 해야 한다" → RDS Custom(Oracle, SQL Server) 또는 EC2. "저장 공간이 예측 없이 늘어 수동 확장이 번거롭다" → 스토리지 자동 확장.

@practice
- **서비스의 주 데이터 저장소**: 회원, 주문, 결제, 재고처럼 정확성과 트랜잭션이 필요한 데이터는 대부분 RDS의 PostgreSQL·MySQL에 둡니다. 쇼핑몰, 예약 서비스, 사내 ERP가 모두 이런 구조입니다.
- **DBA 일을 줄이기**: 작은 회사는 전담 DBA가 없는 경우가 많아, 백업·패치·장애 조치를 RDS에 맡기고 개발자가 스키마와 쿼리에만 집중합니다.
- **기존 상용 DB 이전**: 온프레미스의 Oracle·SQL Server를 라이선스 포함(License Included) 또는 기존 라이선스 그대로(BYOL) RDS로 옮깁니다.
- **스토리지 자동 확장**: 로그성 테이블이 빨리 커지는 서비스는 자동 확장과 최대 한도를 걸어 두어, 새벽에 디스크가 차서 서비스가 멈추는 사고를 막습니다.

@easy
RDS는 DB 서버를 통째로 위탁 관리받는 것입니다. 직접 운영하면 DB 설치, 보안 패치, 매일 백업, 장애 대비를 모두 사람이 해야 합니다. RDS는 이 일을 AWS가 하고, 우리는 테이블 설계와 쿼리만 신경 씁니다. 대신 서버 안으로 들어가 OS를 만지는 일은 할 수 없습니다. 관리형 오피스텔에 살면 관리실이 시설을 고쳐 주지만 벽을 허물 수는 없는 것과 비슷합니다.

@topic c09-replica | 읽기 전용 복제본과 다중 AZ | dom=2,3 | prio=3 | rev=1 | les=RDS Read Replicas vs Multi AZ
둘 다 DB 사본을 하나 더 두지만 **목적이 다릅니다.** 읽기 전용 복제본은 **읽기 성능(확장)**, 다중 AZ는 **장애 대비(가용성)**를 위한 것입니다.

| 비교 | 읽기 전용 복제본 | 다중 AZ(대기 인스턴스 1개) |
|---|---|---|
| 목적 | 읽기 부하 분산 | 자동 장애 조치 |
| 복제 방식 | **비동기**(약간 늦게 따라옴) | **동기**(손실 없음) |
| 사본에서 읽기 | 됨 | 안 됨(대기 전용) |
| 위치 | 같은 AZ, 다른 AZ, **다른 리전** | 같은 리전의 다른 AZ |
| 개수 | 최대 15개 | 대기 1개 |
| 접속 주소 | 복제본마다 별도 엔드포인트 → 앱이 읽기 연결을 나눠야 함 | 하나의 DNS 이름, 장애 시 자동 전환 |
| 승격 | 독립된 DB로 수동 승격 가능 | 자동 |

#### 읽기 전용 복제본

- 보고서, 분석, 대시보드처럼 **읽기만 하는 작업**을 복제본으로 보내 주 DB의 부하를 줄입니다. 복제본에서는 `SELECT`만 됩니다.
- 비동기라 **최종적 일관성**입니다. 방금 쓴 값을 복제본에서 바로 읽으면 옛 값이 나올 수 있습니다.
- 같은 리전 안의 다른 AZ로 복제할 때는 데이터 전송 요금이 없고, **다른 리전으로 복제하면 요금**이 있습니다.
- 복제본을 다른 리전에 두면 재해 복구용으로 쓸 수 있습니다(승격).

#### 다중 AZ

- 주 DB에 쓰면 다른 AZ의 대기 DB에도 **동기식**으로 써진 뒤에 완료됩니다.
- 주 DB의 AZ 장애, 인스턴스 장애, 스토리지 장애, 네트워크 장애가 나면 **DNS 이름이 대기 DB로 자동 전환**됩니다. 앱은 같은 주소로 다시 연결하면 됩니다.
- 단일 AZ에서 다중 AZ로 바꾸는 작업은 **중단 없이** 됩니다. 내부적으로 스냅샷을 찍어 다른 AZ에 대기 DB를 복원하고 동기 복제를 시작합니다.
- 읽기 전용 복제본 자체도 다중 AZ로 만들 수 있습니다.

**다중 AZ DB 클러스터**라는 다른 배포 방식도 있습니다. 쓰기 인스턴스 1개와 **읽을 수 있는** 대기 인스턴스 2개를 세 AZ에 두어, 장애 조치가 더 빠르고 대기에서 읽기도 됩니다(MySQL, PostgreSQL).

> **후기에서** 2026년 6월 합격 후기는 문제를 풀며 헷갈려 따로 정리한 개념에 *RDS Read Replica*를 넣었습니다. 문제의 말로 구분합니다. "보고서 쿼리가 주 DB를 느리게 한다" → 읽기 전용 복제본. "AZ 장애 때 자동으로 넘어가야 한다", "데이터 손실 없이" → 다중 AZ. "다른 리전에 재해 복구용 DB, 평소엔 읽기에 사용" → 리전 간 읽기 전용 복제본(또는 Aurora Global Database).

@practice
- **읽기 전용 복제본, 리포트 분리**: 매일 아침 영업팀이 돌리는 매출 리포트 쿼리가 주문 DB를 느리게 하면, 리포트와 BI 도구(Quick Sight, Tableau)를 복제본에 연결합니다.
- **읽기 전용 복제본, 읽기 분산**: 상품 목록·검색처럼 읽기가 쓰기보다 훨씬 많은 서비스는 앱에서 읽기 쿼리를 복제본 주소로 보냅니다. 방금 쓴 데이터를 바로 읽어야 하는 화면(주문 완료 화면)은 주 DB에서 읽습니다.
- **다중 AZ, 운영 DB의 기본값**: 운영 DB는 거의 모두 다중 AZ로 둡니다. 비용은 두 배 가까이 들지만, 하드웨어 장애나 AZ 장애 때 1–2분 안에 자동으로 넘어갑니다. 개발·테스트 DB는 단일 AZ로 비용을 아낍니다.
- **리전 간 복제본, 재해 복구**: 서울 리전의 주 DB를 도쿄 리전 복제본으로 복제해 두고, 서울 리전에 큰 장애가 나면 도쿄 복제본을 승격합니다.

@easy
읽기 전용 복제본은 원본 장부를 복사해 둔 **열람용 사본**입니다. 여러 사람이 사본을 보면 원본 담당자는 기록에만 집중할 수 있습니다. 다만 사본은 원본보다 조금 늦게 갱신되어, 방금 적은 내용이 사본에는 아직 없을 수 있습니다.

다중 AZ는 다른 건물에 둔 **실시간 백업 장부**입니다. 원본에 적을 때마다 똑같이 적어서 내용이 항상 같고, 원본 건물에 문제가 생기면 바로 그 장부로 일을 이어 갑니다. 평소에는 아무도 그 장부를 보지 않습니다. 하나는 성능, 하나는 장애 대비를 위한 것이라는 점이 다릅니다.

@topic c09-aurora | Aurora 구조와 엔드포인트 | dom=2,3 | prio=3 | les=Amazon Aurora; Amazon Aurora - Hands On
**Aurora**는 AWS가 클라우드에 맞게 새로 만든 관계형 DB입니다. MySQL·PostgreSQL과 호환되어 같은 드라이버로 접속하고, 저장 계층을 따로 떼어 여러 AZ에 나눠 저장합니다.

#### 특징

- 같은 하드웨어에서 MySQL보다 최대 5배, PostgreSQL보다 최대 3배 빠르다고 AWS가 밝힙니다.
- 저장 공간은 10GB 단위로 **자동으로 늘어** 최대 128TiB까지 갑니다(최신 엔진 버전 일부는 256TiB).
- 읽기 복제본 **최대 15개**, 복제 지연은 보통 10ms 미만입니다.
- 장애 조치가 매우 빠르고(보통 30초 미만) 클라우드 네이티브라 기본으로 고가용성입니다.
- RDS보다 약 20% 비싸지만 효율이 높아 전체 비용은 비슷하거나 낮을 수 있습니다.

#### 저장 계층: 3개 AZ에 6벌

1. 데이터를 **3개 AZ에 6벌** 저장합니다.
2. 쓰기는 6벌 중 **4벌**에 기록되면 완료, 읽기는 **3벌**에서 맞으면 됩니다.
3. 깨진 블록은 다른 사본으로 스스로 고칩니다(self-healing).
4. 저장 공간은 수백 개의 볼륨에 나뉘어 있습니다.

그래서 AZ 하나가 통째로 사라져도(2벌 잃음) 쓰기와 읽기가 계속됩니다.

#### 클러스터와 엔드포인트

Aurora DB 클러스터에는 쓰기를 맡는 **주 인스턴스 1개**와 읽기를 맡는 **복제본 여러 개**가 있고, 모두 같은 저장 계층을 씁니다. 주 인스턴스가 고장 나면 복제본 중 하나가 승격됩니다.

| 엔드포인트 | 가리키는 곳 |
|---|---|
| 쓰기(클러스터) 엔드포인트 | 항상 현재 주 인스턴스. 장애 조치 후에도 그대로 |
| 읽기 엔드포인트 | 복제본들에 **연결 단위로** 부하 분산 |
| 사용자 지정 엔드포인트 | 내가 고른 복제본 묶음(예: 큰 인스턴스만 분석용, [9.4](#c09-aurora-adv)) |

> **시험 포인트** "MySQL 호환이면서 고가용성과 읽기 확장이 뛰어나고 저장 공간 관리가 필요 없는 DB" → Aurora. "AZ 하나를 잃어도 데이터 손실 없이" → Aurora는 3개 AZ에 6벌 저장. 앱은 쓰기에 쓰기 엔드포인트, 읽기에 읽기 엔드포인트를 씁니다.

@practice
- **읽기가 많은 대규모 서비스**: 트래픽이 큰 커머스·핀테크 서비스가 MySQL·PostgreSQL에서 Aurora로 옮기는 흔한 이유는 복제본을 15개까지 빠르게 붙일 수 있고, 저장 공간 관리가 필요 없기 때문입니다.
- **엔드포인트 나눠 쓰기**: 앱 설정에 쓰기 엔드포인트와 읽기 엔드포인트를 따로 넣고, 조회 API는 읽기 엔드포인트로 보냅니다. 장애 조치가 일어나도 엔드포인트 주소는 바뀌지 않습니다.
- **빠른 장애 조치**: 주 인스턴스 장애 때 보통 30초 안에 복제본이 승격돼, 결제처럼 멈추면 안 되는 서비스에 맞습니다.
- **고려할 점**: RDS보다 인스턴스 단가가 높고 I/O 요금이 있어(I/O-Optimized 구성을 고르면 I/O 요금 없음), 작고 한가한 DB는 RDS가 더 쌀 수 있습니다.

@easy
일반 DB는 서버 한 대가 자기 디스크에 데이터를 저장합니다. Aurora는 데이터를 저장하는 부분을 서버에서 떼어내 세 건물(AZ)에 여섯 벌로 나눠 둡니다. 서버(인스턴스)는 계산만 하고, 여러 서버가 같은 저장소를 함께 봅니다. 그래서 읽기 서버를 붙이는 데 데이터를 복사할 필요가 없어 빠르고, 한 건물이 통째로 사라져도 데이터가 남습니다.

엔드포인트는 대표 전화번호와 같습니다. 쓰기 번호로 걸면 늘 현재 책임자에게, 읽기 번호로 걸면 열람 담당자 중 한 명에게 연결됩니다. 책임자가 바뀌어도 번호는 그대로입니다.

@topic c09-aurora-adv | Aurora 고급: 자동 확장, Serverless, Global Database | dom=2,3,4 | prio=3 | les=Amazon Aurora - Advanced Concepts
Aurora에는 부하와 지역에 맞춰 늘리는 기능이 여럿 있습니다.

#### 복제본 자동 확장(Replica Auto Scaling)

읽기가 몰려 복제본의 CPU나 연결 수가 기준을 넘으면 **복제본을 자동으로 추가**합니다. 읽기 엔드포인트가 새 복제본까지 포함하므로 앱은 바꿀 것이 없습니다.

#### 사용자 지정 엔드포인트

일부 복제본만 묶은 엔드포인트입니다. 예를 들어 `db.r6g.4xlarge` 같은 큰 복제본 두 개를 분석 쿼리 전용으로 묶어, 일반 읽기와 섞이지 않게 합니다. 사용자 지정 엔드포인트를 쓰면 보통 기본 읽기 엔드포인트는 쓰지 않습니다.

#### Aurora Serverless v2

인스턴스 크기를 고르지 않고, 부하에 따라 **용량(ACU 단위)이 초 단위로 자동으로** 늘고 줄어드는 Aurora입니다. 간헐적이거나 예측할 수 없는 부하에 맞습니다. 최소 용량을 0으로 두면 쓰지 않을 때 자동으로 멈춰 요금을 아낍니다(2024-11 추가). 옛 Serverless v1은 2025년 3월에 지원이 끝났습니다.

#### Aurora Global Database

- 한 **주 리전**에서 읽고 쓰고, **최대 10개의 보조 리전**에 복제합니다(2025-05에 5개에서 늘어남). 보조 리전마다 읽기 복제본을 둘 수 있습니다.
- 리전 간 복제 지연은 보통 **1초 미만**입니다.
- 주 리전에 재해가 나면 보조 리전을 승격합니다. RTO는 보통 1분 안팎입니다.
- 여러 리전 사용자에게 가까운 곳에서 읽기를 제공하는 용도로도 씁니다.

|---|---|
| Aurora 머신러닝 | SQL로 SageMaker AI·Comprehend 모델을 불러 예측(사기 탐지, 감정 분석, 추천)을 받음 |
| Babelfish for Aurora PostgreSQL | SQL Server 앱의 T-SQL을 거의 고치지 않고 Aurora PostgreSQL로 옮김 |

> **시험 포인트** "부하가 들쭉날쭉하고 예측할 수 없는 관계형 DB, 운영 최소" → Aurora Serverless v2. "리전 장애에 대비해 1분 안팎의 RTO와 1초 안팎의 RPO, 다른 리전에서 읽기 지연도 낮게" → Aurora Global Database. "SQL Server 앱을 코드 변경 최소로 PostgreSQL 계열로" → Babelfish.

@practice
- **복제본 자동 확장**: 저녁 시간에만 조회가 몰리는 서비스는 복제본 자동 확장으로 피크 때만 복제본을 늘립니다.
- **사용자 지정 엔드포인트**: 무거운 분석 쿼리가 일반 사용자 조회를 느리게 하지 않도록, 큰 복제본 두 대를 분석 전용 엔드포인트로 묶어 BI 도구만 연결합니다.
- **Serverless v2**: 사용량이 들쭉날쭉한 신규 서비스, 개발·테스트 DB, 고객사마다 DB를 하나씩 두는 SaaS에 맞습니다. 밤에는 용량이 거의 0까지 줄어 요금이 적게 나옵니다.
- **Global Database**: 해외 사용자가 많은 게임·핀테크 서비스는 서울을 주 리전으로, 미국·유럽 리전을 보조 리전으로 두어 그 지역 사용자의 조회를 가까운 곳에서 처리하고 재해 복구에도 대비합니다.

@easy
네 기능은 모두 "부하나 지역이 바뀔 때 손을 덜 대는" 방법입니다.

- **복제본 자동 확장**: 열람 창구에 손님이 몰리면 창구를 저절로 더 엽니다.
- **사용자 지정 엔드포인트**: 대량 자료를 뽑아 가는 손님용 창구를 따로 둬서 일반 손님이 기다리지 않게 합니다.
- **Serverless v2**: 창구 직원 수를 미리 정하지 않고 손님 수에 맞춰 초 단위로 늘리고 줄입니다. 손님이 없으면 문을 닫아 둘 수도 있습니다.
- **Global Database**: 다른 나라에 지점을 두고 본점 장부를 1초 안에 따라 적게 합니다. 본점에 문제가 생기면 지점이 본점 역할을 맡습니다.

@topic c09-ops | RDS·Aurora 백업, 복원, 보안, RDS Custom | dom=1,2 | prio=3 | les=RDS Custom for Oracle and Microsoft SQL Server; RDS & Aurora - Backup and Monitoring; RDS  Security
#### 백업

| 종류 | RDS | Aurora |
|---|---|---|
| 자동 백업 | 매일 전체 백업 + 5분마다 트랜잭션 로그. 보존 1–35일(0이면 끔) | 보존 1–35일, **끌 수 없음** |
| 특정 시점 복원(PITR) | 보존 기간 안의 아무 시점(최근 약 5분 전까지) | 보존 기간 안의 아무 시점 |
| 수동 스냅샷 | 직접 찍고, 지울 때까지 보관 | 같음 |

복원하면 **항상 새 DB**가 만들어집니다. 원래 DB를 덮어쓰지 않습니다.

> **팁** 한 달에 몇 시간만 쓰는 RDS를 멈춰 두면 저장 공간 요금은 계속 나갑니다(멈춘 RDS는 7일 뒤 자동으로 다시 켜지기도 합니다). 오래 안 쓸 거면 스냅샷을 찍고 DB를 지운 뒤, 필요할 때 스냅샷에서 복원하는 편이 쌉니다.

#### 그 밖의 복원·복제 방법

- **S3에서 복원**: 온프레미스 MySQL 백업(Percona XtraBackup)을 S3에 올려 RDS for MySQL이나 Aurora MySQL 클러스터로 복원합니다.
- **Aurora 클론**: 기존 클러스터의 **새 클러스터를 빠르게 복제**합니다. 처음에는 같은 저장 공간을 공유하다가 바뀐 부분만 새로 씁니다(copy-on-write). 운영 DB로 스테이징 환경을 만들 때 스냅샷 복원보다 빠르고 쌉니다.

#### 보안

- **저장 시 암호화**: KMS로 DB를 **만들 때** 켭니다. 주 DB가 암호화되지 않았으면 복제본도 암호화할 수 없습니다. 이미 만든 암호화되지 않은 DB는 스냅샷 → 암호화 복사 → 복원으로 바꿉니다.
- **전송 중 암호화**: TLS로 접속합니다.
- **IAM 데이터베이스 인증**: MySQL, PostgreSQL, MariaDB에서 비밀번호 대신 IAM 역할로 받은 인증 토큰으로 접속합니다.
- **네트워크**: 보안 그룹으로 앱 서버에서 오는 DB 포트만 엽니다. 보통 프라이빗 서브넷에 둡니다.
- **감사 로그**: DB 로그를 CloudWatch Logs로 보내 오래 보관합니다.
- SSH 접근은 없습니다(RDS Custom 제외).

#### RDS Custom

**Oracle과 SQL Server**에서 OS와 DB 설정에 직접 접근해야 할 때 쓰는 RDS입니다. RDS의 자동화(백업, 패치)는 그대로 쓰면서, SSH나 Session Manager로 들어가 사용자 지정 패치·설정·서드파티 에이전트를 설치합니다. 손대기 전에는 **자동화 모드를 잠시 끄고** 스냅샷을 찍어 둡니다.

| 선택지 | 관리 범위 |
|---|---|
| RDS | DB와 OS 모두 AWS가 관리 |
| RDS Custom | AWS 관리 + OS·DB에 직접 접근(Oracle, SQL Server) |
| EC2에 직접 설치 | 모두 직접 |

> **시험 포인트** "운영 DB와 같은 데이터로 테스트 환경을 빨리 만들고 싶다(운영에 영향 없이)" → Aurora 클론. "암호화되지 않은 RDS를 암호화" → 스냅샷 → 암호화 복사 → 복원. "비밀번호 없이 IAM으로 DB 인증" → IAM DB 인증. "Oracle DB의 OS에 서드파티 모니터링 에이전트를 설치" → RDS Custom.

@practice
- **백업과 복구 훈련**: 자동 백업 보존 기간을 7–35일로 두고, 분기마다 특정 시점 복원으로 새 DB를 만들어 실제로 복구되는지 확인하는 회사가 많습니다. 복원은 항상 새 DB로 만들어지므로 앱의 접속 주소를 바꾸는 절차까지 연습합니다.
- **실수 복구**: 개발자가 운영 DB에서 `WHERE` 없이 `UPDATE`를 실행했다면, 실행 직전 시각으로 특정 시점 복원을 해 새 DB를 만들고 필요한 데이터를 옮겨 옵니다.
- **Aurora 클론으로 스테이징**: 운영 데이터와 같은 상태에서 대규모 마이그레이션 스크립트를 미리 돌려 보려고 클론을 만들고, 테스트가 끝나면 지웁니다.
- **보안 점검 항목**: 저장 시 암호화, TLS 강제, 프라이빗 서브넷 배치, 앱 서버 보안 그룹만 허용이 기본입니다. 비밀번호는 Secrets Manager에서 자동으로 교체합니다.
- **RDS Custom**: 특정 보안 에이전트나 사용자 지정 패치를 OS에 설치해야 하는 Oracle 기반 레거시 시스템을 옮길 때 고릅니다.

@easy
자동 백업은 매일 찍는 전체 사진과 5분마다 남기는 변경 일지입니다. 둘을 합치면 보존 기간 안의 아무 시점으로나 되돌릴 수 있습니다. 다만 원래 DB를 되돌리는 것이 아니라, 그 시점의 모습으로 **새 DB를 하나 더** 만듭니다.

Aurora 클론은 같은 책을 복사하지 않고 "고친 쪽만 따로 적는" 방식으로 사본을 만드는 것입니다. 처음에는 원본을 함께 보다가, 사본에서 바꾼 부분만 새로 저장하므로 빠르고 쌉니다.

RDS Custom은 위탁 관리 계약은 유지하면서 관리실 열쇠를 잠깐 빌려 직접 손보는 방식입니다.

@topic c09-proxy | RDS Proxy | dom=2,3 | prio=3 | les=RDS Proxy
**RDS Proxy**는 앱과 DB 사이에서 **DB 연결을 모아 두고 나눠 쓰게(풀링)** 하는 완전 관리형 프록시입니다.

#### 왜 필요한가

DB는 연결 하나마다 메모리와 CPU를 씁니다. **Lambda**처럼 순식간에 수백 개로 늘어나는 앱이 각자 DB 연결을 열면, DB가 연결 수 한도에 걸리거나 연결을 맺고 끊느라 느려집니다. RDS Proxy는 앱의 연결을 받아 **적은 수의 DB 연결을 재사용**합니다.

#### 특징

- 서버리스이고 자동으로 확장되며, 여러 AZ에 걸쳐 고가용성입니다.
- **장애 조치 시간을 최대 66% 줄입니다.** 앱은 프록시에 연결돼 있고, 프록시가 새 주 DB로 연결을 옮깁니다.
- RDS(MySQL, PostgreSQL, MariaDB, SQL Server)와 Aurora(MySQL, PostgreSQL)를 지원합니다.
- 대부분 **코드 변경 없이** 접속 주소만 프록시 엔드포인트로 바꾸면 됩니다.
- **IAM 인증을 강제**하고, DB 자격 증명은 **Secrets Manager**에 둡니다.
- **VPC 안에서만** 접근할 수 있고 인터넷에 공개할 수 없습니다.

> **시험 포인트** "Lambda 함수가 RDS에 너무 많은 연결을 열어 'too many connections' 오류가 난다" → RDS Proxy. "장애 조치 때 앱의 재연결 시간을 줄이고 싶다" → RDS Proxy. "DB 자격 증명을 코드에 두지 않고 IAM으로 접속" → RDS Proxy + IAM 인증 + Secrets Manager.

@practice
- **Lambda와 RDS**: 이벤트가 몰리면 Lambda가 수백 개로 늘어나며 각자 DB 연결을 열어 "too many connections" 오류가 납니다. RDS Proxy를 두면 Lambda 수천 개가 소수의 DB 연결을 나눠 씁니다.
- **장애 조치 시간 줄이기**: 다중 AZ 장애 조치 중 앱이 새 주소를 찾느라 생기는 끊김이 줄어서, 결제 API처럼 짧은 끊김도 문제가 되는 서비스에 씁니다.
- **자격 증명 관리**: DB 비밀번호는 Secrets Manager에 두고, 앱은 IAM 인증으로 프록시에 붙습니다. 비밀번호를 바꿔도 앱 설정을 고칠 필요가 없습니다.

@easy
DB는 동시에 받을 수 있는 연결 수가 정해져 있습니다. 앱이 요청마다 새로 연결하고 끊으면, 전화를 걸 때마다 교환원을 새로 부르는 것처럼 DB가 연결 처리에만 힘을 씁니다.

RDS Proxy는 콜센터의 교환원입니다. 수많은 고객 전화(앱 연결)를 받아, 미리 열어 둔 몇 개의 내선(DB 연결)으로 돌려 연결합니다. DB는 적은 연결만 상대하면 되고, 주 DB가 바뀌어도 교환원이 새 내선으로 바로 이어 줍니다.

@topic c09-elasticache | ElastiCache와 캐시 전략 | dom=3,4 | prio=3 | les=ElastiCache Overview; ElastiCache Hands On; ElastiCache for Solution Architects; List of Ports to be familiar with
**ElastiCache**는 Valkey, Redis OSS, Memcached를 관리형으로 제공하는 **인메모리 캐시**입니다. 메모리에서 읽으므로 응답이 1밀리초 안팎이고, DB 앞에 두어 반복 읽기를 대신 받습니다.

#### 언제 쓰나

- **읽기가 많은 DB의 부하 줄이기**: 같은 상품 정보, 같은 순위표를 매번 DB에서 읽지 않습니다.
- **세션 저장소**: 로그인 세션을 캐시에 두어 웹 서버를 무상태로 만듭니다.
- 캐시를 쓰려면 **앱 코드가 캐시를 먼저 보도록 바뀌어야** 합니다. 자동으로 끼워 넣는 기능이 아닙니다.

#### 엔진 고르기

| 비교 | Valkey · Redis OSS | Memcached |
|---|---|---|
| 고가용성 | 다중 AZ 자동 장애 조치, 읽기 복제본 | 없음(노드가 죽으면 그 데이터 손실) |
| 영속성 | AOF, 백업·복원 | 없음(서버리스만 백업) |
| 데이터 구조 | 문자열, 리스트, 셋, **정렬된 셋**(순위표) 등 | 단순 키-값 |
| 확장 | 샤딩(클러스터 모드) | 여러 노드에 샤딩, 멀티스레드 |

Valkey는 Redis OSS에서 갈라져 나온 오픈 소스로, ElastiCache에서 더 싸게 제공됩니다. 용량을 고르지 않는 **ElastiCache Serverless**도 있습니다.

#### 캐시 전략

| 전략 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 지연 로딩(lazy loading, cache-aside) | 캐시에서 찾고, 없으면(miss) DB에서 읽어 캐시에 넣음 | 실제로 읽는 데이터만 캐시. 캐시가 죽어도 동작 | 처음 읽기는 느림(3번 왕복). 옛 데이터가 남을 수 있음 |
| 라이트 스루(write-through) | DB에 쓸 때 캐시에도 씀 | 캐시가 늘 최신 | 쓰기마다 2번. 안 읽을 데이터도 캐시에 쌓임 |
| TTL(만료 시간) | 일정 시간이 지나면 캐시 항목을 지움 | 옛 데이터 문제를 줄임 | 너무 짧으면 캐시 효과가 떨어짐 |

캐시가 꽉 차면 오래 안 쓴 항목부터 지웁니다(LRU 축출). 축출이 잦으면 노드를 키우거나 늘립니다.

#### 캐시 보안

- Valkey·Redis OSS: IAM 인증, Redis AUTH(비밀번호·토큰), 전송 중 TLS 암호화
- Memcached: SASL 인증
- 보안 그룹으로 앱 서버에서 오는 포트만 엽니다.

#### 외워 둘 DB 포트

| 포트 | DB |
|---|---|
| 3306 | MySQL, MariaDB, Aurora MySQL |
| 5432 | PostgreSQL, Aurora PostgreSQL |
| 1521 | Oracle(RDS) |
| 1433 | Microsoft SQL Server |
| 6379 / 11211 | Redis OSS·Valkey / Memcached |

> **시험 포인트** "같은 쿼리가 반복돼 RDS 읽기 부하가 높다, 가장 적은 변경으로" → 앞에 ElastiCache(또는 읽기 전용 복제본). "게임 순위표" → Redis·Valkey 정렬된 셋. "세션을 외부에 두어 서버를 무상태로" → ElastiCache 또는 DynamoDB. "고가용성·백업이 필요한 캐시" → Memcached가 아니라 Valkey·Redis OSS.

@practice
- **DB 앞 캐시**: 상품 상세, 카테고리 목록, 환율처럼 자주 읽고 가끔 바뀌는 데이터를 Redis에 몇 분~몇 시간 TTL로 저장합니다. 같은 요청이 DB까지 가지 않아 DB 비용이 줄고 응답이 빨라집니다.
- **세션 저장소**: 여러 웹 서버가 로그인 세션을 Redis에 두고 공유합니다. 서버가 늘고 줄어도 사용자가 다시 로그인할 필요가 없습니다.
- **순위표와 카운터**: 게임 순위, 실시간 인기 검색어, 좋아요 수를 Redis의 정렬된 셋과 증가 명령으로 처리합니다.
- **요청 제한**: API 호출 횟수를 사용자별로 세어 1분에 100번 같은 한도를 거는 데 씁니다.
- **고를 때**: 데이터가 사라지면 곤란하거나 장애 조치가 필요하면 Valkey·Redis OSS, 단순 캐시를 여러 스레드로 빠르게 처리하면 Memcached입니다. 요즘은 대부분 Valkey나 Redis를 고릅니다.

@easy
캐시는 자주 찾는 자료를 책상 위에 꺼내 두는 것입니다. 문서고(DB)까지 가면 오래 걸리니, 자주 보는 서류는 복사해서 책상에 둡니다. 대신 책상 위 복사본은 원본이 바뀌어도 자동으로 바뀌지 않아서, 언제 버리고 새로 가져올지(TTL) 정해 둡니다.

지연 로딩은 필요할 때 처음 한 번 문서고에 다녀와서 복사해 두는 방식이고, 라이트 스루는 원본을 고칠 때 책상 위 복사본도 함께 고치는 방식입니다.

@quiz
Q: 주 DB가 장애 나면 자동으로 넘어가고 데이터 손실이 없어야 합니다. 읽기 전용 복제본과 다중 AZ 중 무엇인가요?
A: 다중 AZ입니다. 동기 복제와 DNS 자동 전환을 합니다.
Q: 분석 팀의 보고서 쿼리가 운영 RDS를 느리게 합니다. 가장 알맞은 조치는?
A: 읽기 전용 복제본을 만들고 보고서 쿼리를 복제본으로 보냅니다.
Q: 같은 리전의 다른 AZ에 RDS 읽기 전용 복제본을 둘 때 복제 데이터 전송 요금이 있나요?
A: 없습니다. 다른 리전으로 복제할 때 요금이 생깁니다.
Q: Aurora는 데이터를 몇 개 AZ에 몇 벌 저장하고, 쓰기는 몇 벌에 기록되면 완료되나요?
A: 3개 AZ에 6벌을 저장하고, 쓰기는 6벌 중 4벌에 기록되면 완료됩니다.
Q: 예측할 수 없이 들쭉날쭉한 부하의 관계형 DB를 용량 관리 없이 운영하려면?
A: Aurora Serverless v2입니다.
Q: 리전 장애에 대비해 1초 안팎의 RPO와 1분 안팎의 RTO가 필요한 관계형 DB는?
A: Aurora Global Database입니다.
Q: 운영 Aurora 클러스터와 같은 데이터로 스테이징 DB를 빠르고 싸게 만들려면?
A: Aurora 클론(copy-on-write)을 씁니다.
Q: 수천 개의 Lambda 동시 실행이 RDS 연결 수 한도를 넘깁니다. 해결책은?
A: RDS Proxy로 연결을 풀링합니다.
Q: 캐시가 늘 DB와 같은 최신 값을 갖게 하려면 어떤 캐시 전략인가요?
A: 라이트 스루입니다. 대신 읽지 않을 데이터도 캐시에 쌓이므로 TTL과 함께 씁니다.
Q: PostgreSQL과 SQL Server의 기본 포트는?
A: PostgreSQL 5432, SQL Server 1433입니다.
