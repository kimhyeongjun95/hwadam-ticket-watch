EC2에 붙이는 저장소 세 가지(EBS, 인스턴스 스토어, EFS)와 백업·복제의 단위(스냅샷, AMI)를 배웁니다. "어느 AZ에 묶이나", "인스턴스를 꺼도 남나", "여러 대가 같이 쓸 수 있나" 세 질문으로 구분하면 대부분의 문제가 풀립니다.

@topic c07-ebs | EBS 볼륨, 다중 연결, 암호화 | dom=1,3 | prio=3 | les=EBS Overview; EBS Hands On; EBS Multi-Attach; EBS Encryption; EBS & EFS - Section Cleanup
**EBS(Elastic Block Store) 볼륨**은 EC2에 붙이는 **네트워크 블록 스토리지**, 즉 가상 디스크입니다. OS가 포맷해서 쓰고, 인스턴스를 멈추거나 종료해도 데이터가 남을 수 있습니다.

#### EBS의 성질

- **한 AZ에 묶여** 있습니다. `ap-northeast-2a`의 볼륨은 `2b`의 인스턴스에 붙일 수 없습니다. 다른 AZ로 옮기려면 스냅샷을 찍어 그 AZ에서 새 볼륨을 만듭니다([7.2](#c07-snapshot-ami)).
- 네트워크로 붙으므로 약간의 지연이 있고, 인스턴스에서 떼어 다른 인스턴스(같은 AZ)에 붙일 수 있습니다.
- 보통 **한 번에 인스턴스 하나**에만 붙습니다. 인스턴스 하나에는 볼륨 여러 개를 붙일 수 있습니다.
- 크기(GB)와 성능(IOPS, 처리량)을 미리 정하고, 정한 만큼 요금을 냅니다. 나중에 늘릴 수 있습니다.

#### 종료 시 삭제(Delete on Termination)

인스턴스를 종료할 때 볼륨을 같이 지울지 정하는 속성입니다. 기본값은 **루트 볼륨은 삭제, 나중에 붙인 볼륨은 유지**입니다. 루트 볼륨의 데이터를 남기려면 이 속성을 끕니다.

#### 다중 연결(Multi-Attach)

**io1·io2** 볼륨 하나를 **같은 AZ**의 Nitro 인스턴스 **최대 16대**에 동시에 붙이는 기능입니다. 모든 인스턴스가 읽고 쓸 수 있으므로, 동시 쓰기를 조율하는 **클러스터 인식 파일 시스템**이 필요합니다(XFS, EXT4 같은 일반 파일 시스템은 안 됨). 클러스터형 리눅스 앱의 고가용성에 씁니다.

#### EBS 암호화

볼륨을 암호화하면 다음이 모두 암호화되고, 성능 영향은 거의 없습니다.

- 볼륨에 저장된 데이터
- 인스턴스와 볼륨 사이를 오가는 데이터
- 그 볼륨의 모든 스냅샷과, 스냅샷에서 만든 볼륨

KMS 키(AES-256)로 암호화하고, 리전 단위로 **기본 암호화**를 켜 두면 새 볼륨이 모두 암호화됩니다. 이미 만든 **암호화되지 않은 볼륨은 바로 암호화할 수 없습니다.** 순서는 이렇습니다.

1. 볼륨의 스냅샷을 찍습니다.
2. 스냅샷을 **복사하면서 암호화**를 켭니다.
3. 암호화된 스냅샷으로 새 볼륨을 만듭니다(새 볼륨도 암호화됨).
4. 원래 인스턴스에 새 볼륨을 붙입니다.

> **시험 포인트** "EBS 볼륨을 다른 AZ로 옮겨라" → 스냅샷 후 복원. "암호화되지 않은 볼륨을 암호화하라" → 스냅샷 → 암호화 복사 → 새 볼륨. "여러 EC2가 같은 블록 볼륨에 동시에 써야 한다(같은 AZ)" → io2 다중 연결. AZ를 넘어 여러 인스턴스가 파일을 같이 써야 하면 EBS가 아니라 EFS입니다([7.5](#c07-efs)).

@practice
- **루트와 데이터 볼륨 나누기**: EC2 대부분은 OS가 든 루트 볼륨(gp3) 하나를 쓰고, 데이터가 많은 서버는 데이터 볼륨을 따로 붙입니다. 서버를 바꿀 때 데이터 볼륨만 떼어 새 서버에 붙이면 됩니다.
- **EC2에 직접 설치한 DB**: RDS가 지원하지 않는 버전이나 설정 때문에 EC2에 DB를 직접 설치하면 데이터는 EBS에 둡니다. 지연에 민감하면 io2를 씁니다.
- **기본 암호화**: 보안 점검에서 저장 데이터 암호화를 요구하므로, 리전마다 EBS 기본 암호화를 켜 두는 회사가 많습니다. 켜 두면 새 볼륨이 모두 자동으로 암호화됩니다.
- **다중 연결**: Windows Server 장애 조치 클러스터나 GFS2 같은 클러스터 파일 시스템처럼, 여러 서버가 같은 디스크를 함께 봐야 하는 소프트웨어에 씁니다. 흔한 구성은 아닙니다.
- **정리 누락**: 인스턴스를 지워도 남은 데이터 볼륨은 매달 요금이 나갑니다. 비용 점검에서 "어디에도 붙지 않은 EBS 볼륨"을 찾아 지우는 일이 자주 나옵니다.

@easy
EBS는 서버에 연결하는 외장 SSD입니다. 다만 USB가 아니라 같은 데이터 센터(AZ) 안의 네트워크로 연결됩니다. 그래서 같은 AZ의 다른 서버에는 옮겨 붙일 수 있지만, 다른 AZ로는 바로 옮기지 못하고 스냅샷을 찍어 그곳에서 새로 만들어야 합니다.

암호화되지 않은 디스크를 암호화하는 방법도 같은 원리입니다. 이미 쓰고 있는 디스크에 바로 암호화를 걸 수 없으니, 복사본을 만들면서 암호화하고 그 복사본으로 바꿉니다.

#### EBS 스냅샷

**스냅샷**은 EBS 볼륨의 특정 시점 백업입니다. 처음 한 번은 전체를, 그다음부터는 **바뀐 블록만** 저장합니다(증분). 볼륨을 떼지 않아도 찍을 수 있지만, 일관성을 위해 쓰기를 멈추고 찍기를 권합니다.

- 스냅샷으로 **다른 AZ나 다른 리전**에 새 볼륨을 만들 수 있습니다. 리전을 넘을 때는 스냅샷을 그 리전으로 복사합니다.
- **스냅샷 아카이브(Archive tier)**: 거의 꺼내지 않는 스냅샷을 최대 75% 싸게 보관합니다. 되살리는 데 24–72시간이 걸립니다.
- **휴지통(Recycle Bin)**: 실수로 지운 스냅샷·AMI를 정해 둔 기간(1일–1년) 동안 되살릴 수 있게 보관합니다.
- **빠른 스냅샷 복원(FSR)**: 스냅샷에서 만든 볼륨은 처음 읽을 때 느릴 수 있습니다. FSR은 볼륨을 미리 완전히 초기화해 첫 읽기부터 최대 성능을 냅니다. 비쌉니다.
- 스냅샷 일정 관리는 **Data Lifecycle Manager**나 **AWS Backup**으로 자동화합니다([28.5](#c28-backup)).

#### AMI(Amazon Machine Image)

**AMI**는 EC2를 시작하는 틀입니다. OS, 설치한 소프트웨어, 설정, 붙일 EBS 볼륨의 스냅샷이 들어 있습니다. 내가 만든 AMI로 띄우면 설치가 끝난 상태로 시작하므로 **부팅과 확장이 빨라집니다.**

| 종류 | 설명 |
|---|---|
| 공개 AMI | AWS가 제공(Amazon Linux 등) |
| 내 AMI | 내가 만들고 관리 |
| AWS Marketplace AMI | 다른 회사가 만들어 파는 AMI |

AMI 만드는 순서는 다음과 같습니다.

1. 인스턴스를 띄워 소프트웨어를 설치하고 설정합니다.
2. 데이터 무결성을 위해 인스턴스를 멈춥니다.
3. AMI를 만듭니다. 이때 EBS 스냅샷이 함께 만들어집니다.
4. 그 AMI로 새 인스턴스를 띄웁니다.

AMI는 **리전 단위**입니다. 다른 리전에서 쓰려면 AMI를 그 리전으로 **복사**합니다. 다른 계정과 공유할 수도 있습니다(암호화된 AMI 공유는 KMS 키 권한까지 필요, [26.3](#c26-kms-mr)).

> **시험 포인트** "다른 리전에 같은 서버를 빠르게 띄워 재해 복구" → AMI를 대상 리전으로 복사. "새 인스턴스가 설치 없이 바로 서비스해야 한다" → 미리 구운 골든 AMI. "스냅샷을 오래 보관하되 비용을 줄인다" → 스냅샷 아카이브. "실수로 지운 스냅샷을 되살리고 싶다" → 휴지통.

@practice
- **정기 백업**: AWS Backup이나 Data Lifecycle Manager로 매일 새벽 운영 볼륨의 스냅샷을 찍고 30일쯤 보관합니다. 랜섬웨어에 대비해 백업을 다른 계정이나 다른 리전에 복사해 두기도 합니다.
- **변경 전 안전장치**: OS 패치나 큰 설정 변경 전에 스냅샷을 찍어 두고, 문제가 생기면 그 시점의 볼륨으로 되돌립니다.
- **골든 AMI 파이프라인**: 보안 패치와 모니터링 에이전트를 넣은 회사 표준 AMI를 정기적으로 새로 굽고(EC2 Image Builder), Auto Scaling 그룹의 시작 템플릿이 새 AMI를 쓰도록 바꿉니다.
- **재해 복구**: 서울 리전의 AMI와 스냅샷을 도쿄 리전에 정기적으로 복사해 두면, 서울에 큰 장애가 났을 때 도쿄에서 같은 서버를 바로 띄울 수 있습니다.

@easy
스냅샷은 디스크의 특정 시점 사진입니다. 처음에는 전체를 찍고, 그다음부터는 바뀐 부분만 더 찍어 저장 공간을 아낍니다. 사진이 있으면 다른 AZ나 다른 리전에서 똑같은 디스크를 다시 만들 수 있습니다.

AMI는 서버 전체의 설치 이미지입니다. 회사에서 새 PC를 받을 때 OS와 업무 프로그램이 다 깔린 표준 이미지를 복제해 주듯, AMI로 서버를 띄우면 설치가 끝난 상태로 시작합니다.

**인스턴스 스토어**는 EC2가 실행되는 **호스트 서버에 물리적으로 붙은 디스크**입니다. 네트워크를 거치지 않아 EBS보다 훨씬 빠르고(일부 유형은 수백만 IOPS), 요금은 인스턴스 값에 포함됩니다.

대신 **임시(ephemeral)**입니다.

- 인스턴스를 **중지하거나 종료하면 데이터가 사라집니다.** 재부팅은 유지됩니다.
- 하드웨어가 고장 나도 사라집니다.
- 백업과 복제는 사용자가 직접 해야 합니다.

| 비교 | 인스턴스 스토어 | EBS |
|---|---|---|
| 위치 | 호스트에 직접 | 네트워크로 연결 |
| 성능 | 매우 높음 | 높음(유형에 따라) |
| 중지·종료 후 | 사라짐 | 유지 가능 |
| 떼어 옮기기 | 안 됨 | 같은 AZ 안에서 가능 |
| 쓰임 | 버퍼, 캐시, 임시 작업 공간, 복제가 있는 분산 DB의 데이터 | 부팅 디스크, 지속 데이터 |

> **시험 포인트** "가장 높은 디스크 I/O가 필요하고, 데이터는 다른 노드에 복제되어 있어 잃어도 된다" → 인스턴스 스토어(i 패밀리 등). "인스턴스를 멈췄다 켰더니 데이터가 없어졌다" → 인스턴스 스토어였기 때문입니다.

@practice
- **다시 만들 수 있는 데이터**: 대용량 데이터 처리의 중간 결과, 동영상 인코딩 임시 파일, 빌드 서버의 작업 공간처럼 잃어도 다시 만들 수 있는 데이터를 둡니다.
- **복제하는 분산 DB**: Cassandra, Elasticsearch처럼 데이터를 여러 노드에 복제하는 시스템은 한 노드의 디스크가 사라져도 다른 노드에서 다시 채우므로, 빠른 인스턴스 스토어를 데이터 디스크로 씁니다.
- **운영상 주의**: 인스턴스 스토어를 쓰는 서버를 실수로 중지하면 데이터가 사라집니다. 운영 문서에 "중지 금지, 재부팅만 허용"을 적어 두는 팀도 있습니다.

@easy
인스턴스 스토어는 서버 본체에 들어 있는 내장 디스크입니다. 네트워크를 거치지 않아 아주 빠르지만, 서버를 반납(중지·종료)하면 함께 초기화됩니다. 호텔 객실 금고처럼 머무는 동안만 쓰는 공간이라, 체크아웃 뒤에도 필요한 물건은 넣지 않습니다.

@topic c07-ebs-types | EBS 볼륨 유형 고르기 | dom=3,4 | prio=3 | les=EBS Volume Types
EBS 볼륨은 SSD 4종과 HDD 2종이 있습니다. 작은 입출력을 많이 하는 일(DB)은 **IOPS**를, 큰 파일을 순서대로 읽는 일(로그, 빅데이터)은 **처리량(MiB/s)**을 보고 고릅니다.

| 유형 | 종류 | 크기 | 최대 IOPS | 최대 처리량 | 부팅 | 언제 |
|---|---|---|---|---|---|---|
| gp3 | 범용 SSD | 1 GiB–64 TiB | 80,000 | 2,000 MiB/s | 가능 | 대부분의 작업. 기본 3,000 IOPS·125 MiB/s, 크기와 따로 늘림 |
| gp2 | 범용 SSD(이전 세대) | 1 GiB–16 TiB | 16,000 | 250 MiB/s | 가능 | GB당 3 IOPS로 크기에 비례(작은 볼륨은 3,000까지 버스트) |
| io2 Block Express | 프로비저닝된 IOPS SSD | 4 GiB–64 TiB | 256,000 | 4,000 MiB/s | 가능 | 지연에 민감한 핵심 DB, 다중 연결 |
| io1 | 프로비저닝된 IOPS SSD | 4 GiB–16 TiB | 64,000 | 1,000 MiB/s | 가능 | io2 이전 세대, 다중 연결 |
| st1 | 처리량 최적화 HDD | 125 GiB–16 TiB | 500 | 500 MiB/s | **불가** | 빅데이터, 데이터 웨어하우스, 로그 처리 |
| sc1 | 콜드 HDD | 125 GiB–16 TiB | 250 | 250 MiB/s | **불가** | 거의 안 읽는 데이터, 가장 싼 블록 스토리지 |

gp3의 한도는 2025년 9월에 크게 올랐습니다(16 TiB·16,000 IOPS·1,000 MiB/s → 64 TiB·80,000 IOPS·2,000 MiB/s). 강의 녹화나 문제집에는 옛 숫자가 남아 있을 수 있습니다.

#### 고르는 순서

1. 부팅 볼륨이면 SSD(gp3, gp2, io1, io2)만 됩니다.
2. 16,000~80,000 IOPS 정도면 gp3로 충분합니다. 그보다 높거나 아주 낮은 지연이 꼭 필요하면 io2 Block Express입니다.
3. 여러 인스턴스가 동시에 붙어야 하면 io1·io2(다중 연결)입니다.
4. 큰 파일을 순서대로 읽고 싸야 하면 st1, 거의 안 읽으면 sc1입니다.

> **시험 포인트** "비용 효율적인 범용 볼륨, 크기와 상관없이 IOPS를 정하고 싶다" → gp3(gp2보다 싸고 독립적으로 조절). "64,000 IOPS를 넘는 DB" → io2 Block Express. "자주 읽는 대용량 순차 데이터, 가장 싸게" → st1. "아카이브 성격, 가장 싸게, 블록 스토리지" → sc1. 부팅 볼륨에 HDD를 고르는 보기는 틀립니다.

@practice
- **기본은 gp3**: 새로 만드는 볼륨은 거의 모두 gp3입니다. 예전에 만든 gp2 볼륨을 gp3로 바꾸기만 해도 같은 성능에 비용이 줄어서, 비용 점검의 단골 항목입니다. 볼륨 유형 변경은 서비스를 멈추지 않고 할 수 있습니다.
- **io2**: 결제·주문 DB처럼 지연이 조금만 늘어도 서비스가 느려지는 DB를 EC2에 직접 운영할 때 씁니다.
- **st1**: Kafka 로그, Hadoop 데이터 노드처럼 큰 파일을 순서대로 읽고 쓰는 일에 씁니다.
- **sc1**: 거의 열어 보지 않는 오래된 파일 서버 데이터에 씁니다. 다만 이런 데이터는 S3로 옮기는 편이 더 싼 경우가 많습니다.

@easy
IOPS는 1초에 처리하는 입출력 요청의 수, 처리량은 1초에 옮기는 데이터의 양입니다. 은행 창구로 치면 IOPS는 한 시간에 몇 명의 손님을 처리하느냐, 처리량은 한 시간에 얼마만큼의 현금을 처리하느냐입니다. DB는 작은 요청이 아주 많아 IOPS가 중요하고, 로그나 빅데이터는 큰 파일을 통째로 읽어 처리량이 중요합니다. SSD는 IOPS에, HDD는 순서대로 읽는 처리량에 강합니다.

@topic c07-efs | EFS와 EBS 비교 | dom=2,3,4 | prio=3 | les=Amazon EFS; Amazon EFS - Hands On; EFS vs EBS
**EFS(Elastic File System)**는 **여러 AZ의 여러 EC2가 동시에 마운트하는** 관리형 NFS 파일 시스템입니다. 용량을 미리 정하지 않고 쓴 만큼 자동으로 늘고 줄며, 쓴 만큼 요금을 냅니다.

#### EFS의 성질

- NFSv4.1 프로토콜, **리눅스(POSIX) 전용**입니다. 윈도우 파일 공유가 필요하면 FSx for Windows File Server입니다([16.2](#c16-fsx)).
- 보안 그룹으로 접근을 통제하고, KMS로 저장 시 암호화합니다.
- 수천 개의 동시 NFS 클라이언트, 페타바이트 규모까지 확장됩니다.
- gp2 EBS보다 GB당 값이 약 3배 비쌉니다. 대신 스토리지 클래스로 크게 줄일 수 있습니다.

#### 설정 선택지

| 항목 | 선택지 |
|---|---|
| 가용성 | **리전(여러 AZ에 저장, 운영용)** / 단일 AZ(One Zone, 개발용, 더 쌈) |
| 처리량 모드 | **Elastic**(사용량에 맞춰 자동, 권장) / Provisioned(정한 만큼) / Bursting(크기에 비례) |
| 성능 모드 | General Purpose(기본, 낮은 지연) / Max I/O(옛 방식, 높은 지연 대신 병렬 처리) |
| 스토리지 클래스 | Standard / Infrequent Access(IA) / Archive. **수명 주기 정책**으로 N일 동안 안 읽은 파일을 자동으로 옮김 |

#### EFS와 EBS

| 비교 | EBS | EFS |
|---|---|---|
| 붙는 인스턴스 | 보통 하나(io1·io2 다중 연결은 같은 AZ 16대) | 여러 AZ의 수백 대 동시 |
| AZ | 한 AZ에 묶임 | 리전 전체(One Zone 제외) |
| 용량 | 미리 정함 | 자동으로 늘고 줄음 |
| OS | 리눅스·윈도우 | 리눅스만 |
| 요금 | 정한 용량만큼 | 쓴 만큼(GB당 더 비쌈) |
| 다른 AZ로 옮기기 | 스냅샷 후 복원 | 필요 없음 |

> **시험 포인트** "여러 AZ의 웹 서버가 같은 업로드 파일(예: WordPress 미디어)을 공유" → EFS([11.2](#c11-stateful)). "자주 안 쓰는 파일이 많아 EFS 비용을 줄이고 싶다" → 수명 주기 정책으로 IA·Archive 클래스. "윈도우 서버들이 공유 폴더를 쓴다" → EFS가 아니라 FSx for Windows.

@practice
- **웹 서버 공유 파일**: WordPress 같은 CMS의 업로드 폴더를 EFS에 두면, Auto Scaling으로 서버가 늘어나도 모든 서버가 같은 파일을 봅니다.
- **컨테이너 공유 볼륨**: ECS·EKS 작업(Fargate 포함)에 EFS를 붙여, 컨테이너가 재시작되거나 다른 AZ로 옮겨져도 데이터가 남게 합니다.
- **ML·분석 공유 데이터**: 여러 학습 서버나 SageMaker 노트북이 같은 데이터 세트와 모델 파일을 함께 읽습니다.
- **비용 관리**: 오래된 첨부 파일이 쌓이면 수명 주기 정책으로 30일 넘게 안 읽은 파일을 IA 클래스로 옮겨 비용을 크게 줄입니다.

@easy
EBS가 서버 한 대에 연결하는 개인 외장 디스크라면, EFS는 사무실 전체가 함께 쓰는 공유 드라이브(NAS)입니다. 여러 서버가 동시에 같은 폴더를 열 수 있고, 여러 AZ에서 접근해도 같은 파일이 보입니다. 용량을 미리 정하지 않아 파일이 늘면 저절로 커지고, 쓴 만큼만 냅니다. 리눅스 방식(NFS)만 지원하므로 윈도우 서버의 공유 폴더로는 쓰지 않습니다.

@quiz
Q: ap-northeast-2a의 EBS 볼륨을 2c의 인스턴스에서 쓰려면?
A: 스냅샷을 찍고, 그 스냅샷으로 2c에서 새 볼륨을 만들어 붙입니다.
Q: 인스턴스를 종료했더니 루트 볼륨이 사라졌습니다. 남기려면 무엇을 바꿔야 하나요?
A: 루트 볼륨의 종료 시 삭제(Delete on Termination) 속성을 끕니다.
Q: 암호화되지 않은 EBS 볼륨을 암호화하는 순서는?
A: 스냅샷 → 암호화를 켜고 스냅샷 복사 → 암호화된 스냅샷으로 새 볼륨 생성 → 인스턴스에 붙이기입니다.
Q: 다른 리전에 같은 설정의 서버를 빠르게 띄워야 합니다. 무엇을 복사하나요?
A: AMI를 대상 리전으로 복사합니다(EBS 스냅샷도 함께 복사됨).
Q: 인스턴스를 중지했다 시작했더니 데이터가 사라졌습니다. 어떤 저장소였을까요?
A: 인스턴스 스토어입니다. 중지·종료 시 데이터가 지워집니다.
Q: 크기와 상관없이 IOPS와 처리량을 따로 정하는 가장 비용 효율적인 범용 SSD는?
A: gp3입니다.
Q: st1이나 sc1을 부팅 볼륨으로 쓸 수 있나요?
A: 없습니다. 부팅 볼륨은 SSD 유형(gp2, gp3, io1, io2)만 됩니다.
Q: 세 AZ의 리눅스 웹 서버가 같은 파일을 읽고 써야 합니다. 어떤 저장소인가요?
A: EFS(리전 가용성)입니다.
