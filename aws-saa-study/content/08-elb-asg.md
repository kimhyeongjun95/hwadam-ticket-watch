@part ch08 | High Availability and Scalability: ELB & ASG | 강의 섹션 8 | 8. ELB & ASG
요청을 여러 서버에 나눠 주는 로드 밸런서(ELB)와, 부하에 따라 서버 대수를 자동으로 조절하는 Auto Scaling 그룹(ASG)을 배웁니다. "고가용성 + 탄력적 확장" 문제의 기본 답이 ELB + 다중 AZ ASG 조합입니다.

@topic c08-ha | 확장성과 고가용성 | dom=2,3 | prio=3 | les=High Availability and Scalability
**확장성(scalability)**은 부하가 늘어도 자원을 늘려 감당하는 능력이고, **고가용성(high availability)**은 일부가 고장 나도 서비스가 계속되는 성질입니다. 둘은 서로 연결되지만 다른 개념입니다.

| 개념 | 뜻 | AWS에서 |
|---|---|---|
| 수직 확장(scale up/down) | 서버 한 대를 키우거나 줄임 | `t3.micro` → `t3.large`. DB처럼 나누기 어려운 시스템. 한계가 있음 |
| 수평 확장(scale out/in) | 서버 대수를 늘리거나 줄임 | Auto Scaling 그룹, 로드 밸런서. 분산 시스템이 필요 |
| 고가용성 | 장애에도 계속 동작 | 최소 2개 AZ에 나눠 두기(다중 AZ ASG, 다중 AZ RDS) |
| 탄력성(elasticity) | 부하에 맞춰 자동으로 늘고 줄어 쓴 만큼 냄 | ASG의 자동 조정 |

수평 확장을 하려면 서버가 **무상태(stateless)**여야 합니다. 세션, 업로드 파일처럼 사용자별 상태는 서버 밖(ElastiCache, DynamoDB, S3, EFS)에 두어야 아무 서버가 요청을 받아도 됩니다([11.2](#c11-stateful)).

**내결함성(fault tolerance)**은 고가용성보다 한 단계 더 나아가, 고장이 나도 **성능 저하 없이** 계속 동작하는 것입니다. 예를 들어 평소 4대가 필요한 서비스를 AZ 두 곳에 4대씩 두면, AZ 하나가 멈춰도 4대가 남아 그대로 버팁니다.

> **시험 포인트** "트래픽이 갑자기 몰리는 웹 앱을 고가용성으로" → 여러 AZ에 걸친 ASG + ALB. "DB 인스턴스가 느려 더 큰 유형으로 바꾼다"는 수직 확장입니다. 문제에 *fault-tolerant*가 나오면 장애 후에도 필요한 용량이 남는지까지 따집니다.

@practice
- **수평 확장이 기본**: 웹·API 서버는 작은 서버 여러 대를 로드 밸런서 뒤에 두고, 사용자가 늘면 대수를 늘립니다. 서버 한 대가 고장 나도 나머지가 받아 주므로 고가용성도 함께 얻습니다.
- **수직 확장이 맞는 곳**: 관계형 DB 주 인스턴스처럼 여러 대로 나누기 어려운 시스템은 더 큰 인스턴스로 키웁니다. 이때는 바꾸는 동안 잠시 끊기므로 점검 시간에 합니다.
- **내결함성 계산**: 평소 서버 4대가 필요한 서비스를 AZ 두 곳에 2대씩 두면, AZ 하나가 멈췄을 때 2대만 남아 느려집니다. 예약·결제처럼 장애 중에도 성능이 떨어지면 안 되는 서비스는 AZ마다 4대씩 둡니다.
- **세션 외부화**: 서버를 늘리고 줄이려면 로그인 세션, 장바구니 같은 상태를 Redis(ElastiCache)나 DynamoDB로 빼는 작업이 먼저입니다.

@easy
수직 확장은 직원 한 명에게 더 좋은 컴퓨터를 주는 것이고, 수평 확장은 직원을 더 뽑는 것입니다. 컴퓨터 성능에는 한계가 있고 바꾸는 동안 일이 멈추지만, 직원을 늘리는 방식은 계속 늘릴 수 있고 한 명이 아파도 다른 사람이 일을 받습니다.

고가용성은 "누가 빠져도 가게가 문을 닫지 않는 것", 내결함성은 "누가 빠져도 손님이 기다리는 시간까지 그대로인 것"입니다. 내결함성을 얻으려면 처음부터 빠질 사람 몫까지 인원을 더 둡니다.

@topic c08-elb | ELB 개요와 상태 확인 | dom=2,3 | prio=3 | les=Elastic Load Balancing (ELB) Overview
**로드 밸런서**는 들어온 요청을 뒤의 여러 서버(대상)에 나눠 보내는 장치입니다. **ELB(Elastic Load Balancing)**는 AWS가 운영하는 관리형 로드 밸런서로, 업그레이드·확장·고가용성을 AWS가 맡습니다.

#### 로드 밸런서가 하는 일

- 한 개의 DNS 이름(`my-alb-123.ap-northeast-2.elb.amazonaws.com`)으로 들어온 요청을 여러 대상에 나눕니다.
- **상태 확인(health check)**으로 고장 난 대상을 빼고, 회복하면 다시 넣습니다.
- HTTPS 암호화를 대신 풀어 줍니다(SSL 종료, [8.5](#c08-elb-features)).
- 여러 AZ에 걸쳐 동작해 AZ 장애를 견딥니다.
- 고정 세션, 대상 사이 공평한 분산 같은 기능을 제공합니다.

#### 상태 확인

대상 그룹마다 프로토콜·포트·경로(예: HTTP `/health`)를 정하고, 정해진 간격으로 요청을 보냅니다. 기대한 응답(기본 HTTP 200)이 연속으로 오지 않으면 그 대상을 **unhealthy**로 보고 트래픽을 보내지 않습니다.

#### 네 가지 종류

| 종류 | 계층 | 프로토콜 | 언제 |
|---|---|---|---|
| ALB(Application) | 7 | HTTP, HTTPS, gRPC, WebSocket | 웹 앱, 마이크로서비스, 경로·호스트별 라우팅([8.3](#c08-alb)) |
| NLB(Network) | 4 | TCP, UDP, TLS | 초고성능, 고정 IP, 비HTTP 프로토콜([8.4](#c08-nlb-gwlb)) |
| GWLB(Gateway) | 3 | IP(GENEVE) | 방화벽·침입 탐지 장비 묶음([8.4](#c08-nlb-gwlb)) |
| CLB(Classic) | 4·7 | HTTP, HTTPS, TCP, SSL | 이전 세대. 새로 만들지 않음 |

#### 보안 그룹 연결

로드 밸런서의 보안 그룹은 인터넷의 80·443을 열고, 뒤의 EC2 보안 그룹은 **로드 밸런서 보안 그룹에서 온 트래픽만** 허용합니다([5.3](#c05-sg)). 그래야 사용자가 로드 밸런서를 건너뛰고 EC2에 바로 들어오지 못합니다.

> **시험 포인트** 로드 밸런서는 공개(internet-facing)와 내부(internal) 두 가지가 있습니다. 웹 계층 앞은 공개 ALB, 웹 계층과 앱 계층 사이는 내부 ALB를 둡니다. 로드 밸런서 자체도 AWS가 여러 AZ에 걸쳐 운영하므로 별도로 이중화하지 않습니다.

@practice
- **웹 서비스의 기본 입구**: 운영 중인 거의 모든 웹 서비스는 도메인이 ALB를 가리키고, ALB가 여러 AZ의 서버로 요청을 나눕니다. 서버를 배포하거나 교체해도 사용자 쪽 주소는 바뀌지 않습니다.
- **상태 확인 경로**: 앱에 `/health` 같은 상태 확인 전용 경로를 만들고, DB 연결 같은 필수 의존성까지 확인하게 합니다. 응답하지 않는 서버는 로드 밸런서가 자동으로 뺍니다.
- **공개와 내부**: 인터넷용 공개 ALB 뒤의 웹 계층이, 내부 ALB를 거쳐 사내 API 계층을 부르는 2단 구성이 흔합니다.
- **배포**: 블루/그린이나 롤링 배포 때 로드 밸런서에서 새 버전 서버를 등록하고 옛 서버를 빼는 방식으로 무중단 배포를 합니다.

@easy
로드 밸런서는 콜센터의 자동 분배 시스템과 같습니다. 고객은 대표 번호 하나로 전화하고, 시스템이 지금 통화 가능한 상담원에게 연결합니다. 상담원이 자리를 비우면(상태 확인 실패) 그 사람에게는 전화를 보내지 않습니다. 상담원이 늘고 줄어도 대표 번호는 그대로입니다.

ALB, NLB, GWLB는 어디까지 보고 나누느냐가 다릅니다. ALB는 요청 내용(주소, 경로)을 읽고 나누고, NLB는 내용을 보지 않고 연결만 빠르게 나누며, GWLB는 트래픽을 보안 검사 장비로 돌려보내는 데 씁니다.

@topic c08-alb | Application Load Balancer | dom=2,3 | prio=3 | les=Application Load Balancer (ALB); Application Load Balancer (ALB) - Hands On - Part 1; Application Load Balancer (ALB) - Hands On - Part 2
**ALB(Application Load Balancer)**는 HTTP·HTTPS(7계층) 요청의 **내용을 보고** 어느 대상 그룹으로 보낼지 정하는 로드 밸런서입니다. 한 ALB 뒤에 여러 앱(마이크로서비스, 컨테이너)을 둘 수 있습니다.

#### 라우팅 규칙

리스너(예: HTTPS 443)에 규칙을 달아 요청을 대상 그룹으로 보냅니다.

| 조건 | 예 |
|---|---|
| 경로 | `/users` → 사용자 서비스, `/orders` → 주문 서비스 |
| 호스트 헤더 | `api.example.com` → API, `www.example.com` → 웹 |
| 쿼리 문자열·헤더 | `?platform=mobile` → 모바일용 |
| 출발지 IP | 사내 IP 대역만 관리자 페이지로 |

규칙은 대상으로 보내는 것 말고도 **리디렉션**(HTTP → HTTPS)이나 **고정 응답**(점검 중 503)을 돌려줄 수 있습니다.

#### 대상 그룹

| 대상 유형 | 예 |
|---|---|
| EC2 인스턴스 | ASG가 관리하는 웹 서버 |
| ECS 작업 | 컨테이너(동적 포트 매핑) |
| Lambda 함수 | HTTP 요청이 JSON 이벤트로 바뀌어 전달 |
| IP 주소 | 사설 IP(온프레미스 서버 포함) |

#### 클라이언트 IP

ALB는 요청을 받아 **자기 이름으로 새로 보내므로**, 뒤의 EC2가 보는 출발지 IP는 ALB의 사설 IP입니다. 원래 사용자의 IP·포트·프로토콜은 헤더로 전달됩니다.

| 헤더 | 내용 |
|---|---|
| `X-Forwarded-For` | 클라이언트 IP |
| `X-Forwarded-Port` | 클라이언트가 접속한 포트 |
| `X-Forwarded-Proto` | 클라이언트가 쓴 프로토콜(http, https) |

ALB는 이 밖에 Cognito·OIDC 로그인 처리, 상호 TLS(mTLS) 인증, WebSocket·HTTP/2를 지원합니다.

> **시험 포인트** "URL 경로나 호스트 이름에 따라 다른 서비스로", "컨테이너마다 다른 포트(동적 포트)", "HTTP를 HTTPS로 리디렉션" → ALB. "앱 로그에 사용자 IP가 아니라 ALB IP가 찍힌다" → `X-Forwarded-For` 헤더를 읽도록 앱(웹 서버 로그 형식)을 바꿉니다.

@practice
- **마이크로서비스 하나의 입구**: `api.example.com/users`는 회원 서비스, `/orders`는 주문 서비스, `/payments`는 결제 서비스로 보내는 식으로 ALB 하나 뒤에 여러 팀의 서비스를 둡니다.
- **컨테이너 서비스**: ECS·EKS의 컨테이너가 서버마다 다른 포트로 떠도, ALB 대상 그룹이 동적 포트를 추적해 연결합니다.
- **HTTPS 정리**: HTTP 80으로 들어온 요청은 ALB 규칙에서 HTTPS 443으로 리디렉션하고, 점검 시간에는 고정 응답으로 점검 안내를 돌려줍니다.
- **사용자 IP 기록**: 웹 서버 로그에 ALB IP만 찍혀 보안 분석이 안 된다는 문제가 흔합니다. Nginx나 Spring의 로그 형식에서 `X-Forwarded-For` 값을 남기도록 바꿉니다.
- **Lambda 연결**: 트래픽이 적은 사내 API는 ALB 뒤에 Lambda를 두어 서버 없이 운영합니다.

@easy
ALB는 회사 안내 데스크처럼 방문자의 용건을 듣고 담당 부서로 안내합니다. "회원 문의"는 회원팀으로, "주문 문의"는 주문팀으로 보내듯, 요청 주소의 경로나 호스트 이름을 보고 다른 서버 묶음으로 보냅니다.

ALB가 요청을 대신 전달하므로 뒤의 서버는 ALB가 보낸 것으로만 압니다. 그래서 원래 요청한 사람의 IP는 `X-Forwarded-For`라는 헤더에 적어서 함께 넘겨 줍니다.

@topic c08-nlb-gwlb | Network Load Balancer와 Gateway Load Balancer | dom=1,3 | prio=3 | les=Network Load Balancer (NLB); Network Load Balancer (NLB) - Hands On; Gateway Load Balancer (GWLB)
#### NLB(Network Load Balancer)

**NLB**는 TCP·UDP·TLS(4계층) 연결을 나누는 로드 밸런서입니다. 내용을 들여다보지 않으므로 **초당 수백만 요청을 아주 낮은 지연**으로 처리합니다.

- **AZ마다 고정 IP 하나**를 가지고, 여기에 **탄력적 IP**를 붙일 수 있습니다. 고객사 방화벽에 등록할 고정 IP가 필요할 때 씁니다.
- 대상: EC2 인스턴스, 사설 IP 주소, **ALB**(NLB 뒤에 ALB를 두면 고정 IP와 7계층 라우팅을 함께 얻음).
- 상태 확인은 TCP, HTTP, HTTPS를 지원합니다.
- 보안 그룹을 붙일 수 있습니다(2023년부터).
- 게임 서버(UDP), IoT, 금융 거래처럼 HTTP가 아니거나 극한 성능이 필요한 경우에 고릅니다.

#### GWLB(Gateway Load Balancer)

**GWLB**는 방화벽, 침입 탐지·방지(IDS/IPS), 패킷 심층 검사 같은 **서드파티 가상 보안 장비** 묶음 앞에 두는 3계층 로드 밸런서입니다. 트래픽을 보안 장비로 보냈다가 검사가 끝나면 원래 목적지로 돌려보냅니다.

1. VPC의 라우팅 테이블이 들어오는 트래픽을 **GWLB 엔드포인트**로 보냅니다.
2. GWLB가 트래픽을 **GENEVE 프로토콜(6081번 포트)**로 감싸 보안 장비(EC2) 중 하나로 보냅니다.
3. 장비가 검사해 통과시킨 트래픽만 GWLB를 거쳐 원래 목적지(앱)로 갑니다.

GWLB는 투명한 네트워크 관문(gateway)과 로드 밸런서를 합친 것입니다. 보안 장비를 늘리거나 고장 난 장비를 빼도 트래픽 흐름은 그대로입니다.

| 고를 때 | ALB | NLB | GWLB |
|---|---|---|---|
| 핵심 | HTTP 내용 보고 라우팅 | 초고성능, 고정 IP, TCP·UDP | 보안 장비로 트래픽 경유 |
| 고정 IP | 없음(DNS 이름) | AZ마다, 탄력적 IP 가능 | 해당 없음 |
| 계층 | 7 | 4 | 3 |

> **시험 포인트** "UDP", "고정 IP 또는 탄력적 IP", "초당 수백만 요청·초저지연" → NLB. "서드파티 방화벽·IDS 장비를 VPC 트래픽 경로에 투명하게 넣고 확장" → GWLB. "고정 IP + 경로 기반 라우팅이 둘 다 필요" → NLB 뒤에 ALB, 또는 Global Accelerator 뒤에 ALB.

@practice
- **NLB, 게임·실시간 통신**: 모바일 게임의 실시간 대전 서버, IoT 기기 연결, 음성 통화처럼 UDP나 오래 유지되는 TCP 연결을 다룰 때 씁니다.
- **NLB, 고정 IP가 필요한 B2B**: 은행·카드사 같은 고객사가 방화벽에 우리 IP를 등록해야 할 때 NLB에 탄력적 IP를 붙여 줍니다. HTTP 라우팅까지 필요하면 NLB 뒤에 ALB를 둡니다.
- **NLB, PrivateLink**: 다른 회사나 다른 계정에 우리 서비스를 비공개로 제공할 때 NLB 앞에 VPC 엔드포인트 서비스(PrivateLink)를 붙입니다([27.9](#c27-endpoints)).
- **GWLB, 보안 장비 중앙화**: 보안 규정상 모든 인터넷 트래픽이 방화벽을 거쳐야 하는 회사는 Palo Alto, Fortinet 같은 가상 방화벽을 여러 대 띄우고 GWLB로 묶습니다. 트래픽이 늘면 방화벽만 늘리면 됩니다.

@easy
NLB는 내용을 확인하지 않고 연결만 빠르게 이어 주는 교환기입니다. 그래서 아주 많은 연결을 지연 없이 처리하고, 전화번호처럼 바뀌지 않는 고정 주소를 줄 수 있습니다. 대신 "이 요청은 회원 서비스로" 같은 내용 기반 분배는 하지 못합니다.

GWLB는 공항의 보안 검색대와 비슷합니다. 모든 짐(트래픽)을 검색대 중 비어 있는 곳으로 보내고, 통과한 짐만 원래 가던 곳으로 보냅니다. 검색대가 모자라면 검색대만 더 열면 되고, 짐을 보내는 사람은 검색대가 몇 개인지 몰라도 됩니다.

로드 밸런서의 세부 기능 네 가지입니다. 각각 "어떤 문제를 풀려고 켜는지"로 기억합니다.

#### 고정 세션(Sticky Sessions)

같은 사용자의 요청을 **쿠키로 같은 대상에 계속** 보냅니다. 세션을 서버 메모리에 두는 옛 앱이 로그인 상태를 잃지 않게 할 때 씁니다. 대가로 대상 사이 부하가 고르지 않을 수 있습니다.

| 쿠키 | 만드는 곳 | 이름 |
|---|---|---|
| 기간 기반 쿠키 | 로드 밸런서 | ALB는 `AWSALB`(CLB는 `AWSELB`) |
| 애플리케이션 기반 쿠키 | 대상 앱(사용자 지정 쿠키) 또는 로드 밸런서(`AWSALBAPP`) | 대상 그룹마다 따로 |

더 나은 설계는 세션을 ElastiCache나 DynamoDB에 두고 고정 세션을 끄는 것입니다([11.2](#c11-stateful)).

#### 교차 영역 로드 밸런싱(Cross-Zone)

AZ A에 대상 2개, AZ B에 대상 8개가 있다고 합시다. 로드 밸런서 노드는 AZ마다 있어서, 사용자는 두 노드에 50%씩 들어옵니다.

- **켜면**: 각 노드가 **모든 AZ의 대상 10개**에 고르게 보내 대상마다 10%씩 받습니다.
- **끄면**: 각 노드가 **자기 AZ의 대상**에만 보내 A의 대상은 25%씩, B의 대상은 6.25%씩 받습니다.

| 종류 | 기본값 | AZ 간 데이터 요금 |
|---|---|---|
| ALB | 켜짐(대상 그룹에서 끌 수 있음) | 없음 |
| NLB, GWLB | 꺼짐 | 켜면 요금 발생 |
| CLB | 꺼짐 | 없음 |

#### SSL/TLS 인증서와 SNI

HTTPS 리스너에 인증서를 붙이면 로드 밸런서가 **암호화를 풀고**(SSL 종료) 뒤의 대상과는 사설망으로 통신합니다. 인증서는 **ACM(AWS Certificate Manager)**에서 무료로 발급·자동 갱신해 붙입니다([26.5](#c26-acm-hsm)).

**SNI(Server Name Indication)**는 TLS 연결 첫머리에 클라이언트가 접속할 호스트 이름을 알려 주는 기능입니다. 덕분에 로드 밸런서 하나가 `a.example.com`, `b.example.com`처럼 **도메인마다 다른 인증서**를 고를 수 있습니다. ALB, NLB, CloudFront는 SNI를 지원하고, CLB는 인증서를 하나만 쓸 수 있어 도메인마다 CLB를 따로 두어야 했습니다.

#### 등록 취소 지연(Deregistration Delay)

대상을 빼거나(스케일 인, 배포) unhealthy가 되면, 로드 밸런서는 **새 요청은 보내지 않고 진행 중인 요청이 끝날 때까지** 기다립니다. CLB에서는 연결 드레이닝(Connection Draining)이라 부릅니다.

- 1–3,600초, 기본 300초입니다. 0이면 기다리지 않습니다.
- 요청이 짧은 API면 짧게(예: 30초), 긴 업로드가 있으면 길게 잡습니다.

> **시험 포인트** "한 ALB에서 여러 도메인의 HTTPS 인증서" → SNI(리스너에 인증서 여러 개). "AZ마다 대상 수가 달라 부하가 쏠린다" → 교차 영역 로드 밸런싱. "스케일 인 때 진행 중인 요청이 끊긴다" → 등록 취소 지연을 늘림. "로그인이 자꾸 풀린다(세션을 서버 메모리에 둠)" → 단기 해결은 고정 세션, 근본 해결은 외부 세션 저장소.

@practice
- **고정 세션**: 세션을 서버 메모리에 두는 오래된 자바 웹 앱을 클라우드로 옮길 때 임시로 켭니다. 이후 세션을 Redis로 옮기면 끕니다.
- **SNI로 인증서 여러 개**: 한 회사가 `shop.example.com`, `admin.example.com`, `api.example.com`을 ALB 하나로 받으면서 도메인마다 다른 ACM 인증서를 붙입니다. 인증서 갱신은 ACM이 자동으로 합니다.
- **교차 영역**: NLB에서 AZ마다 서버 수가 달라 한쪽 서버만 바빠지면 교차 영역을 켭니다. 다만 NLB는 AZ 간 전송 요금이 붙으니 서버 수를 AZ별로 맞추는 것이 먼저입니다.
- **등록 취소 지연**: 짧은 API는 30초 정도로 줄여 배포 시간을 줄이고, 대용량 파일 업로드가 있는 서비스는 길게 둡니다. 기본값 300초 그대로면 배포가 서버마다 5분씩 늘어지는 일이 흔합니다.

@easy
네 기능은 각각 다른 불편을 풉니다.

- **고정 세션**은 "단골손님은 늘 같은 상담원에게" 연결하는 것입니다. 상담원이 손님 정보를 자기 메모장에만 적어 두는 경우에 필요합니다.
- **교차 영역**은 층이 달라도 모든 상담원에게 고르게 전화를 나누는 것입니다. 끄면 각 층 안에서만 나눠서, 상담원이 적은 층이 바빠집니다.
- **SNI**는 한 건물의 안내 데스크가 방문한 회사 이름을 듣고 그 회사의 출입증(인증서)을 내주는 것입니다.
- **등록 취소 지연**은 퇴근하는 상담원에게 새 전화는 주지 않되, 통화 중인 전화는 끝내고 가게 하는 것입니다.

@topic c08-asg | Auto Scaling 그룹 | dom=2,4 | prio=3 | les=Auto Scaling Groups (ASG) Overview; Auto Scaling Groups Hands On
**Auto Scaling 그룹(ASG)**은 EC2 인스턴스 묶음을 **정한 개수 범위 안에서 자동으로 늘리고 줄이며**, 고장 난 인스턴스를 새것으로 바꾸는 기능입니다. ASG 자체는 무료이고 띄운 EC2 값만 냅니다.

#### 크기 세 가지

| 값 | 뜻 |
|---|---|
| 최소(minimum) | 아무리 한가해도 이 수 아래로 줄지 않음 |
| 원하는(desired) | 지금 유지하려는 수. 조정 정책이 이 값을 바꿈 |
| 최대(maximum) | 아무리 바빠도 이 수를 넘지 않음 |

#### ASG를 만들 때 정하는 것

- **시작 템플릿(Launch Template)**: AMI, 인스턴스 유형, 보안 그룹, 키 페어, IAM 역할, 사용자 데이터, EBS 설정. (예전의 시작 구성은 더 이상 권장하지 않습니다.)
- **서브넷(AZ)**: 여러 AZ를 고르면 AZ 사이에 고르게 나눠 띄웁니다.
- **로드 밸런서 대상 그룹**: 새 인스턴스를 자동으로 등록합니다.
- **상태 확인**: 기본은 EC2 상태 확인(인스턴스가 살아 있나). **ELB 상태 확인**을 켜면 앱이 응답하지 않는 인스턴스도 교체합니다.
- **조정 정책**: 언제 늘리고 줄일지([8.7](#c08-scaling)).

#### 흐름

1. CloudWatch 경보(예: 평균 CPU 70% 초과)가 울립니다.
2. 조정 정책이 원하는 개수를 4 → 6으로 올립니다.
3. ASG가 시작 템플릿으로 인스턴스 2대를 여러 AZ에 띄웁니다.
4. 새 인스턴스가 ALB 대상 그룹에 등록되고, 상태 확인을 통과하면 트래픽을 받습니다.

> **시험 포인트** "인스턴스가 응답하지 않는데 ASG가 교체하지 않는다" → ASG의 상태 확인 유형을 ELB로 바꿉니다. "AZ 하나가 멈춰도 최소 2대가 남게" → 여러 AZ에 걸친 ASG의 최소 용량을 AZ 장애 후 필요량을 기준으로 잡습니다. ASG는 리전 안의 AZ들에 걸칠 수 있지만 리전을 넘지는 못합니다.

@practice
- **웹 서버 자동 확장**: 쇼핑몰은 평소 4대, 행사 때 최대 20대처럼 최소·최대를 정해 두고, 부하에 따라 ASG가 대수를 조절합니다. 새벽에는 다시 줄어 비용을 아낍니다.
- **자동 복구**: 서버 한 대가 멈추면 ASG가 새 서버로 바꿉니다. 대수를 늘리지 않는 고정 크기(최소 = 원하는 = 최대) ASG도 이 자동 교체 때문에 씁니다. 배스천 서버를 ASG 1대로 운영하는 경우가 대표적입니다.
- **ELB 상태 확인 켜기**: 서버는 살아 있는데 앱이 멈춘 경우까지 교체하려고 ASG 상태 확인을 ELB로 바꿉니다. 운영에서 거의 필수인 설정입니다.
- **시작 템플릿 버전 관리**: 새 AMI나 설정을 적용할 때 시작 템플릿의 새 버전을 만들고, 인스턴스 새로 고침으로 조금씩 교체합니다.

@easy
ASG는 매장 아르바이트 인원을 자동으로 조절하는 점장과 같습니다. "최소 2명, 최대 10명"을 정해 두면, 손님이 몰리면 사람을 더 부르고 한가하면 퇴근시킵니다. 누가 갑자기 쓰러지면 바로 대신할 사람을 부릅니다.

시작 템플릿은 새로 오는 사람에게 주는 업무 매뉴얼입니다. 누가 와도 같은 복장, 같은 장비, 같은 절차로 일하게 해서 몇 명을 늘리든 똑같은 서버가 만들어집니다.

@topic c08-scaling | 조정 정책 | dom=2,3,4 | prio=3 | les=Auto Scaling Groups - Scaling Policies; Auto Scaling Groups - Scaling Policies Hands On
**조정 정책(scaling policy)**은 ASG가 언제 몇 대를 늘리고 줄일지 정한 규칙입니다. 상황에 따라 네 가지를 고릅니다.

| 정책 | 동작 | 예 | 언제 |
|---|---|---|---|
| 대상 추적(target tracking) | 지표를 목표값에 맞추도록 알아서 늘리고 줄임 | 평균 CPU 40% 유지 | 가장 간단, 대부분의 기본 선택 |
| 단계·단순 조정(step / simple) | CloudWatch 경보가 울리면 정한 만큼 조정 | CPU 70% 넘으면 +2대, 30% 밑이면 -1대 | 경보 기준과 조정 폭을 직접 정할 때 |
| 예약 조정(scheduled) | 정한 시각에 용량을 바꿈 | 금요일 17시에 최소 10대 | 미리 아는 이벤트·출근 시간 |
| 예측 조정(predictive) | 과거 패턴을 머신러닝으로 예측해 미리 늘림 | 매일 아침 9시 부하를 미리 대비 | 일·주 단위로 반복되는 부하 |

#### 자주 쓰는 지표

- `CPUUtilization`: 인스턴스 평균 CPU
- `RequestCountPerTarget`: 대상 하나당 요청 수(ALB). 대상마다 적정 요청 수가 정해진 웹 앱에 좋음
- 평균 네트워크 입출력: 네트워크가 병목인 앱
- 사용자 지정 지표: 대기열 길이 등. SQS 대기열의 메시지 수를 인스턴스 수로 나눈 *인스턴스당 백로그*로 조정하는 패턴은 [17.3](#c17-sqs-asg)에 있습니다.

#### 휴지 기간과 워밍업

조정 직후에는 새 인스턴스가 아직 지표에 반영되지 않습니다. **휴지 기간(cooldown, 기본 300초)** 동안 다음 조정을 미뤄 과하게 늘리는 것을 막습니다. 인스턴스가 바로 서비스할 수 있도록 **설치가 끝난 AMI**를 쓰면 준비 시간이 줄어 휴지 기간도 줄일 수 있습니다.

#### 수명 주기 후크와 인스턴스 새로 고침

- **수명 주기 후크(lifecycle hook)**: 인스턴스가 시작되거나 종료되기 직전에 멈춰 세우고 작업(설정 적용, 로그 백업)을 하게 합니다.
- **인스턴스 새로 고침(instance refresh)**: 시작 템플릿을 바꾼 뒤 기존 인스턴스를 조금씩 새 템플릿으로 교체합니다.

> **시험 포인트** "매주 월요일 오전 9시마다 트래픽이 몰려 처음 몇 분 동안 느리다" → 예약 조정(또는 예측 조정)으로 미리 늘림. "평균 CPU를 50% 근처로 유지" → 대상 추적. "SQS 대기열이 길어지면 처리 서버를 늘림" → 대기열 지표(인스턴스당 백로그)로 대상 추적. "스케일 인 전에 인스턴스 로그를 S3에 백업" → 수명 주기 후크.

@practice
- **대상 추적이 기본**: 대부분의 회사는 "평균 CPU 50%"나 "서버당 요청 수 1,000"을 목표로 대상 추적 정책 하나를 둡니다. 경보와 조정 폭을 따로 관리할 필요가 없습니다.
- **예약 조정**: 매일 오전 9시 출근 시간에 몰리는 사내 시스템, 정해진 시각에 열리는 티켓 예매나 수강 신청은 시작 몇 분 전에 미리 늘려 둡니다. 부하가 온 뒤에 늘리면 새 서버가 뜨는 몇 분 동안 느려지기 때문입니다.
- **예측 조정**: 요일별·시간대별 패턴이 뚜렷한 배달 앱(점심·저녁 피크)처럼 반복되는 부하에 씁니다.
- **수명 주기 후크**: 서버가 줄어들 때 마지막 로그를 S3에 올리거나, 서버가 늘어날 때 설정 관리 도구에 등록을 마친 뒤 트래픽을 받게 합니다.

@easy
조정 정책은 인원을 늘리는 기준을 정하는 방법입니다.

- **대상 추적**: "계산대 줄을 늘 3명 이하로"처럼 목표만 정하면 알아서 맞춥니다.
- **단계 조정**: "줄이 10명 넘으면 2명 추가, 20명 넘으면 4명 추가"처럼 구간마다 직접 정합니다.
- **예약 조정**: "매주 금요일 저녁 6시에는 미리 8명"처럼 달력에 적어 둡니다.
- **예측 조정**: 지난 몇 주의 손님 수를 보고 내일 몰릴 시간을 예상해 미리 부릅니다.

휴지 기간은 사람을 부른 뒤 그 사람이 일을 시작할 때까지 기다리는 시간입니다. 기다리지 않고 계속 부르면 필요 이상으로 많이 부르게 됩니다.

@quiz
Q: 웹 서버가 세션을 메모리에 저장해, ASG가 서버를 늘리면 로그인이 풀립니다. 근본적인 해결은?
A: 세션을 ElastiCache나 DynamoDB 같은 외부 저장소에 두어 서버를 무상태로 만듭니다. 고정 세션은 임시 방편입니다.
Q: 경로 `/api`는 API 서버로, `/images`는 이미지 서버로 보내야 합니다. 어떤 로드 밸런서인가요?
A: ALB입니다. 경로 기반 라우팅 규칙으로 대상 그룹을 나눕니다.
Q: 고객사가 방화벽에 등록할 고정 IP가 필요하고, 프로토콜은 TCP입니다. 어떤 로드 밸런서인가요?
A: NLB입니다. AZ마다 고정 IP를 가지고 탄력적 IP를 붙일 수 있습니다.
Q: 서드파티 방화벽 장비 여러 대를 VPC 트래픽 경로에 넣고 장비 수를 늘리고 줄이려 합니다. 무엇을 쓰나요?
A: Gateway Load Balancer입니다(GENEVE 6081 포트).
Q: 뒤의 EC2 로그에 사용자 IP 대신 ALB의 IP가 찍힙니다. 사용자 IP는 어디서 보나요?
A: `X-Forwarded-For` 헤더입니다.
Q: NLB에서 교차 영역 로드 밸런싱을 켜면 무엇이 달라지나요?
A: 노드가 모든 AZ의 대상에 고르게 보내고, AZ 간 데이터 전송 요금이 생깁니다. NLB는 기본이 꺼짐입니다.
Q: 한 ALB에서 `shop.example.com`과 `blog.example.com`을 각각의 인증서로 HTTPS 서비스하려면?
A: HTTPS 리스너에 두 인증서를 붙이면 SNI로 호스트 이름에 맞는 인증서를 고릅니다.
Q: 앱이 응답하지 않는 인스턴스를 ASG가 바꾸지 않습니다. 무엇을 바꿔야 하나요?
A: ASG의 상태 확인 유형에 ELB 상태 확인을 켭니다.
Q: 매주 금요일 18시에 판매 이벤트가 있습니다. 미리 용량을 늘리는 정책은?
A: 예약 조정입니다.
